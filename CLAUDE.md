## Project overview

Mergulho Virtual ("Virtual Diving") is a Unity-based AR mobile app targeting Android (ARCore) with iOS support for the photo-picker / sighting-report path. It identifies marine life via on-device ONNX classification of the AR camera feed, overlays a location-aware UI (GPS + reverse geocoding of Fernando de Noronha beaches), places AR 3D models (e.g. Tubarão Martelo / hammerhead shark) the user can tap for info, reports sightings counts pulled from a backend HTTP API, lets users contribute their own sightings (photo + metadata) via a queued background upload, shows the project's latest Instagram post on the About screen (served through the backend, never directly from Instagram), and carries an in-app library of educational articles ("Conteúdo educativo") authored as Markdown in the repo and compiled to typed block JSON at build time, so no Markdown parser ships in the APK.

**The UI is mid-rebuild.** The app now boots into a **UI Toolkit shell** (four destinations — Início / Mergulho / Praias / Avistamentos) built on the Material Design 3 **design system** at [Assets/DesignSystem/](src/app/MergulhoVirtual/Assets/DesignSystem/), against a designer's V2 prototype; the original uGUI screens are being strangled one slice at a time per [DESIGN_IMPLEMENTATION.md](DESIGN_IMPLEMENTATION.md). Slices 0–4 have landed (SOS is Slice 5, deleting the legacy screens is Slice 6). **Nothing has been run on a device**, and Slice 4 put a UI Toolkit overlay on the live AR camera — the panel-over-camera stacking and hit-testing it rests on are the top of the device checklist in [docs/handover-v2-redesign.md](docs/handover-v2-redesign.md) §8. Start at **App shell, scene layout and the AR performance gate** and **Phase 3 — UI layer** below before touching any screen.

The Unity project lives at [src/app/MergulhoVirtual/](src/app/MergulhoVirtual/) and the FastAPI backend at [src/backend/](src/backend/) — **all compiled/served code is under `src/`**. The repo root above it holds only docs and tooling: this file, [README.md](README.md), the two design/plan documents ([DESIGN_IMPLEMENTATION.md](DESIGN_IMPLEMENTATION.md), [design-system-implementation-plan.md](design-system-implementation-plan.md)), [InstagramPlan.md](InstagramPlan.md), the Firebase/Firestore config (`firebase.json`, `.firebaserc`, `firestore.indexes.json`), the [Makefile](Makefile), and three directories — [tools/](tools/) (stdlib-Python generators), [docs/](docs/), and **[content/](content/)**, which is authoring input rather than code: `content/articles/*.md` is the source of the educational article library and `make articles` compiles it *into* the Unity project (see **Educational article library** under Architecture). Gitignored build output also lands at the root (`.shots/`, `.shots-devices/`, `.arsim/`, `.figma-sync/`).

- Unity editor version: `6000.3.14f1` (Unity 6) — see [ProjectVersion.txt](src/app/MergulhoVirtual/ProjectSettings/ProjectVersion.txt). Match this when opening the project; Unity will otherwise auto-upgrade assets.
- Render pipeline: URP 17.3.0 (`com.unity.render-pipelines.universal`).
- Solution file: [MergulhoVirtual.slnx](src/app/MergulhoVirtual/MergulhoVirtual.slnx) (note: `.slnx`, not `.sln`).

## Build, run, and test

There is no CLI build wrapper; all development goes through the Unity Editor opened on `src/app/MergulhoVirtual/`.

- **Play / iterate**: open [Assets/Scenes/MainScene.unity](src/app/MergulhoVirtual/Assets/Scenes/MainScene.unity) and press Play. AR features that depend on real device sensors (camera, GPS) are stubbed in editor — see [GPSHandler.cs:73-80](src/app/MergulhoVirtual/Assets/Scripts/GPSHandler.cs#L73-L80) which hardcodes a Fernando de Noronha coordinate under `UNITY_EDITOR`. Note: the stub coordinate `(-3.85, -32.44)` now falls inside **Praia da Cacimba do Padre**'s real OSM outline, so editor `CurrentPlaceName` auto-resolves to that beach on Play (it was null before the 2026-07 places.json migration to precise coastlines). To exercise the override path in-editor, pick a different beach from the hero selector on the **Praias** tab; to test the "off all beaches → null" path (which the Praias landing has a real state for), move the stub to a coordinate >`beachBufferMeters` from every polygon.
- **Android build**: File > Build Profiles > Android. ARCore + FineLocation/CoarseLocation permissions are required at runtime; the code requests them in [GPSHandler.cs:32-38](src/app/MergulhoVirtual/Assets/Scripts/GPSHandler.cs#L32-L38).
- **On-device logs**: `com.unity.mobile.android-logcat` is included — use Window > Analysis > Android Logcat rather than plain `adb logcat` to get Unity-aware filtering.
- **Seeing the UI without a device**: `make ds-shots` renders every UI Toolkit screen and design-system gallery section to PNGs in a gitignored `.shots/` — see **Headless workflow** under **Design system**. Faster than a build for anything layout- or token-shaped.
- **Seeing the AR stabilization without a beach**: `make ar-sim` replays the whole stabilizer family against a synthetic wave-drift model and prints the metrics table; `make ar-sweep BLOCK=device|jumps|threshold|budget` re-runs it across the model's least-grounded parameters and reports whether the *ranking* survives (omit `BLOCK` for all four — it is much slower than `ar-sim`). Editor **closed**, same as the `ds-*` targets. Output lands in a gitignored `.arsim/` at the repo root (one CSV time series per scenario × stabilizer, plus a `manifest.json` recording seeds, model parameters and metrics), the readable table is echoed out of `Logs/ar-sim.log` / `Logs/ar-sweep.log`, and `make ar-sim ARSIM=pan` filters to one scenario. This is the only thing that verifies anything in [Assets/Scripts/AR/](src/app/MergulhoVirtual/Assets/Scripts/AR/) — see **Offline wave-drift simulator** under Architecture.
- **Educational articles**: `make articles` compiles `content/articles/*.md` into `Assets/Resources/articles.json`; `make articles-check` validates and writes nothing (CI / pre-commit, non-zero exit on any error). **These two are the only content targets that never touch Unity — stdlib Python, no venv, and the editor may stay OPEN**, unlike every `ds-*` / `ui-*` / `ar-*` target. They do write inside `Assets/Resources/`, so Unity reimports the JSON (and any photo installed into `Assets/Resources/Articles/`) the next time it has focus; an unchanged corpus rewrites nothing at all, so a no-op build triggers no reimport either. `make articles VERBOSE=1` adds per-article block counts and `python3 tools/build_articles.py --self-test` runs the parser's own in-memory escaping assertions. **Neither target writes anything while any error stands** — a malformed article fails here, with a file name and a line number, rather than on a phone at a beach. ⚠️ **The JSON is a generated artifact that is committed**: edit an `.md` without re-running `make articles` and the app keeps rendering the *previous* text with nothing on screen to say so, and a working copy that has never run it gets one `[Articles]` warning plus the "could not load" state. See **Educational article library** under Architecture.
- **Tests**: EditMode + PlayMode, NUnit (`com.unity.test-framework` 1.6.0). Prefer the **headless make targets** (editor closed): `make ds-test` runs EditMode across `MergulhoVirtual.DesignSystem.Tests.Editor`, `MergulhoVirtual.UI.Tests.Editor` and `Assembly-CSharp-Editor`, and `make ds-test-play` runs the PlayMode interaction tests. Current state: **874/874 EditMode** (2026-09-30), **27/27 PlayMode** (2026-09-29, unchanged) — 177 in `MergulhoVirtual.DesignSystem.Tests.Editor`, 467 in `MergulhoVirtual.UI.Tests.Editor`, 230 in `Assembly-CSharp-Editor`. The jump from 683 is the educational article library (its parser, tokens, formatter, two ViewModels and both screens). In-editor the same suites are under Window > General > Test Runner (right-click a `[Test]` method > Run for one). Tests live in three places: [Assets/Scripts/Tests/Editor/](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/) (job queue, geocoding, tides, **and the whole AR stabilization + simulator suite** — `ArCore*`, `ArSim*`, `ArStabilizationComponentTests`, `MotionGateBudgetTests`, ~115 `[Test]` methods), [Assets/UI/Tests/Editor/](src/app/MergulhoVirtual/Assets/UI/Tests/Editor/) (ViewModels + formatters + router) and [Assets/DesignSystem/Tests/](src/app/MergulhoVirtual/Assets/DesignSystem/Tests/) (components, token discipline, shape discipline, pointer interaction, stadium corners). The reverse-geocoding and beach-content tests read `Resources/*.json` via `Resources.Load`, so they need a Unity test runner (batchmode counts), not an isolated NUnit runner.
  ⚠️ **Counting the results file: count `<test-case>` elements, NOT `result=` attributes — or just run the tool.** `make ds-test` writes NUnit XML to `src/app/MergulhoVirtual/Logs/ds-test-editmode.xml`, where **every `<test-suite>` rollup and the root `<test-run>` carry the same `result="Passed"` attribute as the individual cases** — so the obvious grep over-counts by the number of suites, about 8–10 %. On the current run that is 874 cases + 71 suites + 1 run = **946** `result="Passed"` matches for **874** actual tests, and an inflated number has been mistaken for the test count more than once (including into this file). `grep -c '<test-case '` is the count; `grep -c 'result="Failed"'` is the only attribute grep that is safe (a rollup only reports Failed if a case under it did).
  **The census is now a script: `python3 tools/summarize_test_results.py src/app/MergulhoVirtual/Logs/ds-test-editmode.xml`** — stdlib only, prints `N/N passed` plus the per-assembly breakdown, names the first 25 failures with their messages, and exits non-zero if anything failed (or if the file is absent or truncated, which it reports as such instead of as "0 tests"). **Both `ds-test` and `ds-test-play` were rewired to call it**, on success and on failure, so the Makefile's summary is no longer the attribute grep it used to be. Use it rather than re-deriving a count; quote its numbers when updating the line above.
  ⚠️ **A green suite does not mean the screens are right.** Every one of these is a *structure* test — it can assert that an element exists, carries a class and raises an event, and it cannot see layout. The "Se identifique" heading collided with the field below it while the entire suite was green (see the flex-row footgun under **Design system**). After any change to flex direction, typography, padding or wrapping, **render the screens and look at them**: `make ds-shots` is the check, not `make ds-test`.

## Backend service — setup and debug mode

The FastAPI backend at [src/backend/](src/backend/) ships as a single image and runs as **one process** both in production (a GCE free-tier VM with `ROUTER_MODE=both`) and in local dev. Routes are split between two routers, gated by `ROUTER_MODE` so the same image *could* be split across processes if ever needed:
- **`/api/v1/*`** (App Check-gated, Unity-facing): `POST /api/v1/avistamentos` (multipart sighting upload), `GET /api/v1/avistamentos/count` (HUD counter), and `GET /api/v1/latest-post` + `/api/v1/latest-post/image` (cached Instagram latest post — see **Instagram latest post** under Architecture). See [api/endpoints/avistamentos_api.py](src/backend/api/endpoints/avistamentos_api.py) and [instagram_api.py](src/backend/api/endpoints/instagram_api.py). The router has a global `Depends(verify_app_check)` in [api/api.py](src/backend/api/api.py) — every request must carry a valid `X-Firebase-AppCheck` header in non-debug mode.
- **`/` + `/avistamentos*` + `/telemetria*`** (Cloudflare Access-gated, operator-facing): landing, paginated list, view, edit/delete forms, telemetry list + count. HTML-only — the old `?format=json` content negotiation is gone (admin is HTML-only behind Cloudflare Access, no external JSON consumer). See [api/endpoints/avistamentos_admin.py](src/backend/api/endpoints/avistamentos_admin.py) and [telemetria_admin.py](src/backend/api/endpoints/telemetria_admin.py).

Which router(s) the process serves is gated by **`ROUTER_MODE`** in [config.py](src/backend/config.py):
- `ROUTER_MODE=api` — `/api/v1/*` only (Unity-facing, App Check in code).
- `ROUTER_MODE=admin` — admin HTML only (`/` + `/avistamentos*` + `/telemetria*`, operator-facing, Cloudflare Access at the edge).
- `ROUTER_MODE=both` (default) — single process serves everything; this is what both the production VM and local dev run. No path collisions because the two routers own disjoint (method, path) pairs.

See **Production deploy — GCE free-tier VM + Cloudflare** below for the deploy steps.

Two credential modes, controlled by `BACKEND_DEBUG`:
- **Prod / cloud mode** (default, `BACKEND_DEBUG` unset): real Firestore + GCS via **Application Default Credentials** (ADC). On the GCE VM the attached service account is auto-detected via the metadata server — no key file in the image. Locally outside debug mode, set `GOOGLE_APPLICATION_CREDENTIALS=./serviceAccountKey.json` (or run `gcloud auth application-default login`); the legacy hardcoded `from_service_account_json('./serviceAccountKey.json')` path in [database.py](src/backend/database.py) / [services/storage.py](src/backend/services/storage.py) is gone, replaced by `firestore.Client()` / `storage.Client()` which read ADC.
- **Debug / local mode** (`BACKEND_DEBUG=1`): Firestore client points at the local emulator via `FIRESTORE_EMULATOR_HOST`; GCS writes go to the local folder `src/backend/local_storage/{originals,imagens}/` and are served by FastAPI at `/local_storage/...`. **App Check verification is also bypassed** (see [api/dependencies.py](src/backend/api/dependencies.py)) so the LAN backend keeps accepting unauthenticated requests from the Unity editor. Same code paths as prod otherwise — `db.collection().document().set(…)`, `services.storage.upload_bytes(…)`, `generate_signed_url(…)`, just routed at local substitutes. All four pieces (Firestore, GCS, App Check, seed data) are gated on `DEBUG_MODE` in [config.py](src/backend/config.py).

### One-time setup

- **Python env**: this repo uses the conda env `trn_backend` (Python 3.12). Activate it (`conda activate trn_backend`) and `pip install -r src/backend/requirements.txt` — `Pillow`, `pillow-heif`, `google-cloud-firestore`, `google-cloud-storage`, `fastapi`, `uvicorn`, etc. are all pinned there.
- **Java JRE** (only for debug mode — the Firestore emulator is a Java app):
  ```bash
  sudo apt install default-jre-headless
  ```
- **gcloud CLI + Firestore emulator component** (only for debug mode). **Do not install gcloud via snap** — snap sandboxes the install so `gcloud components install` errors out with `"You cannot perform this action because this Google Cloud CLI installation is managed by an external package manager"`, and the snap variant has no Firestore-emulator component of its own. Use Google's apt repo, which ships the emulator as its own package:
  ```bash
  sudo snap remove google-cloud-cli  # only if you previously installed via snap
  sudo apt-get install apt-transport-https ca-certificates gnupg curl
  curl https://packages.cloud.google.com/apt/doc/apt-key.gpg | sudo gpg --dearmor -o /usr/share/keyrings/cloud.google.gpg
  echo "deb [signed-by=/usr/share/keyrings/cloud.google.gpg] https://packages.cloud.google.com/apt cloud-sdk main" | sudo tee /etc/apt/sources.list.d/google-cloud-sdk.list
  sudo apt-get update
  sudo apt-get install google-cloud-cli google-cloud-cli-firestore-emulator
  ```
  The emulator runs offline — no `gcloud auth login` or project config required.

### Running in debug mode

Two terminals:

```bash
# Terminal 1 — Firestore emulator (port matches FIRESTORE_EMULATOR_HOST in config.py)
gcloud emulators firestore start --host-port=localhost:8080

# Terminal 2 — backend
conda activate trn_backend
cd src/backend
BACKEND_DEBUG=1 uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

The emulator is **in-memory by default** — killing it wipes everything and the next backend startup re-seeds from scratch. Pass `--data-dir=./.firestore-emulator-data` to persist across emulator restarts.

What `BACKEND_DEBUG=1` actually changes (all in [config.py](src/backend/config.py)):
- [database.py](src/backend/database.py) sets `os.environ["FIRESTORE_EMULATOR_HOST"]` from `FIRESTORE_EMULATOR_HOST` (default `localhost:8080`) before importing `google.cloud.firestore`, then constructs `firestore.Client(project=FIRESTORE_EMULATOR_PROJECT)` (default `mergulho-virtual-debug`). The env var is the SDK's documented switch — same client class as prod, no auth, routes to the emulator's gRPC endpoint.
- [services/storage.py](src/backend/services/storage.py) writes bytes to `LOCAL_STORAGE_DIR / blob_name` (`src/backend/local_storage/<blob>`) and `generate_signed_url` returns a relative `/local_storage/<blob>` URL — no signing, no expiration. Same blob layout as the prod bucket (`originals/<registro>.<ext>`, `imagens/<registro>.jpg`), so [read_avistamento](src/backend/api/endpoints/avistamentos_admin.py#L126) and `view.html` work unchanged.
- [main.py](src/backend/main.py) `mkdir`s `local_storage/` and mounts it at `/local_storage` via `StaticFiles`. The `mkdir` is load-bearing — `StaticFiles(directory=...)` validates the directory exists at construction time, not at first request.

### Debug seed data

On startup, the FastAPI `lifespan` hook in [main.py](src/backend/main.py) calls [scripts/seed_debug_data.py](src/backend/scripts/seed_debug_data.py)'s `seed_avistamentos()` if `BACKEND_DEBUG=1`. Six sample sightings (`seed-001` … `seed-006`) across distinct beaches/species/dates, each with a Pillow-generated solid-color placeholder JPEG that's written to both `local_storage/originals/<id>.jpg` and `local_storage/imagens/<id>.jpg`. Each Firestore doc carries `modo_registro: "seed"` as a sentinel — makes them easy to spot among real app submissions (`"app"`) and CSV-imported pre-app records (other values).

- **Idempotent**: each entry uses a stable doc id; the script checks `coll.document(registro).get().exists` per id and skips if present. Safe to re-run, safe across uvicorn `--reload` cycles.
- **Failure-tolerant**: the lifespan hook wraps the call in `try/except` and downgrades errors to `logger.warning("Debug seed skipped: %s", ...)`. If the emulator isn't up yet when uvicorn boots (race), the seed silently no-ops and the server still serves; rerun the seed manually once the emulator is up.
- **Manual reseed** (without restarting the server, e.g. after wiping the emulator):
  ```bash
  cd src/backend
  BACKEND_DEBUG=1 python -m scripts.seed_debug_data
  ```
- **Adding more sightings**: append to the `SEED_AVISTAMENTOS` list at the top of [seed_debug_data.py](src/backend/scripts/seed_debug_data.py). Beach names must match entries in [places.json](src/app/MergulhoVirtual/Assets/Resources/places.json) exactly (case + accents) if you want the Unity beach filter to match them later — same constraint as `BeachSharkSpawner`'s Inspector list.
- **Instagram seed**: the same lifespan hook also calls `seed_instagram_post()` in debug mode — a placeholder post + Pillow JPEG so the About-screen Instagram widget works in the editor with zero Meta credentials. It checks the stored doc's `media_id` sentinel and never clobbers a real fetched post (relevant if you point a debug backend at real credentials).

**Architecture**: one `e2-micro` VM in `us-central1` runs a **single uvicorn process with `ROUTER_MODE=both`** ([config.py](src/backend/config.py)) — no router split, no second machine. The two trust boundaries are gated differently from that one process:
- `/api/v1/*` (Unity-facing) — **Firebase App Check**, verified in code ([api/dependencies.py](src/backend/api/dependencies.py)). There is **no user login** in the app; App Check attests the request came from a genuine, untampered install of the signed app (Play Integrity on Android, App Attest on iOS), not from `curl` or a repackaged APK. ## Firestore indexes — declarative + deployed via Firebase CLI

The operator UI's [Avistamentos list](src/backend/templates/avistamentos/list.html) lets you filter by `ano_registro`, `mes_registro`, `dia_registro`, `local`, `nome_popular` (and more later); the result list orders by `registro`. Firestore requires a **pre-built composite index for every unique combination of equality-filtered fields + the order_by field** — a query like `where("ano_registro", "==", "2024").order_by("registro")` will return a `FailedPrecondition: The query requires an index` 500 on the first hit, with a console URL to provision it one at a time. Clicking those URLs as errors arrive doesn't scale past a handful of filters, so the project uses indexes-as-code.

### File layout (repo root, not inside `src/backend/`)

- [tools/generate_firestore_indexes.py](tools/generate_firestore_indexes.py) — declarative source of truth. `QUERY_PATTERNS` at the top lists each `(collection, filter_fields, sort_field)` tuple. The script enumerates every non-empty subset of `filter_fields`, appends `sort_field`, and emits the Firebase-CLI JSON shape. Stdlib only; no venv.
- [firestore.indexes.json](firestore.indexes.json) — **generated; do not hand-edit**. 32 composite indexes currently (31 for avistamentos = 2^5 - 1 filter subsets × the `registro` sort field, 1 for telemetria = `(oid, date)`).
- [firebase.json](firebase.json) — minimal Firebase config; the only key is `firestore.indexes`. Firestore security rules aren't configured because all access is server-side via ADC (the backend), not from client SDKs.
- [.firebaserc](.firebaserc) — project alias; `default` points at `mergulho-virtual-2025`.

### One-time setup

Firebase CLI ships as a standalone binary (no Node/npm needed — `sudo npm install -g firebase-tools` errors with `npm: command not found` on a vanilla Linux box):

```bash
curl -sL https://firebase.tools | bash   # installs to /usr/local/bin/firebase
firebase login                            # browser OAuth, one-time
```

### Deploy

```bash
# Run from repo root (where firebase.json lives).
firebase deploy --only firestore:indexes
```

The CLI returns in seconds, but Firestore backfills each index in the background — the Firebase Console (Firestore → Indexes tab) shows them as "Building" for **5–15 minutes** on the initial deploy. Queries that need a still-building index get the same `FailedPrecondition` 500 until it flips to "Enabled." Subsequent deploys with no diff are fast; deploys that add a single new index also build in the background.

The backend deploy (VM `git pull` + `systemctl restart`) and the index deploy (`firebase deploy --only firestore:indexes`) are **independent steps with no shared toolchain** — touching one doesn't touch the other.

### Adding a new filter to the operator UI

1. Append the field name to the relevant pattern's `filter_fields` in [tools/generate_firestore_indexes.py](tools/generate_firestore_indexes.py).
2. `python3 tools/generate_firestore_indexes.py` — regenerates `firestore.indexes.json`.
3. `firebase deploy --only firestore:indexes` — backfill in 5–15 min.
4. Update [services/avistamentos.py](src/backend/services/avistamentos.py)'s `_build_query` to accept the new field, the endpoint in [api/endpoints/avistamentos_admin.py](src/backend/api/endpoints/avistamentos_admin.py) to thread it through, and the template form in [templates/avistamentos/list.html](src/backend/templates/avistamentos/list.html).

The order is load-bearing: deploy indexes **before** rolling out the UI change, or the first filter hit goes 500.

### Scaling headroom and the 200-index limit

Firestore allows **200 composite indexes per database** (free tier; same in paid). With N filter fields all combined with one sort field, the index count is `2^N - 1`. Current state:

| Filter fields | Indexes generated |
|---|---|
| 5 (now) | 31 |
| 6 | 63 |
| 7 | 127 |
| 8 | 255 ← over the limit |

So this approach is good for ~7 filter fields. Past that, the realistic options are:
- **Drop the explicit `order_by("registro")`** and use Firestore's implicit `__name__` order. Single-field equality queries then use auto-created indexes (no composite needed); only multi-field equality queries need composites. Halves the count roughly.
- **Switch the schema to a sortable composite field** (e.g., a `data_iso` "2024-07-15" string) and use range filters on it. Drastically reduces the index count because range-on-sort-field is auto-indexed; only non-date facets (local, species) need composites alongside it.

Neither is needed yet — flag this when filter count starts pushing past 6.

### Local dev / `BACKEND_DEBUG=1`

The Firestore emulator **does not enforce indexes** — every query "just works" against it regardless of what's in `firestore.indexes.json`. This means index errors are a pure prod-mode failure mode; you can't catch a missing index by running the emulator. The fastest way to flush out missing indexes before prod is to hit each filter combo against the deployed VM admin UI (or a staging clone) and watch the logs.

## Architecture

The runtime is a small set of single-responsibility `MonoBehaviour`s wired into `MainScene`. They do not talk to each other directly — each one owns one concern and is composed via Inspector references.

### Camera-feed ML inference — [CameraFeedToInference.cs](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs)

Subscribes to `ARCameraManager.frameReceived`, samples **once a second** (`FRAME_INTERVAL`, [CameraFeedToInference.cs:56](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs#L56)), converts the `XRCpuImage` into an RGBA32 `Texture2D`, resizes to the model's input dims, and runs Unity Inference Engine (`com.unity.ai.inference` 2.6.1) on `BackendType.GPUCompute`. **The ImageNet classifier is off by default** — `runImageNetClassifier` ([CameraFeedToInference.cs:43](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs#L43)) is `false` in code and unticked in `MainScene`, so the model is never loaded, the sampled frame goes to `SeaDetector` alone, and the debug label mirrors the sea score instead of a class name; tick it to get the argmax label back. The bundled model is [Resources/mobilenet_v2.onnx](src/app/MergulhoVirtual/Assets/Resources/mobilenet_v2.onnx) (ImageNet-1k, default 224×224). Class labels come from [Resources/class_desc.txt](src/app/MergulhoVirtual/Assets/Resources/class_desc.txt) — one label per line, ImageNet classes. Output is argmax-then-label; there's no softmax or top-k. When swapping models, update both the `.onnx` asset reference in the Inspector and `class_desc.txt`; the script assumes output shape `[1, N_classes]`.

Tensor/worker lifecycle is manual: `worker` and any cached input tensors are `Dispose()`d in `OnDestroy` — follow the same pattern for any tensors you add, or you will leak GPU memory on scene reloads.

### Zero-shot sea detection — [SeaDetector.cs](src/app/MergulhoVirtual/Assets/Scripts/SeaDetector.cs) (+ hooks in [CameraFeedToInference.cs](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs))

Detects "is the camera pointing at the sea?" with **no training data**: a MobileCLIP2-S0 image encoder ([Resources/mobileclip_image_encoder.onnx](src/app/MergulhoVirtual/Assets/Resources/mobileclip_image_encoder.onnx), 45 MB, tracked via Git LFS) produces a 512-dim embedding, and "sea vs not-sea" is defined purely by precomputed text-prompt embeddings ([Resources/sea_embeddings.json](src/app/MergulhoVirtual/Assets/Resources/sea_embeddings.json): 10 classes, one `isSea` flag each). Dot products → softmax (logitScale 64.3) → sum of `isSea` probabilities → EMA smoothing → on/off hysteresis. Consumers poll `IsSeaVisible`/`SmoothedScore` or wire the `onSeaDetected`/`onSeaLost` UnityEvents (nothing consumes them yet). Tooling, prompt lists, and the offline test harness live in [tools/sea_detector/](tools/sea_detector/) (own venv at `.venv`; see its README — note `hf-hub:apple/MobileCLIP2-S0` 404s, the scripts use open_clip's built-in `MobileCLIP2-S0`+`dfndr2b` config instead). Tweaking prompts = re-run `precompute_text_embeddings.py` + re-copy the JSON; no ONNX re-export.

- **Wiring**: the component sits on `ComputerVisionServices` next to `CameraFeedToInference`, which calls `seaDetector.Classify(...)` on the same 5-second AR frame it feeds mobilenet — so it inherits the `inferenceEnabled` screen gating. `SeaDetector` auto-loads its two assets via `Resources.Load` when the Inspector slots are empty (they are, in the scene). Own `Worker`, async `ReadbackRequest` readback, no per-frame allocation.
- **Orientation is load-bearing** ([CameraFeedToInference.GetUprightCameraTexture](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs)): the `XRCpuImage` arrives sensor-native landscape regardless of how the phone is held, and a sideways frame tanks CLIP scores (a 90% beach can drop to ~10%). The frame is rotated per `Screen.orientation` **in MirrorY-converted (bottom-up) coordinates, which inverts the usual convention: Portrait needs 270°, not 90°** (confirmed empirically via the rotation sweep — portrait rot=270 scored 98%), then center-cropped to the display aspect so the model sees what the user sees, not the sensor's wider FOV.
- **Thresholds** (ON 0.5 / OFF 0.35, smoothing 0.5 at the 5 s cadence) sit in the measured gap: Noronha beach photos score 0.56–0.99, non-sea 0.01–0.31 (underwater shark close-ups ≈0.1 "pool"; sRGB→linear color-space shift is ~1% — irrelevant, verified).
- **Debug switches** (both default off): `SeaDetector.runSelfTest` classifies [Resources/sea_selftest.png](src/app/MergulhoVirtual/Assets/Resources/sea_selftest.png) (praia_do_sancho @256², uncompressed import) at startup and logs score + embedding head vs. the Python reference — expected ~82.6%, device measured 82.7%, proving on-device parity; `CameraFeedToInference.debugTryAllRotations` classifies each tick at 0/90/180/270 (blocking) and dumps `sea_debug_raw.png`/`sea_debug_upright.png` to `persistentDataPath`. Debug workflow: parity first (self-test), then orientation (sweep), then content (pull the PNGs).

### Beach AR stabilization — [Assets/Scripts/AR/](src/app/MergulhoVirtual/Assets/Scripts/AR/) (built by `Tools > Mergulho Virtual > Setup AR Stabilization`)

Stops ocean waves from fooling ARCore's visual-inertial tracking while preserving full 6DOF. Productionized from the prototype in [tools/ar/](tools/ar/) (kept as design notes — the app versions differ where flagged below). Three layers on one `ARStabilization` root GameObject, wired by [ArStabilizationBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/ArStabilizationBuilder.cs):

- **[StillnessDetector.cs](src/app/MergulhoVirtual/Assets/Scripts/AR/StillnessDetector.cs)** — IMU "is the phone physically still?" (EMA-smoothed gyro + linear accel, slow-entry/fast-exit hysteresis). **Rewritten for the new Input System** (`UnityEngine.InputSystem.Gyroscope` / `LinearAccelerationSensor`, enabled via `InputSystem.EnableDevice`) because the project runs `activeInputHandler: 1` where the prototype's `Input.gyro` throws. In editor there are no IMU devices → `HasSensors` false, gate inert (expected). Units are backend-dependent (gyro ≈ rad/s, accel ≈ g) — tune from measured `SmoothedGyro`/`SmoothedAccel` readouts (log them, or call `ArStabilizationController.BuildTelemetry()`), not assumed units.
- **[SpuriousMotionGate.cs](src/app/MergulhoVirtual/Assets/Scripts/AR/SpuriousMotionGate.cs)** — while still, per-frame AR camera translation is hallucinated, so the XR Origin is counter-shifted the same amount (camera can't be written; the TrackedPoseDriver owns it). `[DefaultExecutionOrder(100)]`. **Since 2026-09-28 it suppresses *every* translation while still.** `relocalizationJumpThreshold` used to ship at 0.35 m on the theory that a bigger single-frame jump is ARCore deliberately relocalizing and should pass through; the simulator measured that theory as a net loss in every regime, so it now ships at 0 — see the parameter table below and **Offline wave-drift simulator**.
- **[GpsArKalmanFusion.cs](src/app/MergulhoVirtual/Assets/Scripts/AR/GpsArKalmanFusion.cs)** — two 1D Kalman filters (east/north): AR displacement is the predict step (process noise ∝ meters walked), GNSS fixes are the update step (R = reported accuracy², clamped by `minGpsAccuracy`). `DriftError` = fused − AR-only estimate; `ApplyDriftCorrection()` bleeds it into the XR Origin capped at `maxCorrectionSpeed` (default 0.25 m/s). **Heading**: seeded from a 2 s compass average, then **auto-refined from the GPS track** — every `headingSegmentMeters` (8 m) walked, the AR displacement direction vs. the GNSS displacement direction re-measures the azimuth of Unity +Z (rejected when the two lengths disagree >2×, i.e. GPS jump or gated AR). This is the prototype README's "best" option and matters because a wrong heading rotates every correction.

Plus two support pieces:

- **[GnssProvider.cs](src/app/MergulhoVirtual/Assets/Scripts/AR/GnssProvider.cs)** — best-available GNSS. On Android it bypasses Unity's LocationService and subscribes to the raw `LocationManager` **GPS provider** via an `AndroidJavaProxy` LocationListener (~2 Hz, true per-fix accuracy, course speed/bearing, satellite count from extras). Callbacks arrive on the **Android main thread** — primitives are extracted immediately and handed to Unity's `Update()` through a lock; don't touch Unity APIs in the listener. Falls back to polling `Input.location` (editor/iOS/native failure). Waits for the FineLocation grant that GPSHandler requests; [AndroidManifest.xml](src/app/MergulhoVirtual/Assets/Plugins/Android/AndroidManifest.xml) now declares `ACCESS_FINE_LOCATION` explicitly (Unity only auto-injects it for `Input.location`, not for native LocationManager use). Coexists with GPSHandler's `Input.location` — separate streams, no conflict.
- **[ArStabilizationController.cs](src/app/MergulhoVirtual/Assets/Scripts/AR/ArStabilizationController.cs)** — glue at `[DefaultExecutionOrder(200)]` (after the gate): applies the GPS drift correction each LateUpdate, and when it does so, only while the user is walking (`correctOnlyWhileMoving` — shifts are invisible mid-stride; the gate holds things steady while standing). **`driftCorrectionEnabled` ships OFF as of 2026-09-28** — the whole Kalman layer measured as a large net harm, for two reasons that are not tuning problems; see the switches table below. `GpsArKalmanFusion` still runs (it predicts, updates and refines heading, and the telemetry still reads out `DriftError`), it just never writes the XR Origin. It also builds the `BuildTelemetry()` status string (IMU / gate / GNSS / fusion / switches), which now has **no on-screen consumer** — call it from a log line or a temporary readout. **It no longer persists anything**: the `TuningData` JSON round-trip through `<persistentDataPath>/ar_stabilization_tuning.json` (`LoadTuning` in `Awake`, the debounced `SaveTuning`, `MarkTuningDirty`, `ResetToDefaults`) was **removed on 2026-09-29** together with the on-beach panel that drove it, so the authored values are now the only values — nothing can override them at runtime.

**The on-beach tuning UI is GONE (removed 2026-09-29).** `ArTuningPanel.cs`, the "AJUSTE AR" pill and its panel under `ScreenUI/MainScreen/ArTuning`, the shell-building half of `ArStabilizationBuilder`, and the `ar_stabilization_tuning.json` round-trip in `ArStabilizationController` were all deleted together. **Both halves had to go together**: with the panel gone but the loader kept, any device that had ever run one tuning session would keep replaying that stale file over the authored defaults forever, with no UI left to change it. The mechanisms themselves — `StillnessDetector`, `SpuriousMotionGate`, `GnssProvider`, `GpsArKalmanFusion`, `Core/` and the controller's correction logic — are untouched, and **every parameter in the tables below is still a public/`[SerializeField]` field on its component**, editable in the Inspector and settable from code. What is lost is only the ability to change one *without a rebuild* — see **What field tuning costs now** below the tables.

**`ScreenUI/MainScreen` has therefore lost its last live tenant.** Slice 4 replaced its `TopBar` with the UI Toolkit `MergulhoScreen` (and `AppUiBuilder` deactivates it), `ArTuning` was the only reason `AppUiHost.OnRouteChanged` still switches the GameObject on for `AppRoutes.Mergulho`, and that subtree is now deleted — so all that remains under `MainScreen` is the deactivated `TopBar`. Retiring it the way Slice 6 retired `BottomNav` / `BeachesScreen` / `RegisterScreen` / `AnimalsScreen` is now unblocked but **has not been done**: it still needs the `legacyArOverlay` field and its `OnRouteChanged` branch removed from `AppUiHost`, the `mainScreen` lookup + `LegacyArOverlayChildrenToHide` removed from `AppUiBuilder`, and `ConditionsPillView`/`BeachNameView` (already permanently deactivated, live only under `TopBar`) deleted with it.

**Parameter reference** — every parameter below lives on its component as a public field: set it in the Inspector on `ARStabilization` in `MainScene` (or change the C# initializer) and rebuild. There is no runtime tuning surface, so nothing here can be changed on device.

*StillnessDetector* (IMU stillness — feeds the gate and `correctOnlyWhileMoving`):
| Parameter | Default | Meaning / how to tune |
|---|---|---|
| `gyroStillThreshold` | 0.12 rad/s | Smoothed rotation rate below which the phone counts as still. Hand tremor is typically 0.02–0.10 and varies per person — **raise** if `IsStill` flickers while standing (test with several people), read the actual value off the telemetry. |
| `accelStillThreshold` | 0.03 g | Same idea for smoothed linear acceleration (gravity removed). Units are backend-dependent — trust the telemetry readout, not the unit label. |
| `enterStillTime` | 0.4 s | How long the IMU must stay quiet before stillness is declared (slow entry, prevents flicker). |
| `exitMultiplier` | 1.6 | An instantaneous reading above threshold×this breaks stillness immediately (fast exit). **Lower** if `IsStill` lags when you start walking — content briefly "sticks". |
| `emaAlpha` | 0.25 | Per-frame EMA factor on the raw IMU. Lower = smoother but slower to react (interacts with both thresholds). |

*SpuriousMotionGate* (anti-wave translation gate):
| Parameter | Default | Meaning / how to tune |
|---|---|---|
| `minDelta` | 0.0005 m | Per-frame camera translation below this is ignored as float noise (0.5 mm/frame). Rarely needs touching. |
| `relocalizationJumpThreshold` | **0 m** (was 0.35) | Single-frame jumps **larger** than this are treated as ARCore deliberately relocalizing and pass through even while still; 0 = suppress everything, which is now the default. It is a **magnitude** filter and magnitude is the wrong discriminator — measured phantom jumps land at 0.27–0.35 m and genuine tracker corrections at 0.01–0.58 m, so genuine sits mostly *below* phantom and no threshold separates them. 0 is the best available value of a bad knob, not a good mechanism. |

*SpuriousMotionGate — correction budget* (seven fields added 2026-09-28; the path-based mechanism, **present but inert** because `correctionBudgetPerMeter = 0` and the entire budget block in [MotionGateCore.Step](src/app/MergulhoVirtual/Assets/Scripts/AR/Core/MotionGateCore.cs#L320) is behind that one test, so with it at 0 the gate is bit-identical to the pre-budget one): decide on distance **travelled** rather than on magnitude. A walk earns `metres × rate` of correction credit (non-wave odometry error is path-proportional: 0.34 %/m in a static scene, 14.4 %/m in a dynamic one), the gate is inert while walking so that error lands in the camera pose and is frozen in when the user stops, and only the earned amount is ever admitted back — bled in at 0.25 m/s so it is a slide, not a pop. Measured against the plain gate in the offline harness it is a **wash** (±0.5 % of the weighted composite across a 4 assumed-rate × 5 true-rate grid), which is why it is off: the budget bounds *how much* correction is admitted but still cannot tell *which* correction is genuine. Turn `correctionBudgetPerMeter` up (in the Inspector, then rebuild — the slider that used to do it at the beach is gone) once there is a real per-device measurement of that rate — the one number the whole mechanism is a function of.
| Parameter | Default | Meaning / how to tune |
|---|---|---|
| `correctionBudgetPerMeter` | **0** (off) | Master switch. Credit earned per metre travelled. The harness ran 0.07 (upper half of the measured 0.0034–0.144 bracket, on the grounds that surf is a dynamic environment), but across every cell of the assumed-rate × true-rate grid the **lowest** rate tried (0.01) scored best — mismatching costs at most 1.4 %, and the direction it points is "credit less". |
| `correctionBudgetCapM` | 1.5 m | Cap on accrued credit; past ~1.5–2 m the tracker has relocalized or lost tracking. |
| `correctionBudgetHalfLifeS` | 120 s | Half-life of *unspent* credit. Stale credit would admit a phantom correction on the strength of a walk that finished minutes ago. 0 disables. |
| `correctionFloorM` | 0.05 m | A per-frame delta at or above this counts as a candidate **correction** and may spend budget; below it is wave oscillation (~1 mm/frame nominal, ~13 mm/frame catastrophic) and is always suppressed. Also caps what one accrual window can credit. |
| `correctionBudgetWindowS` | 2 s | Credit comes from **net horizontal displacement** over each window, not summed path — a pan and the wave both move the camera and both come back. Summed 3-D path credited ~2× the distance actually walked. 0 falls back to per-frame path. |
| `correctionBudgetMinSpeedMps` | 0.25 m/s | A window only counts as travel at this average speed or above. Without it a phone sweep is paid as a walk: `tilt-down-swash` (90 s, zero travel) earned enough credit to admit a phantom correction, which is pure damage. A slow walk on sand is 0.75 m/s. |
| `correctionBleedSpeedMps` | 0.25 m/s | How fast an admitted correction is applied. 0 = in one frame, i.e. the tracker's own pop — a 1.5 m teleport is ~5.7° of apparent slide and costs more than the error it removed. Mirrors `GpsArKalmanFusion.maxCorrectionSpeed`. |

*GpsArKalmanFusion* (GPS↔AR drift filter + heading):
| Parameter | Default | Meaning / how to tune |
|---|---|---|
| `processNoisePerMeter` | 0.05 m²/m | Variance added per meter walked — how fast trust shifts from AR dead-reckoning to GNSS while moving. **Raise** if drift corrections lag on long walks; **lower** (or raise `minGpsAccuracy`) if content wobbles with GPS noise. |
| `minGpsAccuracy` | 3 m | Reported accuracies better than this are clamped (phones over-report). Effectively a floor on measurement noise R. |
| `maxUsableAccuracy` | 25 m | Fixes reporting worse accuracy than this are dropped entirely (no update step). |
| `maxCorrectionSpeed` | 0.25 m/s | Cap on how fast `ApplyDriftCorrection()` bleeds `DriftError` into the XR Origin. Keep small so corrections stay imperceptible; raise only if drift outruns the bleed. |
| `headingSegmentMeters` | 8 m | GNSS-track distance walked per heading re-measurement (AR path direction vs. GPS path direction). Smaller = calibrates sooner but noisier per segment. |
| `headingBlend` | 0.5 | Weight of each heading re-measurement after the first (1 = jump straight to the new value). |
| `compassAverageSeconds` | 2 s | Duration of the startup compass average that seeds the heading before the GPS track refines it. |

*ArStabilizationController* (switches — useful for A/B tests at the beach):
| Parameter | Default | Meaning |
|---|---|---|
| `gateEnabled` | on | Master switch for the IMU stillness gate. |
| `driftCorrectionEnabled` | **off** (was on) | Master switch for bleeding GPS drift corrections into the XR Origin. The simulator measured this layer as a large net harm in **every** scenario, `walk-calm` included — a scenario with no waves in it at all, where it dragged the world **9.4 m over 48 s** and roughly tripled camera-position RMS error (0.78 → 2.45 m; perceptual cost 2.29 → 8.93, i.e. +289 % against doing nothing). *(The code comment on the field records `0.13 → 2.65 m` — the same finding measured before the model grew its genuine, path-proportional odometry channel, which gives even the no-wave baseline a non-zero error. The 9.4 m reproduces exactly.)* Two structural causes: **(1) nothing is geo-anchored** — `Beach Shark Spawner` is a scene root (`m_Father: {fileID: 0}` in `MainScene.unity`), not a child of the XR Origin, so the animals live at fixed Unity world coordinates and shifting the XR Origin toward a GPS estimate cannot correct content that was never in GPS space; it only slides the *user* relative to it. **(2) GPS noise (~1–4 m) is an order of magnitude larger than the wave-induced error it was written to fix** (0.05–0.3 m, [docs/ar-wave-drift-research.md](docs/ar-wave-drift-research.md) §3), so the filter spends most of its time chasing that noise at the full `maxCorrectionSpeed` slew. It remains the **right** tool for bounding minutes-scale *geo* drift, so re-enable it if geo-anchored content is ever added — in the Inspector now, and `BuildTelemetry()`'s last line still reads `Correção ligada/DESLIGADA` if you log it. |

*GnssProvider* *(changing either needs a native re-subscribe, so they were never runtime-tunable even when the panel existed)*: `minTimeMs` (500 ms) and `minDistanceM` (0 m) — the minimum interval/distance between native GPS fixes requested from Android's `LocationManager`.

Re-running the builder replaces the `ARStabilization` root only — it no longer builds any UI. **It also resets every parameter on it to its C# default**, so anything tuned in the Inspector is lost; same iterate-in-code-XOR-editor rule as the other builders.

**What field tuning costs now.** Nothing in the stack can be changed on a device any more: changing any value means Inspector edit (or code edit) → `make apk` → reinstall, and a full IL2CPP/ARM64 build is 10–30 min. The parameters that were *only* practically settable in the field, because their right value is a property of the phone and the beach rather than something the offline simulator can answer, are: `gyroStillThreshold` and `accelStillThreshold` (hand tremor differs per person and the IMU backend's units differ per device — these were meant to be read off the live telemetry and dialled in on the spot, with several people holding the phone), `exitMultiplier` (whether `IsStill` lags when you start walking), `correctionBudgetPerMeter` (the master switch for the correction budget: its whole point was to be raised at the beach once someone measures this device's odometry drift per metre walked — nobody has, and now nobody can without a rebuild per trial), and the three A/B switches `gateEnabled` / `driftCorrectionEnabled` / `correctOnlyWhileMoving`, which were the cheapest way to answer "is this layer helping *here*". The replacements, in order of preference: **(1)** `make ar-sim` / `make ar-sweep` for anything the seeded model covers — which is how the last three defaults were decided, and is strictly better evidence than a slider; **(2)** log `BuildTelemetry()` and read it over Android Logcat to *measure* on the beach, then change the value once — the measure-then-set half of the old loop still works, it is only the set half that now needs a build; **(3)** if a genuine multi-value sweep is ever needed on a real beach again, build a throwaway debug build that cycles a small set of candidate values on a timer or a tap, rather than resurrecting a general-purpose panel.

### Offline wave-drift simulator — [Assets/Editor/ArSim/](src/app/MergulhoVirtual/Assets/Editor/ArSim/) (`make ar-sim` / `make ar-sweep`)

**Why it exists.** Everything in the section above was written against a physical hypothesis and shipped unverified, because the only way to exercise it is to stand in front of breaking surf holding an Android build — and that is exactly the situation in which nothing can be *measured*. Kalman tuning had already failed once for that reason: parameters were changed, nobody could say whether the result was better, and the on-beach tuning panel (since removed) was built because of it. The simulator replaces the beach with a seeded model and scores every stabilizer against every scenario in a few minutes with the editor closed (15 scenarios × 19 stabilizer configurations × 3 seeded repeats — 6 for the two travelled-then-stood rows). Its first three findings were the three changed defaults documented above, two of which turned shipped code **off**.

**The `Core/` extraction is what made it possible** ([Assets/Scripts/AR/Core/](src/app/MergulhoVirtual/Assets/Scripts/AR/Core/)). [StillnessCore](src/app/MergulhoVirtual/Assets/Scripts/AR/Core/StillnessCore.cs), [MotionGateCore](src/app/MergulhoVirtual/Assets/Scripts/AR/Core/MotionGateCore.cs) and [DriftFusionCore](src/app/MergulhoVirtual/Assets/Scripts/AR/Core/DriftFusionCore.cs) (plus `HeadingSeedAccumulator`) hold every decision and all the arithmetic, **engine-free by contract** — no `Transform`, no `Input`, no `Time`, no `MonoBehaviour`, no `Debug`; every input, the frame delta included, arrives as an argument to `Step`. They are `internal`, and the tests and the harness see them through the `InternalsVisibleTo("Assembly-CSharp-Editor")` that was already in [Assets/Scripts/AssemblyInfo.cs](src/app/MergulhoVirtual/Assets/Scripts/AssemblyInfo.cs) for the JobQueue tests — no new seam. The three MonoBehaviours are now thin forwarders (sensor plumbing, Transform reads, the XR Origin write), and **each one copies its public fields into `core.Config` every frame rather than once**. That is not stylistic: it is the only thing that keeps a value written to those fields while the app runs (an Inspector edit during Play; a slider drag, back when the tuning panel existed) taking effect on the next frame, and "hoist the copy into `Awake`" is the natural-looking cleanup that would silently kill it — which is why `ArStabilizationComponentTests.Gate_LiveFieldEdits_TakeEffectOnTheVeryNextFrame` and `Fusion_Component_MatchesTheReferenceImplementation_AndHonoursLiveEdits` change a field mid-sequence and assert the behaviour changes on the next frame.

The extraction was *proven* behaviour-preserving, not assumed: [ArCoreReference.cs](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/ArCoreReference.cs) holds verbatim transcriptions of the pre-extraction algorithms, [ArCoreCharacterizationTests.cs](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/ArCoreCharacterizationTests.cs) replays core and reference frame-by-frame over long deterministic sequences that cross every branch **and** pins hard-coded goldens so a future edit cannot "fix" the reference and the core in one stroke and stay green, and [ArStabilizationComponentTests.cs](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/ArStabilizationComponentTests.cs) closes the other half — component == core, including the Transform feedback loop and the fusion `Start` coroutine. The chain *component == core == pre-refactor shipped code* is therefore closed permanently, not just at the moment of the refactor.

**Nothing in the harness ships.** `Assets/Editor/ArSim/` carries no asmdef, so it compiles into `Assembly-CSharp-Editor`: the wave model, the scenarios, the candidate stabilizers and `StepDetectorCore` are all editor-only and a device build cannot see them. Corollary — if a candidate is ever adopted, its core has to **move** to `Assets/Scripts/AR/Core/`.

**Pluggable candidates** — [IArStabilizer.cs](src/app/MergulhoVirtual/Assets/Editor/ArSim/IArStabilizer.cs): `Name` / `Describe()` / `Reset()` / `Step(in ArFrameSample, FakeArRig)`, and **the only output channel is `rig.OriginPos`** — the same single lever the shipped stack has on device, so nothing can cheat by reaching around the AR rig, and ground truth is never handed to a stabilizer. An optional second face, `IArStabilizerDiagnostics`, feeds the report's diagnostics columns (`SuppressingNow`, `GateSuppressedPathM`, heading state, a `Summarize()` line); a candidate without one prints dashes. **Adding a candidate is one line** in `ArStabilizerRegistry.Factories` — the runner, the report, the CSVs and the manifest all pick it up — and several registry rows are a `MotionGateCore.Settings` object initializer rather than new code, which is the most useful thing a candidate can be. [FakeArRig](src/app/MergulhoVirtual/Assets/Editor/ArSim/FakeArRig.cs) is deliberately minimal but reproduces **the feedback loop**: `CameraWorldPos = OriginPos + SessionPos`, so a stabilizer's own correction changes what it measures next frame. `MotionGateCore`'s `lastCamPos` bookkeeping only makes sense inside that loop; a harness that handed it the raw session pose would be testing a different algorithm.

**Adding a scenario is also one line**, in `ArSimScenarios.All()` ([ArSimScenario.cs:180](src/app/MergulhoVirtual/Assets/Editor/ArSim/ArSimScenario.cs#L180)): a motion script (`MotionSegment.Standing` / `Walking` / `Shuffling` / `SlowPan` / `FastPan`), a `WaveDriftModel` preset, a `SyntheticImu`, a `SyntheticGnss`, a frame rate and a `SessionProfile`. The profile is what the composite weights by — `SessionTimeWeights` is **standing 55 % / panning 25 % / walking 20 %**, a guess at the usage profile and not a measurement, and `SessionProfile.Excluded` keeps a diagnostic run (the 60 Hz probe, `walk-then-stand`, `mixed-session`) out of the weighting entirely. Two scenario mechanics that are easy to miss and both load-bearing: a `Pan` segment carries a **pivot radius** (wrist ~0.05 m / elbow ~0.15 m / torso ~0.30 m) because nobody rotates a phone about its optical centre, so a 50–110° sweep mixes 0.10–0.30 m of *genuine* translation into the phantom drift; and `MetricsStartS` simulates a prologue it does not **score**, which is how `walk-then-look` measures the *standing* posture while the tracker carries the odometry error a real ~46 m walk would have left it holding. Standing from a clean session is a modelling error, and one that happens to favour suppress-everything.

**The wave model** ([WaveDriftModel.cs](src/app/MergulhoVirtual/Assets/Editor/ArSim/WaveDriftModel.cs)) is a transcription of [docs/ar-wave-drift-research.md](docs/ar-wave-drift-research.md) §3 (read that for the evidence; it is not restated here), and **every constant carries its evidence tag — `[M]` measured/cited, `[D]` derived from measured values, `[E]` extrapolated, i.e. a defensible guess with no measurement behind it.** Check the tag before trusting a number: much of §3 is `[D]` or `[E]`. Five properties do the work, and all five change the results:

1. **The error frame is world-fixed, not camera-local** (§3.0). The phantom translation lives in {seaward, alongshore, up} and does not rotate with the phone, so panning away lowers the *amplitude* (the near water leaves the frame) and never changes the *direction*. Emitting drift along the camera's forward axis would be wrong the moment the user turns — and panning is this app's commonest posture.
2. **An asymmetric-sawtooth seaward ratchet** (§1.4, §3.3). Foam flows shoreward, so the tracker infers the camera moved *seaward*; each wave's pulse only partly relaxes back (`relaxationFraction` 0.65 — flagged as the **softest number in the model**, and alone deciding whether the drift is bounded or a runaway ramp), so a residual accumulates until it is capped or a relocalization jump takes it back. Rendered, that is content creeping toward the viewer and growing, then snapping away.
3. **Amplitude set by the nearest moving water via 1/Z²** (§1.2, §3.1). `waterRangeNearM` is the dominant knob — the swash 3 m from your feet outweighs the whole bay — so camera *pitch* matters enormously, which is what `tilt-down-swash` exists to probe.
4. **Four frequency bands under a 1/f² IMU ceiling** (§1.3, §3.2). Groundswell Tp 14 s, wind sea 9 s, swash 22 s — each a 5-component narrowband process, not a sine — amplitude-modulated by a 110 s **wave-group envelope** that is deliberately *not* a fourth oscillator. The accelerometer can only veto *accelerating* phantom motion, so admissible amplitude is **`A_max = a_th/(2πf)²`**: long swell hurts far more than short wind sea, and a phone with a worse accel bias (measured 0.018–0.206 m/s², a ~17× spread in admissible amplitude) drifts far more. Nothing above 0.5 Hz is simulated at all, because the admissible amplitude there is below ARCore's own jitter floor and adding it would make the simulator *less* faithful.
5. **A genuine, non-wave registration error proportional to distance travelled** — added late and load-bearing. Without it every relocalization jump was by construction a correction of the model's own ratchet, which the gate has already cancelled, so discarding jumps was free and "suppress everything" won against a simulator with no mechanism able to charge it anything. That was a **modelling gap, not a result**. The rate is bracketed by measurement (0.34 %/m for ARCore in an ordinary static scene, 14.4 %/m for AR systems in a large dynamic environment) with the model defaulting to 3 %/m, and `genuineDriftPerMeterPath = 0` recovers the older model bit-exactly. What makes this channel structurally uncancellable is the whole point: it accrues with *real travel*, the gate is inert by design while the IMU reports travel, so it lands in the camera pose and the gate freezes it in the moment the user stops.

**The metrics are perceptual, not pose error** ([ArSimMetrics.cs](src/app/MergulhoVirtual/Assets/Editor/ArSim/ArSimMetrics.cs)). A virtual animal is anchored 15 m out at session start and the columns describe how it *appears* to move; the camera's rotation is assumed correct for every stabilizer (VIO orientation is well-conditioned, and neither the gate nor the drift correction touches it), so the whole error is camera world-position error projected to an angle. `driftDeg`/`driftP95` is apparent-bearing error, `jitDeg/s` is the RMS rate of it over a fixed **100 ms** window — fixed *time*, so the 30 Hz and 60 Hz runs are comparable instead of differing by a sampling artefact — `fidel` is recovered ÷ true motion while walking, and `cost` collapses them into equivalent degrees: `driftP95 + 4·jit + 11.4·range + 30·|1−fidel|`. Drift and jitter are separated on purpose: a 3° wander over a minute is barely noticeable, 3° of oscillation at wave period is what makes the app look broken.

**`range%` matters as much as bearing, and this is the non-obvious one.** The phantom drift is seaward and the user is looking seaward, so most of the error lies *along* the line of sight — it changes the animal's apparent **size** and barely moves its bearing at all, and a bearing-only metric is blind to it. `rotation-only` is the proof: on `walk-then-look` it scores 0.07° of apparent-bearing error — flawless, by that column — while being **298 % wrong about the animal's distance**. The exchange rate (11.4°) is the angular size a 3 m shark subtends at 15 m, so a 10 % range error is charged as ~1.1° of apparent slide.

**Negative results — five mechanisms that were built, measured, and lost.** Each is still in the registry so the comparison stays reproducible, and each lost for a *different* reason that is not the obvious one. Don't re-try one without an argument that engages its specific failure:

- **Accel-only gating** (`accel-gate` — the gyro threshold raised to 1e6 so the accel channel decides alone). The premise is right: the gate corrects *translation*, rotation does not imply translation, and including the gyro is exactly what makes panning (25 % of session time) switch the gate off while the user has not travelled anywhere. Two things sink it. First, **while jump-passthrough was on the extra suppression bought nothing** — every additional suppressed frame is another frame in which a phantom offset can arrive above the threshold and be banked permanently, and `accel-gate` lands level with `gate-only` on the standing group (3.01 vs 3.02). Turn the threshold to 0 and the extra suppression finally pays (`accel-gate-absorb` 1.04 vs `gate-absorb` 1.19 standing) — i.e. the jump fix was the prerequisite, not the companion. Second, and decisively: it **loses the panning group it was built for** (2.26 vs 1.42), because a pan is not pure rotation — the pivot radius makes the sweep genuinely translate the camera, and an accel-only gate calls that "still" and suppresses it (`false m` 4.44 on `pan-waves` against the plain gate's 0.00). Composite either way: 3.36 / 2.23 against 3.12 / 2.10.
- **Rotation-only** (`rotation-only` — discard AR translation entirely and pin the camera's world position). It dominates every standing and panning metric, as it must. Then **50 m of walking costs ~87° p95 bearing error** and ~29 m of position error: the anchored animal ends up behind you (`fidel` 0.00, walking-group cost 129 vs the plain gate's 5.5). ARCore does not honour `TrackingMode.RotationOnly` (§4.1 A3 — ARKit does), so this was implemented the only way it can be, by counter-shifting the origin, which at least means the simulated version is the shippable one.
- **The graded / IMU-arbiter gate** (`graded-gate` — suppression weight `w ∈ [0,1]` from the band-limited accelerometer instead of binary on/off). The interesting part is why the *obvious* scale for `w` is arithmetically impossible: the IMU admissibility ceiling `A_max = a_th/(2πf)²` is ≈ 0.26 m at the groundswell band and the reference device bias, **three to four times the nominal regime's 0.075 m phantom amplitude** — the ceiling *certifies the phantom as admissible*, which is precisely why the phantom exists at all. Grading on "excess over what the IMU can justify" therefore suppresses **nothing** in the regime that matters. Grading on the other side of the same fact (how close the band-limited accel sits to its own noise floor) does fire, but only the **gait signature** actually breaks the tie, and this one loses badly the moment the user moves (walking group 22.2, `shuffle-walk` fidelity 0.59).
- **Step-gating** (`step-gate` / `step-absorb` / `step-absorb-slow` — ask "did the user take a step?" instead of "is the phone quiet?"; waves can fake optical flow but cannot fake a gait signature). Step **counting** is excellent: 79 of 80 real steps on `walk-calm`, and **zero false positives in every standing and panning scenario**, including while panning, which is exactly where the shipped gate gives up. What kills it is **release timing** — the gate closes `steppingTimeoutS` after the last step, and on slow irregular sand gait that eats real motion (`shuffle-walk` fidelity 0.82 vs the plain gate's 0.965; walking group 11.1 vs 5.5). Stretching the timeout to 1.3 s recovers part of it (`step-absorb-slow`: walking 9.03, `shuffle-walk` fidelity 0.88) but never closes the gap, and that number was picked after seeing the score, which is what makes it tuned. It lost to the much simpler jump fix, and it would need a step detector in the runtime that the app does not have.
- **The path-proportional correction budget** (`gate-budget` plus `accel-budget` / `budget-pop` / `budget-path` / `budget-f15` / `step-budget`; parameters in the table above). The best-founded of the five and still not a better gate: it bounds *how much* correction is admitted but cannot tell **which** correction is genuine, and at the model's ~40 % genuine mixture most of the credit is spent admitting phantom corrections. The sweep's own verdict is the tell — across every cell of the assumed-rate × true-rate grid the **lowest** assumed rate tried (0.01) scored best, including where the true rate was 14.4 %/m. "The optimal assumed error rate is as low as possible" means credit nothing, which means threshold 0.

**Footguns.**

- **The tuning-JSON footgun is gone, and a stale file on an old device is now harmless.** Until 2026-09-29 `LoadTuning()` in `Awake` applied `<persistentDataPath>/ar_stabilization_tuning.json` over the authored values, `JsonUtility` filled only *missing* keys, and so a phone that had been tuned once kept replaying its old `relocalizationJumpThreshold` / `driftCorrectionEnabled` over every later build — a build that looked like it regressed on the beach might just have been replaying last week's session. Both the panel and the loader were deleted, so the file is simply never read. Any already-installed build still writes and reads it; wipe it with `adb shell run-as dev.mergulhovirtual rm files/ar_stabilization_tuning.json` if you want that state gone before installing the new build, though the new build ignores it either way.
- **There are still *two* copies of every one of these values, and the C# initializer is the weaker.** `MainScene.unity` serializes the component's fields (currently `gateEnabled: 1`, `driftCorrectionEnabled: 0`, `relocalizationJumpThreshold: 0`, `minDelta: 0.0005`), and a serialized value wins over a changed `= …` in the script — so changing a default means changing it in **both** places. A field the YAML block has never seen (the seven budget fields, today) does fall back to its initializer, which is exactly the window in which the two can silently diverge. (The device's tuning JSON used to be a third copy that beat both; it no longer exists.)
- **Changing a shipped default can break a goldened test — and pinning the test is the fix, not moving the default back.** Setting the threshold to 0 broke `ArStabilizationComponentTests.Gate_Component_MatchesTheReferenceImplementation`, which goldens against `MotionGateCore.Settings.Defaults`; the two had silently diverged, so the test started goldening a configuration the golden number never came from. The fix was to pin the settings explicitly inside the test. Hence the two-struct split in `MotionGateCore.Settings`: **`Defaults` is the pre-budget baseline every golden pins** (and `MotionGateBudgetTests.Defaults_HaveTheBudgetOff_SoEveryGoldenStaysValid` asserts it keeps the budget off, so it fails honestly instead of quietly re-meaning the golden), while **`Shipped` mirrors what the component actually authors**, kept beside it so the divergence is visible in one file instead of only in the Inspector. Note `Shipped` is *documentation, not an invariant* — nothing asserts that the component's authored fields still equal it, so if you change a default on `SpuriousMotionGate`, update `Shipped` in the same edit or the two silently drift.
- **Add, never rename, a public field on `StillnessDetector` / `SpuriousMotionGate` / `GpsArKalmanFusion` / `ArStabilizationController`.** A rename breaks two things at once with no compile error: the serialized value in `MainScene.unity`, and the **string** field names in `ArStabilizationBuilder.Wire()` (`SerializedObject.FindProperty`, which returns null silently). `[FormerlySerializedAs]` covers only the first of the two. (It used to break two more — `TuningData` plus every JSON already on a device, and the `ArTuningPanel.BuildRows()` lambdas — both removed 2026-09-29.)
- **The stillness EMA is frame-rate dependent, deliberately.** `Mathf.Lerp(previous, raw, emaAlpha)` applies the same weight *per frame* regardless of frame length, so identical motion smooths ~2× faster at 60 fps than at 30 and every threshold tuned on a 30 fps device is wrong on a 60 fps one. Nobody has noticed because `ScreenManager` pins `Application.targetFrameRate` to 30 on the AR route. It is kept bit-exact so the extraction is provably behaviour-preserving, and the defect itself is **asserted** by `ArCoreCharacterizationTests.StillnessCore_EmaIsFrameRateDependent_KnownDefect` — a test that *fails if someone fixes it*, which is the point: `alpha = 1 - exp(-dt/tau)` is a shipped-app change that needs its own measurement (the `still-waves-60hz` scenario exists to provide one), not a cleanup.
- **Reading the report: the row called `shipped` is not what ships.** It is deliberately frozen as the AS-WAS configuration (gate at 0.35 + GPS drift correction on) so the regression stays quantified; **`gate-absorb` is the as-now shipped configuration**, and `gate-only` is the intermediate (gate at 0.35, drift off). On the current full run the composite reads noop 3.33 → `shipped` 10.52 → `gate-only` 3.12 → `gate-absorb` 2.10.

**What the simulator cannot answer** — state this plainly to anyone who starts trusting the table:

- **Nobody has ever published a measurement of ARCore pointed at surf.** The research doc names this as its headline gap: the whole of §3, and therefore the whole error model, is a **derived hypothesis**. Every number the harness prints is conditional on it.
- **The perceptual cost function decides several of the close calls.** `JitterWeightSeconds = 4`, `FidelityPenaltyDeg = 30`, `RangeWeightDeg = 11.4` and the three `SessionTimeWeights` are every one of them marked PROVISIONAL in the code. The **jitter weighting** is the one that matters most: charging oscillation four seconds of equivalent offset per deg/s is what makes "admit a tracker correction in the frame it arrived" cost more than the error it removed, and that is part of why suppress-everything wins. Halve it and some of the margins above are no longer margins.
- **`genuineJumpFraction` is ungrounded and sets the budget's entire expected value.** The research doc does not address the mixture at all. The default 0.40 is taken from the harness's own self-consistency measurement (`genShare`, the time-averaged share of accumulated pose error the genuine channel holds) rather than guessed, but that only makes it internally coherent, not measured.
- **The untried discriminator is *direction*.** A phantom correction points anti-parallel to the ratchet the gate has just been cancelling, and the gate knows that vector — so a directional test is the one mechanism with a plausible chance where magnitude and path both failed. It was deliberately **not** built: it would key off the model's least-grounded parameters (`jumpDirectionBias`, `relaxationFraction`), so a win there would be unfalsifiable — the simulator would be grading the gate against homework it set itself.
- **A handful of cheap on-device experiments would turn the model into data** — §3.8's six falsification tests plus two one-call API probes from §4. **Currently deferred by the user**, so nobody has built them, and until someone does, everything above stays a hypothesis with a number attached. The high-value ones: the **sign test** (stand still, phone at the surf, anchored object placed — does content creep *toward* you between snaps? if it creeps away, flip the seaward axis and every result changes); the **tilt-down / 1-Z² test** (phone level at distant surf vs tilted onto the swash 3 m away should differ **10–50×** in drift — if they are similar, the whole 1/Z² argument and therefore §1.2 needs rebuilding); the **one-line `TrackingMode.RotationOnly` read-back** (set `requestedTrackingMode`, wait a frame, read `currentTrackingMode` — settles §4.1 A3 permanently, and it is one line); and **`GetSemanticLabelFraction(SemanticLabel.Water)`** (also one call — ARCore's `WATER` label is documented for lakes and rivers, and whether it fires on surf, foam and wet sand is unverified; if it does, it is the only water signal ARCore will ever hand back). Plus the **occlusion test** (tape over the sea half of the lens — the cheapest possible proxy for the feature mask ARCore will not give you) and the **dry-sand control** (same posture pointed inland at the dune; whatever drift remains is ARCore's baseline and must be subtracted before anything is blamed on the waves).

### Location + reverse geocoding — [GPSHandler.cs](src/app/MergulhoVirtual/Assets/Scripts/GPSHandler.cs) + [ReverseGeocoding.cs](src/app/MergulhoVirtual/Assets/Scripts/ReverseGeocoding.cs)

`GPSHandler` starts `Input.location`, polls every frame, and asks `ReverseGeocoding.GetPlaceName(Vector2(lon, lat), beachBufferMeters)` for a human-readable place. **Coordinate convention is lon→x, lat→y everywhere** — do not swap these; the tests and `places.json` both rely on it. `beachBufferMeters` is a `[SerializeField]` on `GPSHandler` (Inspector: `LocationServices → GPSHandler → Beach Buffer Meters`, default **50 m**) — the max distance from a beach outline at which the point still resolves to that beach. It also exposes `CurrentPlaceName` + a `PlaceChanged` event (fires only when the resolved beach actually changes, not every frame), and `SetBeachOverride(name)` / `ClearBeachOverride()` so the GPS result can be bypassed from UI.

`ReverseGeocoding` is a static utility that lazily loads [Resources/places.json](src/app/MergulhoVirtual/Assets/Resources/places.json) into memory on first call, caching each place's ring as a `Vector2[]` (`placePolygons`) so the per-frame `GetPlaceName` call allocates nothing. Each "place" is a named polygon of `{lat, lon}` points; the polygons may be concave and need not be quadrilaterals despite the `IsPointInQuadrilateral` name. `JsonUtility` can't parse a top-level JSON array, so the loader wraps the file in `{ "places": ... }` before deserializing — keep `places.json` as a bare array at the file level. `GetAllPlaceNames()` exposes the loaded keys and `GetAllPlaces()` the whole `PlaceData` list — the latter is what the UI layer's `BeachCatalogAdapter` reads.

**Resolver = nearest-beach-within-D, not first-match-inside.** `GetPlaceName(coord, D)` computes `BeachDistanceMeters` for every beach (0 if the point is inside the polygon via even-odd ray casting, else the meters to the nearest edge using a local flat-earth projection at `RefLatDeg = -3.85`, matching [tools/beach_polygon_debug.py](tools/beach_polygon_debug.py)) and returns the **closest** beach if it's within `D`, else null. This replaced the old first-box-in-file-order-that-contains-you logic, which made standing at e.g. Sharks Cove resolve to the giant "Porto de Santo Antônio" bounding box. Nearest-wins makes polygon overlaps harmless (file order no longer matters), so the 30 overlapping geocoder-box pairs are no longer a correctness hazard. **The geometry itself was migrated 2026-07 from geocoder bounding boxes to precise coastlines**: 13 beaches from OSM `natural=beach` ways, Cacimba do Padre from OSM multipolygon relation `5476220` (14 precise total), and 3 spots with no OSM outline (Quixaba, Sharks Cove, Buraco da Raquel) as small point-polygons centered on their best-known coordinate — sized so none overlaps a precise neighbor (no distance-0 ties). The migration is reproducible via [tools/migrate_places_to_osm.py](tools/migrate_places_to_osm.py) (`--apply`); OSM outlines are refreshed by [tools/fetch_osm_beaches.py](tools/fetch_osm_beaches.py), and [tools/beach_polygon_debug.py](tools/beach_polygon_debug.py) is an interactive matplotlib debugger for testing points against the data.

**Two names per beach, one of which is not for humans.** Since the V2 Praias slice each `places.json` entry carries both `name` and `displayName`. **`name` is the machine key** and is wired into three places that must all agree: the `Beach Shark Spawner` Inspector list, the keys of [beaches_content.json](src/app/MergulhoVirtual/Assets/Resources/beaches_content.json), and the backend's `local` field (so also the debug seed data and every CSV-imported row). Several keys are English or awkward — `Sueste Beach`, `Boldró Beach`, `Sharks Cove`, `Praia do Porto de Santo Antônio Noronha` — which is exactly why `displayName` exists: it is the pt-BR label (`Baía do Sueste`, `Praia do Boldró`, `Enseada dos Tubarões`, `Praia do Porto`) and it is **editorial, re-wordable, and never a lookup key**. `GPSHandler.CurrentPlaceName`, `PlaceChanged` and `SetBeachOverride` all speak `name`. The UI layer enforces the split in the type itself — `BeachInfo.DisplayName` ([IBeachCatalog.cs](src/app/MergulhoVirtual/Assets/UI/Interfaces/IBeachCatalog.cs)) falls back to `Name` when `displayName` is absent, so rendering it is always safe; pinned by [BeachDisplayNameTests.cs](src/app/MergulhoVirtual/Assets/UI/Tests/Editor/BeachDisplayNameTests.cs). **Renaming a `name` is a breaking change across four files and the Firestore history** — add/adjust `displayName` instead.

There is also a [Resources/praias_noronha.kml](src/app/MergulhoVirtual/Assets/Resources/praias_noronha.kml) source file; `places.json` appears to be the runtime-friendly derivation. Treat the KML as source-of-truth for beach boundaries.

### Per-beach shark spawning — [BeachSharkSpawner.cs](src/app/MergulhoVirtual/Assets/Scripts/BeachSharkSpawner.cs)

`BeachSharkSpawner` subscribes to `GPSHandler.PlaceChanged` and, via an Inspector-wired list of `{ beachName → GameObject[] sharkPrefabs }`, destroys the previously-spawned instances and instantiates the new beach's prefabs under its `spawnRoot` (defaults to its own transform). Beach names in the Inspector must match the `name` (**not** `displayName`) of an entry in [places.json](src/app/MergulhoVirtual/Assets/Resources/places.json) exactly, accents included — see the two-names note above. Shark prefabs live in [Assets/Prefabs/Sharks/](src/app/MergulhoVirtual/Assets/Prefabs/Sharks/), source FBX/textures/extracted materials in `Assets/Models/<kebab-name>/`, and Animator Controllers in [Assets/Animations/](src/app/MergulhoVirtual/Assets/Animations/) (one `.controller` per species, shared across the project rather than colocated with the model).

**The beach override moved to the UI Toolkit Praias screens.** The uGUI `BeachSelectorDropdown.cs` and the `ScreenUI/BeachesScreen` it lived under were deleted in Slice 6. The live selector is the hero pill on `PraiasScreen` / `PraiaDetalheScreen`, driven by `PraiasViewModel` → `BeachesViewModel.SelectOverride` → `GPSHandler.SetBeachOverride`. Entry 0 is still `Automático (GPS)` (→ `ClearBeachOverride()`), the list is still derived from `places.json` so new entries appear with no code change, and the override still re-points the spawner, the conditions fetch and the detail screen together. In-editor the GPS stub resolves to Cacimba do Padre, so the hero selector is how you reach any other beach.

Each spawned instance is also handed to `ArSpeciesTarget.Attach(instance, prefab.name)`, which tags it with its species key and fits it a `BoxCollider` — the shark prefabs have none of their own, so without this nothing in AR is tappable. See **Tap-to-interact** below.

There is no persistent shark GameObject in the scene; everything is spawned by `BeachSharkSpawner`. When adding a new species, follow "Adding a new shark species" below for the full FBX → prefab → spawner workflow; tap-to-info then works with no extra wiring, provided the prefab file name matches the `AnimalDef` asset name.

### Species catalog + 3D viewer rig — [AnimalDef.cs](src/app/MergulhoVirtual/Assets/Scripts/Content/AnimalDef.cs) + [UiServiceAdapters.SpeciesModelViewerAdapter](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/UiServiceAdapters.cs) + [AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs) + [EspecieScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/EspecieScreen.cs)

> **Slice 6 deleted the uGUI Animais screen; the rig and the catalog outlived it.** `ScreenUI/AnimalsScreen`, `AnimalsScreenController.cs`, `AnimalViewerInput.cs` and `AnimalsScreenBuilder.cs` are gone. Decision D1 landed 2026-09-29 as the UI Toolkit [EspecieScreen](src/app/MergulhoVirtual/Assets/UI/Screens/EspecieScreen.cs) (`AppRoutes.Especie`, pushed from the Praia detalhe species cards), which renders the **same `AnimalViewerRig`** through `ISpeciesModelViewer`. The rig's construction was extracted into [AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs) so it stays reproducible. The `AnimalDef` assets are the app's **species catalog**, read by `UiServiceAdapters.SpeciesCatalogAdapter` for the Praia detalhe species cards, the Reportar species chips, the AR info card and the Espécie screen.

**3D viewer rig — a scene ROOT, NOT under the Canvas.** `AnimalViewerRig` lives at world position `(5000, 0, 0)` so it sits comfortably beyond the AR camera's far plane (typical 100 m) and can't be visible from the AR scene even if a stray cullingMask lets through. Contains `ViewerCamera` (FOV 35°, solid deep-navy clear color, target = [Assets/RenderTextures/AnimalViewer.renderTexture](src/app/MergulhoVirtual/Assets/RenderTextures/AnimalViewer.renderTexture)), a three-point directional light rig — `KeyLight` (warm, upper-front-right) + `FillLight` (subtle cool, upper-opposite, pitched *down* — never below) + `RimLight` (aquatic blue, behind-above, for silhouette separation against the navy clear color) — and `Turntable` (empty Transform; the adapter mounts models under it). Camera and all three lights have `cullingMask` restricted to the `AnimalViewer` layer (defined at index 3 in [TagManager.asset](src/app/MergulhoVirtual/ProjectSettings/TagManager.asset)) so they don't cross-contaminate the AR scene.

**Why a separate rig instead of an in-canvas world-space camera**: rendering 3D models inside the same camera as AR is messy (depth conflicts, lighting overlap, AR session overhead). RenderTexture isolates the viewer from AR completely — the AR session stays paused on every non-Mergulho route (`ScreenManager.useOptimizedPerformance`), and the viewer camera renders at the UI's frame rate without fighting the AR pipeline.

**Gestures live on `EspecieScreen`** (UI Toolkit pointer events on the viewport element), not on the rig: one pointer = drag-rotate around Y, two pointers = pinch-zoom, mouse wheel = zoom in editor. They call `ISpeciesModelViewer.Rotate`/`Zoom`, and the adapter applies them to the world-space `Turntable` (rotate) and `ViewerCamera` (zoom). **The zoom clamp is relative, not absolute** — the deliberate change from the deleted `AnimalViewerInput`, which clamped to 0.5–10 m and so put the first pinch-out almost on the stop for a 4 m animal auto-framed at ~7.3 m. It is now `0.35×–2.5×` the fit distance, the only formulation that works across a catalog whose members differ 2× in length.

**`AnimalDef`** is a `ScriptableObject` (Assets > Create > Mergulho Virtual > Animal): `displayName`, `binomial` (scientific name, e.g. `Sphyrna mokarran` — added for the V2 species cards, which print it under the common name; **leave it empty rather than guessing**, the screens render the common name alone when it is blank), `approximateSize` / `diet` / `behaviour` (the AR species card's three spec rows — free pt-BR text, **blank on all five assets** and subject to the same rule: the card drops a row it has no value for rather than inventing marine biology), `imageName` (string filename loaded via `Resources.Load<Sprite>("Animals/" + imageName)` from [Resources/Animals/](src/app/MergulhoVirtual/Assets/Resources/Animals/)), `description`, `prefab`, `viewerScale`, `viewerOffset`, `photoCredit`, `modelCredit`, and `videos` (a `VideoRef[]` rendered as inline tap-to-play cards — see **Inline video player** below). The string-based image lookup mirrors `places.json`'s `imageName` field on the Beaches side — Sprite assets and AnimalDef `.asset` files cohabit in the same `Resources/Animals/` folder (a flat layout; `LoadAll<AnimalDef>("Animals")` filters by type so the jpgs don't pollute the result). The adapter mounts `prefab` under `Turntable`, applies `viewerOffset` + `viewerScale` (rotation is **not** overridden — see "Camera framing" below), then re-layers the entire instance to `AnimalViewer` (so the dedicated camera/lights pick it up). Adding a new species = drop a new `.asset` under `Resources/Animals/` — no code changes; `SpeciesCatalogAdapter` does `Resources.LoadAll<AnimalDef>("Animals")` lazily on first use.

**`photoCredit` and `modelCredit` are one line each, on a fixed convention**: `Foto: <author> / <licence> (<source>)` and `Modelo: <author> / <licence> (<source>)` — e.g. `Modelo: Ra_in_coat / CC BY 4.0 (Sketchfab)`, with pt-BR wording throughout (`Domínio público`, not "Public domain"). This is a rule, not a preference: `modelCredit` is a free-text field that used to hold the model's raw **Sketchfab description**, and `hammerhead.asset`'s ran to ~180 words of English across 20 YAML lines (camera rigs, Blender, a PIT tag number, funders) which rendered as **the largest single element on the Espécie page**. Credits are a licence obligation and a caption; they are not copy. Never drop the author name or the licence identifier while shortening one.

⚠️ **Two licensing/content items still open on the catalog**:
- **`hammerhead` and `reef_shark`'s 3D models are CC BY-NC** (`Jer Bot` and `DigitalLife3D`, both Sketchfab). That is a problem the moment the app is distributed commercially, and it is independent of how the credit line is worded — it needs a licence decision or a model swap, not a re-edit.
- **`lemon_shark`'s two `videos` entries point at the same URL**, so the one species that has videos draws two identical cards. Pre-existing; also tracked in `DESIGN_IMPLEMENTATION.md` §8.8.

**The `.asset` file name is the species key** used by everything: `beaches_content.json`'s `species[].key`, `ReportSightingJob.SpeciesKey`, and `SpeciesCatalogAdapter.Find(key)`. Renaming `lemon_shark.asset` silently orphans every reference (the adapter logs nothing for a key it simply does not have — the species just stops appearing). Duplicate keys are warned about and the first wins.

**The viewer's 3D model comes from `AnimalDef.prefab` — a second, independent wiring of the same shark prefab.** Each species' prefab is referenced from two places: `BeachSharkSpawner`'s Inspector list (AR beach spawning) and the species' `AnimalDef.asset` under `Resources/Animals/` (the Espécie viewer). Fixing or re-wiring one does NOT fix the other. **Empty-viewer failure mode**: `SpeciesModelViewerAdapter.Show` returns `false` when `animal.prefab == null` (one `LogWarning`), and `EspecieScreen` then simply omits the "Modelo 3D" section — the page renders normally with no model and no error on screen. When a species shows no model, check the `prefab` slot on its `.asset` in `Resources/Animals/` first (Inspector shows **"Missing (Game Object)"** if the reference is broken, `None` if never set). The most common way it breaks: the species' FBX was replaced with a new export — see "Replacing an existing species' FBX" under **Adding a new shark species**.

**Camera framing — auto-center + auto-fit on each mount** (`SpeciesModelViewerAdapter.MountModel` / `CenterAndFit`, ported line-for-line from the deleted `AnimalsScreenController`). The shark prefabs are sized to real-world meters (3–4 m sharks) and have AR-scene-specific transforms baked in (`localPosition (-4, 0, 4)` so they sit broadside of the AR origin), but in the viewer they need to be centered on the turntable and framed against the camera regardless of how the FBX hierarchy places the visible mesh relative to the prefab's root pivot. The adapter does both, every time you open a species:
1. **Position**: instantiate under `turntable`, set `localPosition = animal.viewerOffset` (default `(0,0,0)`) — this throws away the AR-baked offset.
2. **Scale**: `localScale = animal.viewerScale` (default `(1,1,1)` — at real-world scale).
3. **Rotation**: deliberately **NOT** reset. The prefab's rotation (e.g. hammerhead's Y=180° to face camera) carries through to the viewer, so dialing in a rotation on the prefab once shows everywhere. Tiger and lemon have identity rotation, hammerhead has Y=180.
4. **Center**: union all `Renderer.bounds` in the mounted hierarchy and translate the root so `bounds.center` sits at `turntable.position`. This hides FBX-internal pivot offsets — it doesn't matter if the mesh is offset 1 m forward of the FBX root; the visible body lands centered on the turntable. The user's pinch-rotate also orbits around the visible body center, not the pivot.
5. **Fit camera — on whichever axis actually binds, NOT on the longest dimension.** `FitCamera` takes `max(verticalRadius / tan(fovV/2), horizontalRadius / tan(fovH/2)) * 1.15` (15 % breathing room), where `fovH` is derived from the *render target's* aspect and the horizontal radius is the circle the XZ footprint sweeps (`0.5·√(x²+z²)`), not `size.x` — the turntable rotates about Y and the user will spin it, so the fit has to hold in every orientation or the nose clips mid-drag. Then it moves the camera along its existing direction vector to that distance and `LookAt(turntable)`; the camera *direction* is preserved (pitch/roll stay whatever was authored), only distance changes.
   ⚠️ **The bug this replaces is worth knowing, because the wrong version looks plausible.** The port from the uGUI viewer fitted the animal's **longest** dimension against `Camera.fieldOfView` — which is the **vertical** field, the *short* axis of a 358×260 viewport. A 4 m shark lying horizontally therefore landed at the distance where its length filled the *height*, covering ~63 % of the width and ~22 % of the height: roughly a seventh of the box, with the rest empty, **invariant of viewport height** so no amount of resizing would have revealed it as a sizing problem. Fitting both axes frames it at ~84 % of the width; the margin left is a long thin animal in a 1.38:1 box, which is geometry, not a bug.

**The camera does not render into the authored RenderTexture at runtime — it renders into one sized to the viewport.** `EspecieScreen` pushes the resolved pixel size of its viewport element through `ISpeciesModelViewer.SetViewportSize`, and the adapter allocates a matching `RenderTexture`, swaps `camera.targetTexture` to it, destroys the previous one and raises `TextureChanged`. [AnimalViewer.renderTexture](src/app/MergulhoVirtual/Assets/RenderTextures/AnimalViewer.renderTexture) is the authored fallback the camera reverts to when the viewer is released; everything in the **Anti-aliasing** notes below still applies to it. `SetViewportSize` early-returns on an unchanged size, and **re-fits the camera when a model is already mounted**, because the framing is a function of the target's *aspect* and the first target arrives after the mount (the screen only has a resolved layout later). Early-returning is also what makes the re-fit safe: it cannot walk over a zoom the user is mid-gesture on.

⚠️ **The screen caches the pushed size, so it has to clear the cache whenever the adapter drops its target.** `EspecieScreen.UnmountModel` zeroes `viewportWidthPx`/`viewportHeightPx` next to the `modelViewer.Hide()` call. `Hide()` releases the runtime target, but the screen's cache does not know that — leaving it set made `PushViewportSize` early-return on the **next** visit (same dp, same scale), so no target was ever recreated and **the second open of any species showed the placeholder instead of the model**. The cache tracks the adapter's state; it has to be cleared with it.

**Bind-pose `bounds` caveat**: `SkinnedMeshRenderer.bounds` returns the bind-pose AABB transformed to world space (Unity computes it once at import time when `updateWhenOffscreen = false`, the default). For an animation with a wide tail sweep, the centroid can drift a few cm between frames — usually invisible. If it visibly jitters when opening a species, set `updateWhenOffscreen = true` on that species' SkinnedMeshRenderer (slight perf cost, exact bounds every frame) or precompute a tighter `localBounds` in the FBX importer.

**Tuning levers** when auto-fit isn't quite right: `viewerOffset` shifts the body within the frame *after* auto-centering (e.g. push eyes up to the framing center), and `viewerScale` rescales (rarely needed at real-world FBX scale). The 1.15 padding factor is `SpeciesModelViewerAdapter.FitPadding`; change it there if the default framing feels too tight or too loose across the catalog.

**Lighting isolation from the AR scene** — the rig's three directional lights restrict `cullingMask` to bit 3 (`AnimalViewer`), and the scene's main `Directional Light` is configured to exclude the same bit ([MainScene.unity](src/app/MergulhoVirtual/Assets/Scenes/MainScene.unity) `m_CullingMask.m_Bits = 1073741879`). This double-sided exclusion is what keeps the rig and the AR sun direction from fighting each other. Without the exclusion on the scene light, the spawned model picks up the AR-scene directional alongside the rig and looks washed out / wrongly directional (silhouette lit from two contradictory directions). If you ever add another directional light to `MainScene` and the viewer suddenly looks off, check that the new light also clears bit 3.

If shading still looks off even with isolation in place, dial the rig itself — the `KeyLight`/`FillLight`/`RimLight` colors and intensities are the three `MakeLight(...)` calls in [AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs). Edit the builder and re-run `Tools > Mergulho Virtual > Create Animal Viewer Rig` rather than tweaking the GameObjects in the Hierarchy directly, otherwise the next builder re-run wipes your edits.

**Anti-aliasing in the viewer — RT must be single-sample, MSAA goes on the URP asset, SMAA needs Post Processing**. URP renders the ViewerCamera into an internal multisampled buffer at `URPAsset.m_MSAA` samples, runs post-processing (including SMAA if enabled), then *resolves* the result into the target RenderTexture — so the RT only ever stores the final single-sample image. Three rules that need to hold or the viewer breaks (subtly on desktop, loudly on Android with `RenderPass: Attachment 0 was created with N samples but M samples were requested` every viewer frame):

- **`Mobile_RPAsset.m_MSAA`** is the only knob that produces real MSAA in the viewer (and is the only MSAA URP actually does — `Camera.allowMSAA` is a permission gate, not a sample count). **4 is the practical maximum on Android** — Adreno/Mali clamp 8x at the driver level, leaving URP's renderpass setup configured for 8 against a clamped 4-sample attachment. Desktop GPUs honor 8x natively, which is why simulator hides the bug. The mapping from Android to this asset goes through `ProjectSettings/QualitySettings.asset`: `m_PerPlatformDefaultQuality.Android: 0` → quality entry `Mobile` → its `customRenderPipeline` GUID → `Mobile_RPAsset.asset`.
- **[AnimalViewer.renderTexture](src/app/MergulhoVirtual/Assets/RenderTextures/AnimalViewer.renderTexture) `m_AntiAliasing` must stay at 1.** The Inspector's "Anti-aliasing: 2/4/8 samples" dropdown on a RenderTexture is **dead in URP** — URP doesn't read it for rendering, but Unity *does* allocate the GPU surface at that sample count and bind it as MSAA. Setting it to anything but 1 (a) re-triggers the renderpass mismatch the moment URP's MSAA disagrees, (b) makes the RT un-sample-able by `RawImage` on most mobile GPUs, and (c) shows the misleading Inspector warning *"Camera target texture requires Nx MSAA. Universal pipeline has MSAA disabled"* — which reads like "increase URP MSAA to N" but actually means "this field does nothing useful here, set it to 1." Don't follow the warning's literal advice.
- **SMAA / FXAA / TAA require `renderPostProcessing = true` on the camera.** All three are implemented as post-processing passes; setting `m_Antialiasing: 2` (SMAA) without `m_RenderPostProcessing: 1` silently no-ops AND fires an Inspector warning (paraphrased as "Post Processing not enabled"). Same for the other two modes. The combination on the ViewerCamera is `m_RenderPostProcessing: 1` + `m_Antialiasing: 2` (SMAA, High quality) layered on top of the pipeline's 4x MSAA.

[AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs) pins all three (RT to 1, `renderPostProcessing = true`, SMAA High); manual Inspector edits to RT MSAA or the camera's PP toggle get overwritten the next time the builder runs, so fix the builder rather than the asset if a tweak should be permanent. **Editor save vs. external file edit**: when an asset is selected in the Inspector and you Save the scene, Unity rewrites the asset file from the Inspector's cached state — so a `.renderTexture` edit made via Edit/file write may be silently reverted on next save. To make an asset edit stick, either close the Inspector view of that asset before saving, or make the change through the Inspector / a builder script.

**Building / regenerating — Editor menu**: `Tools > Mergulho Virtual > Create Animal Viewer Rig` ([AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs)) rebuilds the whole `AnimalViewerRig` root — turntable, camera (FOV/clear color/culling mask/SMAA), the three lights, and the single-sample assertion on the RenderTexture. It is the only place those values live, so fix the builder rather than the Hierarchy. **Follow it with `make ui-setup`**: the rig is a fresh GameObject, so `AppUiHost.animalViewerRig` has to be re-pointed at it or the Espécie screen loses its 3D section. It has no headless make target of its own; run `-executeMethod AnimalViewerRigBuilder.BuildHeadless` if you need it with the editor closed. Same iteration rule as every builder: iterate entirely in code OR entirely in the Editor, never alternately.

**Idempotency footgun — `GameObject.Find` skips inactive objects**: the rig is INACTIVE whenever no species is open, which is most of the time. So a naive `GameObject.Find("AnimalViewerRig")` returns null even though the rig exists — a builder would think there is nothing to delete and create a *second* rig alongside the inactive one. Both `AnimalViewerRigBuilder` and `AppUiBuilder` iterate `SceneManager.GetActiveScene().GetRootGameObjects()` filtered by name instead (that sees inactive too); generalize this to any builder that touches a scene root whose visibility something else controls. If you ever inherit a scene with duplicates from this footgun: Hierarchy → both rigs share the name; the inactive one has the greyed-out toggle in the Inspector — delete that one.

### Tap-to-interact — [ObjectInteraction.cs](src/app/MergulhoVirtual/Assets/Scripts/ObjectInteraction.cs) + [ArSpeciesTarget.cs](src/app/MergulhoVirtual/Assets/Scripts/ArSpeciesTarget.cs)

The AR scene's **hit source**, and nothing else: it reads `Pointer.current` (new Input System — not legacy `Input.GetMouseButton`), casts a `Physics.SphereCast` with a **0.2 m radius** so a distant animal is still an easy target, and raises `SpeciesSelected(speciesKey)`. Presentation lives in the UI Toolkit [MergulhoScreen](src/app/MergulhoVirtual/Assets/UI/Screens/MergulhoScreen.cs), which reaches it through `IArSelection` / `UiServiceAdapters.ArSelectionAdapter`.

**It had never worked before Slice 4, in three independent ways** — worth knowing, because each is a live constraint now:
- The component was **not in `MainScene` at all**. `AppUiBuilder` now adds it to the `Beach Shark Spawner` GameObject (the thing that owns the animals it casts against).
- It compared `hit.collider.gameObject.name` to a hardcoded `targetName = "Tubarão Martelo"`, which matches nothing — `BeachSharkSpawner` names its instances after the prefab (`hammerhead`). The comparison is now a `GetComponentInParent<ArSpeciesTarget>()` lookup, so **adding a species needs no change here**.
- **The shark prefabs carry no colliders**: they are Prefab Variants of Sketchfab FBXs, which import a SkinnedMeshRenderer and nothing else, so a raycast could never hit them. `ArSpeciesTarget.Attach` fits a `BoxCollider` to the union of the renderer bounds at spawn time (a MeshCollider off a skinned mesh would be expensive and stuck in the bind pose, and the tap only has to mean "that animal").

`BeachSharkSpawner` calls `ArSpeciesTarget.Attach(instance, prefab.name)` on everything it spawns. **`prefab.name` is the species key** — the five shark prefabs and the five `AnimalDef` assets under `Resources/Animals/` share file names, which is the same key `beaches_content.json` and `ISpeciesCatalog.Find` use. A prefab that authors its own `ArSpeciesTarget` wins over that convention, which is the escape hatch if the two names ever diverge.

Two deliberate behaviours: a **miss raises nothing** (the card is dismissed by its ⨯, not by tapping elsewhere — otherwise half the screen would be a dismiss target), and the component idles until `Listening` is set, which `MergulhoScreen.OnEnter`/`OnExit` does, so it does not raycast from the other three tabs.

⚠️ **It must panel-pick before it raycasts, or every AR tap fires twice.** Reading `Pointer.current` raw means the component sees taps the UI has already consumed — there is no `EventSystem` in the path for a UI Toolkit panel, and the uGUI `EventSystem` would not know about one anyway. Without the guard, a tap on the species card, on its ⨯, or on any row of the open beach menu **also fired the 0.2 m SphereCast behind it**, so the ⨯ could close the card and immediately re-open it. `ObjectInteraction` now converts the screen position with `RuntimePanelUtils.ScreenToPanel` (panel coordinates are **y-down** where screen coordinates are y-up, so the flip is not optional) and bails if `panel.Pick(...)` returns anything. The panel comes from an optional `[SerializeField] UIDocument uiPanelSource` that `AppUiBuilder` wires, falling back to a cached `FindAnyObjectByType`. **Open-water taps still get through**, because the HUD root, the hero strip and the dock are all `PickingMode.Ignore` by design — that is the property the guard leans on, so if a future HUD element becomes pickable across the whole screen it will silently kill AR tapping.

### Sighting reports — [ReportScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ReportScreen.cs) + [ReportViewModel.cs](src/app/MergulhoVirtual/Assets/UI/ViewModels/ReportViewModel.cs) + [UiServiceAdapters.SightingReportsAdapter](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/UiServiceAdapters.cs#L438) + [ReportSightingJob.cs](src/app/MergulhoVirtual/Assets/Scripts/Jobs/ReportSightingJob.cs) + [GalleryPicker.cs](src/app/MergulhoVirtual/Assets/Scripts/Photo/GalleryPicker.cs)

The **Avistamentos** tab lets a user pick a photo from their phone gallery, tag it (species / size / behaviours / identity / profile — all optional; only the photo is required), and submit it for upload. The submit path is fire-and-forget from the user's perspective — they bounce to Início after ~1.2 s, and the **Background job system** below handles upload, retry, and offline persistence. The same screen shows **"Seus avistamentos pendentes"**, a live feed of what is still queued or has permanently failed, read back out of the queue via `JobQueue.ListPending`/`ListFailed`.

> **Slice 3 replaced the uGUI screen and Slice 6 deleted it.** `RegisterScreenController.cs`, `ScreenUI/RegisterScreen` and `RegisterScreenBuilder.cs` are gone from the repo and the scene. `ReportScreen` is the only sighting form.

There is no date field in V2, so `WhenUtc` is the submit time, and the beach comes from `IActiveBeach` (GPS or the manual override) rather than a dropdown — a null beach is a supported, common value.

**Photo source — [GalleryPicker.cs](src/app/MergulhoVirtual/Assets/Scripts/Photo/GalleryPicker.cs)**: thin cross-platform wrapper over [yasirkula/UnityNativeGallery](https://github.com/yasirkula/UnityNativeGallery) (added to [Packages/manifest.json](src/app/MergulhoVirtual/Packages/manifest.json) as `com.yasirkula.nativegallery` from a git URL — needs internet on first import, then resolves from the package cache). Single API: `GalleryPicker.PickImage((path, error) => …)`. In Editor falls through to `EditorUtility.OpenFilePanel` so you can iterate without building. **Do not call `NativeGallery.RequestPermission` separately** — `GetImageFromGallery` requests permission internally; in the current package version (`be4007e35700`) it **returns `void`**, and a permission denial surfaces as a `null` path in the callback, indistinguishable from an ordinary cancel. Older docs and earlier versions had it returning `NativeGallery.Permission`; if you assign that return value the Android build fails with `CS0029: Cannot implicitly convert type 'void' to 'NativeGallery.Permission'` while the editor build still compiles, because the device branch is gated by `#if (UNITY_ANDROID || UNITY_IOS) && !UNITY_EDITOR` and the editor never sees it. If you need to distinguish denial from cancel, call `NativeGallery.RequestPermissionAsync(PermissionType.Read, MediaType.Image)` first and only call `GetImageFromGallery` on `Permission.Granted`. iOS requires `NSPhotoLibraryUsageDescription` in Project Settings → Player → iOS → Other Settings (NativeGallery's documentation will nag if it's missing).

**EXIF preservation is the whole point** of the photo path — backend can extract GPS, original timestamp, camera model from the EXIF block. Two places preserve it:
- NativeGallery (Android: `ContentResolver.openInputStream` → `FileOutputStream` raw byte copy; iOS: `PHAsset` request with `version = .original`).
- `ReportSightingJob.Execute` reads the on-disk file with `File.ReadAllBytes` and uploads it as a `MultipartFormFileSection`. **Never** decode → re-encode the image anywhere in this path; `Texture2D.LoadImage` for the in-screen preview is a separate in-memory copy that does not replace the upload bytes.

**`ReportSightingJob` ownership of the image file**: at enqueue time, [SightingReportsAdapter.Submit](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/UiServiceAdapters.cs#L438) copies the picked file to `Application.persistentDataPath/sightings/<guid>.<ext>` and stores that path in the job. This is critical — NativeGallery returns a path inside the app's *cache* directory (Android may evict; iOS exports a temporary), and the user can also delete the original from their gallery between enqueue and execute. Owning a copy under `persistentDataPath/sightings/` makes the upload immune to both. The job deletes the file on `Success`. On `PermanentFailure` the file currently stays put (the queue moves the `.json` envelope to `jobs/failed/` but the sidecar isn't moved with it) — acceptable now since failures are rare and bounded by user actions; revisit if you change failure semantics.

**Submit UX — fire-and-forget, three outcomes**: the screen intentionally does *not* gate the user on backend availability. `ReportViewModel.Submit` raises `Submitted` **even when the report could not be taken at all**, and `LastSubmitAccepted` tells the screen which of three endings to play ([ReportScreen.OnSubmit](src/app/MergulhoVirtual/Assets/UI/Screens/ReportScreen.cs)):
- **accepted** → `"Enviando avistamento…"`, form resets, and after `SubmitExitDelayMs` (1200 ms) the screen navigates to `AppRoutes.Home`. Only this outcome navigates, because only this one left something durable behind.
- **no photo** → stays on the screen with `"Adicione uma foto do avistamento."` The photo is the one required field.
- **queue refused it** (full, or the file copy failed) → stays, error tone, form untouched so nothing typed is lost.

A permanent upload failure surfaces later in the pending feed as a `"Falhou"` row (the adapter subscribes to `JobQueue.JobCompleted` and re-emits `ISightingReports.Changed`), not as a dialog.

**Backend contract** — implemented at [POST /api/v1/avistamentos](src/backend/api/endpoints/avistamentos_api.py) in the FastAPI service: `multipart/form-data` with one file part `photo` and form fields `beach`, `timestamp` (RFC3339 UTC), `species_guess`, `notes`. Empty values are skipped, so a part the user left blank is simply absent. Two headers:
- **`Idempotency-Key`** (required) — the server uses it as the Firestore document id AND as the `<registro>` in the bucket key, so a retry with the same key is first-write-wins (`doc.exists` short-circuits to `200 + existing avistamento`, no second blob write). The app sends the same `Guid.NewGuid().ToString("N")` it baked into the local sighting filename — generated once per submit in `SightingReportsAdapter.Submit` and persisted into the queued `ReportSightingJob`, so JobQueue retries (TCP timeout after the server already wrote, app kill mid-upload, etc.) collapse server-side instead of duplicating documents. Without this header the server returns 400.
- **`X-Firebase-AppCheck`** (required in prod) — fetched by [AppCheckTokenProvider.cs](src/app/MergulhoVirtual/Assets/Scripts/AppCheckTokenProvider.cs); see **Production deploy — GCE free-tier VM + Cloudflare** above for the full setup. In `BACKEND_DEBUG=1` mode the backend ignores the header, so the LAN dev workflow keeps working before Firebase is installed.

**401-on-retry semantics**: [ReportSightingJob.Execute](src/app/MergulhoVirtual/Assets/Scripts/Jobs/ReportSightingJob.cs) classifies the *first* 401 as `TransientFailure`, sets its own persisted `TokenRefreshAttempted` flag, and passes `forceRefresh: true` to AppCheck on the next attempt to bypass the SDK token cache — the cached token is what the server just rejected. A 401 **after** that flag is set → `PermanentFailure`, on the assumption that a freshly-refreshed token also getting rejected means the app is genuinely deregistered. This lets a long-queued job (token aged past 1h while offline) retry cleanly with a refreshed token instead of moving straight to `jobs/failed/`.

**The rule is keyed on that flag and NOT on `AttemptCount` — this was a real bug, fixed 2026-09-29.** It used to read `AttemptCount == 1`, but `AttemptCount` counts *every* attempt including connection errors, so after a few attempts on a bad network the first **genuine** 401 — exactly the aged-token case the retry exists for — was classified permanent and the sighting was moved to `jobs/failed/`. Anything that decides "have we tried the fix for this yet?" needs its own flag; the attempt counter answers a different question. The decision itself is extracted as `internal JobResult ClassifyHttpFailure(long)` so it can be unit-tested without real HTTP.

**Six fields the app sends and the backend does not read yet.** Slice 3 added `species_key`, `size_bucket`, `behaviours` (**repeated — one part per selected behaviour**), `reporter_name`, `reporter_email` and `reporter_profile` to `ReportSightingJob` and to the multipart body ([ReportSightingJob.cs:116](src/app/MergulhoVirtual/Assets/Scripts/Jobs/ReportSightingJob.cs#L156)). **The deployed endpoint declares none of them.** That is safe and deliberate, not an oversight: it was verified empirically against the exact signature of `create_avistamento` that FastAPI **ignores undeclared multipart parts** (extra parts, and repeated parts for a name it does not declare, still return `201`). So today's wire contract and today's Firestore documents are unchanged, and the moment the backend grows the matching `Form()` parameters the data starts landing with no app release. Key values are documented on `ReportViewModel` (`lt_1m`/`1_2m`/`gt_3m`; `calmo`/`perto_da_praia`/`alimentacao`/`arredio`; `turista`/`condutor`); `species_key` is the `AnimalDef` asset name and `species_guess` keeps carrying the pt-BR label the backend already stores as `nome_popular`.

**Backend catch-up, when someone does it** (three steps, in this order): add the `Form()` params to [avistamentos_api.create_avistamento](src/backend/api/endpoints/avistamentos_api.py) (`behaviours: list[str] = Form([])` for the repeated part); decide the Firestore field names and write them next to `nome_popular`/`observacao`; and if any of them becomes a list filter in the operator UI, **regenerate the composite indexes first** (`tools/generate_firestore_indexes.py` → `firebase deploy --only firestore:indexes`, 5–15 min backfill, and mind the 2^N budget in **Scaling headroom** above). ⚠️ `reporter_email` is **personal data** the moment Firestore stores it — the app carries it in the job envelope and never persists it anywhere else (no PlayerPrefs, no prefill); a retention / privacy-notice decision is owed *before* the backend writes it.

**`uploadUrl` = `https://mergulhovirtual.dev/api/v1/avistamentos`** — now a **code constant**, `SightingReportsAdapter.DefaultUploadUrl`, not an Inspector field (the old `RegisterScreenController.uploadUrl` serialized value is dead along with the screen). To test against a LAN `BACKEND_DEBUG=1` backend, pass the URL to the `SightingReportsAdapter` constructor in [AppUiHost.Awake](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/AppUiHost.cs); that mode ignores the missing App Check header. On HTTPS via Cloudflare, the [AndroidManifest.xml](src/app/MergulhoVirtual/Assets/Plugins/Android/AndroidManifest.xml) cleartext whitelist is no longer exercised; it's only needed for a plain-HTTP LAN backend.

**GCP bucket layout** (bucket = `avistamentos` per [config.py](src/backend/config.py)): two blobs per app-submitted sighting, written atomically by the endpoint:
- `originals/<registro>.<ext>` — raw bytes from the device, EXIF intact, kept as canonical source-of-truth.
- `imagens/<registro>.jpg` — Pillow-resized display variant (max 1600 px longest side, JPEG q85, EXIF + ICC profile preserved). The `imagens/` path is **load-bearing** — [read_avistamento](src/backend/api/endpoints/avistamentos_admin.py#L126) generates its signed URL from `imagens/{registro}.jpg`, so renaming the prefix breaks every existing list/view page (including the CSV-imported pre-app sightings, which use the same convention).

**Server-side resize, not client-side**, lives in [services/image_processing.py](src/backend/services/image_processing.py). EXIF is preserved by passing `image.info["exif"]` (raw bytes) back to `image.save(..., exif=...)` — Pillow doesn't re-interpret the block, so GPS, DateTimeOriginal, camera model, and orientation tag carry through unchanged. The orientation tag's `PixelXDimension`/`YDimension` and the embedded thumbnail go stale after resize but no viewer reads those — they read the actual JPEG SOF marker. **Why server-side**: Unity's `Texture2D.EncodeToJPG` strips all EXIF, and re-splicing the APP1 segment cross-platform (Android/iOS HEIC → JPEG paths) is painful — Pillow does the right thing in one `image.save` call. Trade-off: full-size originals get uploaded; long-tail download bandwidth (every list/view page hit) and storage cost win. **HEIC**: optional `pillow-heif` import in `image_processing.py` registers the HEIF opener; without the wheel installed, HEIC uploads return 415 `unsupported image format`. Both packages are pinned in [requirements.txt](src/backend/requirements.txt) — `pip install -r requirements.txt` after pulling.

**Firestore document shape** (app-submitted): `registro` = the Idempotency-Key GUID (32 hex chars, distinguishable from CSV-imported `registro`s which are sequential numbers/dates), `local` = beach name, `data_hora_iso` = the raw RFC3339 timestamp, `dia_registro`/`mes_registro`/`ano_registro` = string ints parsed from that timestamp (matches the existing query filters in [services/avistamentos.py](src/backend/services/avistamentos.py) so list filters work uniformly across both sources), `nome_popular` = species_guess, `observacao` = notes, `modo_registro` = `"app"` (sentinel that lets you separate app submissions from imported CSV rows in queries).

**Adding fields to the form**: five places, all of them. `ReportViewModel` (state + copy + a `ReportOption` list if it is a choice) → `SightingDraft` ([ISightingReports.cs](src/app/MergulhoVirtual/Assets/UI/Interfaces/ISightingReports.cs)) → `SightingReportsAdapter.Submit` → `ReportSightingJob` (public field + the `Data` struct + `SerializeData`/`DeserializeData` + an `AddIfPresent` in `Execute`) → `ReportScreen` to draw it. **Add, never rename.** The job's persisted JSON envelope auto-handles versioning *only* in the JsonUtility "missing field stays default" sense, so a job queued by an older build still reloads intact — but rename or delete a field and every in-flight queued job silently loses that data on reload. Keeping every new part `AddIfPresent`-gated is also what makes an old queued job produce a body byte-identical to what the shipped build sends.

**Seeing it without a device**: `make ds-shots SHOT=report` renders the empty form (Tela 11) and a driven, filled one (Tela 12, species + size + three behaviours + a real picked photo + profile) to `.shots/` — see **Headless workflow** under **Design system**.

### Background job system — [Assets/Scripts/Jobs/](src/app/MergulhoVirtual/Assets/Scripts/Jobs/)

`JobQueue` is a singleton MonoBehaviour ([JobQueue.cs](src/app/MergulhoVirtual/Assets/Scripts/Jobs/JobQueue.cs)) that owns a persistent FIFO of `Job` objects, retrying each one with exponential backoff while the app is alive and resuming from disk on next launch. Use it for any network operation where "user might not have signal right now" or "user might close the app before this finishes" is a real scenario. **Scope**: jobs survive *app kill* (file-on-disk reloads on next launch), but they do **not** run while the app is fully killed/swiped away — that would require Android `WorkManager` via a native plugin and is intentionally out of scope (see `WorkManager`/foreground-service note in design history if you ever need it).

**Calling it**:
```csharp
JobQueue.GetOrCreate().Enqueue(new HttpPostJob {
    Url = "https://example.com/register",
    JsonBody = "{\"name\":\"...\"}",
    IdempotencyKeyHeader = "user-42-register-v1",  // optional, server-side dedupe
});
```
Three job types ship: [HttpPostJob.cs](src/app/MergulhoVirtual/Assets/Scripts/Jobs/HttpPostJob.cs) for JSON POSTs, [FileDownloadJob.cs](src/app/MergulhoVirtual/Assets/Scripts/Jobs/FileDownloadJob.cs) for HTTP→file with optional SHA-256 verify, and [ReportSightingJob.cs](src/app/MergulhoVirtual/Assets/Scripts/Jobs/ReportSightingJob.cs) for multipart photo uploads (see "Sighting reports" above). Subscribe to `JobQueue.Instance.JobCompleted` for in-session completion (best-effort — does not survive restart), or query `GetStatus(jobId)` on boot to check whether a previously-enqueued job is `Pending`, has `Failed`, or is `NotFound`. **`NotFound` is ambiguous** — it means *either* the job already succeeded (success records aren't kept), *or* it was never enqueued. Callers that need to distinguish these should write a sentinel to PlayerPrefs at enqueue time and clear it from `JobCompleted`.

**Enumerating the queue — [`ListPending(type)`](src/app/MergulhoVirtual/Assets/Scripts/Jobs/JobQueue.cs#L326) / [`ListFailed(type)`](src/app/MergulhoVirtual/Assets/Scripts/Jobs/JobQueue.cs#L350)** (added for the Avistamentos pending feed). Both return [`JobRecord`](src/app/MergulhoVirtual/Assets/Scripts/Jobs/JobRecord.cs) rows — envelope fields (`Id`, `Type`, `AttemptCount`, `CreatedAtUtc`, `NextAttemptAtUtc`, `LastError`) plus a `State` of `Queued` / `Retrying` / `WaitingForNetwork` / `Failed`, with **offline winning over backoff** because that is the actionable thing to tell a user. `record.Snapshot<ReportSightingJob>()` hands back a **detached** copy deserialized from the payload (null if the type doesn't match), so a feed can read a job's own fields without being able to mutate the instance the run loop is about to execute. `ListPending` reads memory in FIFO order; `ListFailed` re-reads `jobs/failed/` on every call. **This is the unambiguous half of the status API** — unlike `GetStatus`, a record only ever exists for a job genuinely in that state; a job in neither list is simply no longer in storage, and "did this ever succeed?" still needs your own durable flag.

⚠️ **There is no event for "a job is retrying".** `JobCompleted` — and therefore `ISightingReports.Changed` above it — fires only on `Success` and `PermanentFailure`, so a UI that renders `ListPending` on entry and then waits for an event shows a frozen attempt count and a stale `State` for the entire backoff ladder (up to an hour), which reads to the user as a stuck queue rather than a working one. **Any live view of the queue has to poll.** `AppUiHost` does it for the Avistamentos feed off the existing ~60 s freshness tick rather than adding a timer — see **Phase 3 — UI layer**.

**Use `JobQueue.GetOrCreate()` over `JobQueue.Instance`** for any caller that initiates jobs. `Instance` returns null if no `JobServices` GameObject is in the scene (and the documented scene layout below is aspirational — the queue is normally auto-spawned, not pre-wired). `GetOrCreate()` lazily creates one with `DontDestroyOnLoad`, so the user is never blocked by a missing scene component. Read-only callers (status queries, event subscriptions) can use `Instance` directly since they have nothing useful to do without an existing queue.

**Who starts the queue, and the bug that came from nobody doing it.** Nothing in `MainScene` instantiates `JobQueue` — before Slice 3 the only `GetOrCreate()` call was inside the uGUI Register screen's submit handler, so **a sighting queued and then interrupted by an app kill never resumed** unless the user happened to reopen that screen. Since Slice 3 the `SightingReportsAdapter` constructor calls `JobQueue.GetOrCreate()` **and** `LoadPendingFromDisk()`, and it is constructed in [AppUiHost.Awake](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/AppUiHost.cs) — i.e. at app start, not on first visit to the tab. (The explicit `LoadPendingFromDisk()` is because `GetOrCreate`'s own `Start()` loads a frame later, which would leave the feed's first render empty.) **Any future job type needs an equivalent app-start owner** — a queue nobody constructs is a queue that never retries.

**Persistence shape**: one file per job at `Application.persistentDataPath/jobs/<jobid>.json`; permanent failures move to `jobs/failed/<jobid>.json` for debugging instead of being deleted. One-file-per-job (vs. one big queue file) gives atomic per-job lifecycle and avoids rewrite-everything contention. Writes go through `<file>.tmp` + `File.Replace`/`File.Move` so a crash mid-write leaves either the old file or the new file, never a half-written one. **`File.Move(src, dst, overwrite)` does not exist in Unity 6000.3.14f1** (neither the netstandard 2.1 reference assembly nor the AOT mscorlib has the 3-arg overload — it is a `CS1501`), so the write is `File.Exists(path) ? File.Replace(tmp, path, null) : File.Move(tmp, path)`; with a null backup name `File.Replace` reduces to a single `rename(2)`, and a `Move` onto a free name is already atomic. Do not "simplify" this to the 3-arg `Move`. Until 2026-09-29 it was `File.Delete` then `File.Move`, which has a window where neither file exists — the comment and the test name both claimed atomicity the code did not have. `FileDownloadJob`'s destination finalize uses the identical pair, deliberately, so there is only one answer to "overwrite a file atomically" in this folder. **`JsonUtility` can't deserialize polymorphically**, so each job is wrapped in a `JobEnvelope` with a `type` discriminator and a `data` field containing the type-specific JSON as a nested string — that's why every concrete job overrides `SerializeData`/`DeserializeData` for its own fields. No Newtonsoft dependency.

**Backoff — TWO schedules, chosen by whose fault the failure was.** A transient failure sets `Job.LastFailureWasNetwork`, and `HandleResult` picks accordingly:
- **Server-side transient** (5xx, 408, 429, or an exception thrown by our own code): the original `BackoffSchedule` 5s → 30s → 2min → 10min → 1h, capped at 1h, indexed by `BackoffStep`.
- **Connectivity transient** (`ConnectionError`, a stall-watchdog abort, or the App Check token wait timing out): the gentler `NetworkBackoffSchedule` 15s → 30s → 60s → 120s, capped at 2min, indexed by the separate `NetworkFailureStep`. A dead uplink is not the server's fault and must not cost an hour; 2-minute polling on a broken network is the accepted battery floor.

`PermanentFailure` (other 4xx) moves to `failed/`. Network-required jobs (`Job.RequiresNetwork == true`, the default) are additionally gated on `Application.internetReachability` — if offline they're skipped each tick until reachability returns, and **no attempt is burned**, which is the one part that was always right.

**Two pull-forward paths, because an absolute `NextAttemptAtUtc` ignores the user.** `NextAttemptAtUtc` is persisted as wall-clock, so a job on the 1h rung does become due again on a later launch — but nothing used to *shorten* it, so reconnecting to a good network and reopening the app (the clearest possible "send it now" signals) both did nothing for up to an hour. Now:
- `OnConnectivityRegained()` fires on the offline→online edge (`wasOnline` is a `bool?` so launching online is not mistaken for a transition) and, for every pending job whose delay was network-caused, sets `NextAttemptAtUtc = now`, resets `NetworkFailureStep` and persists.
- `LoadPending()` applies the same clamp at launch: a network-caused delay more than 30s out becomes `now + 5s` (not 0 — keeps the first attempt off the very first frame while the app is still starting). **Server-caused delays are deliberately never clamped** by either path: a backend that is 500ing should keep its full backoff.

**Both `Application.internetReachability` gates are interface checks, not reachability checks** — they are true for any associated Wi-Fi/cell interface with a dead uplink (captive portal, no DNS, backend unreachable). That is why the connectivity schedule and the stall watchdog exist: the honest-offline path is cheap and correct, and the near-offline path is the one that actually costs you.

**Lifecycle gotchas worth knowing before extending**:

- **Every request goes through `Job.Send(req, outcome, stallSeconds, hardCapSeconds)` — never `req.SendWebRequest()` bare.** Concurrency is 1, so one half-open TCP socket (routine on mobile data) used to leave `running = true` forever and silently stop *every* queued job with nothing in the log. The helper sets `req.timeout` as a backstop, then aborts the request if `req.uploadedBytes + req.downloadedBytes` has not moved for `stallSeconds` (45 default, 600s hard cap for the photo upload). It is a **stall** watchdog, not a deadline, on purpose: a multi-MB original on a slow link legitimately takes minutes and must not be killed while it is still making progress. Use the byte counters, not the coarse float `uploadProgress`, and `Time.realtimeSinceStartup`, not `Time.time`. An abort is reported as a *connectivity* transient failure.
- **`ReportSightingJob`'s App Check token wait is bounded too** (`TokenWaitTimeoutSeconds`, 30s, an `internal static` test seam). It was an unbounded `while (!tokenTask.IsCompleted) yield return null;` — the same wedge as above, and the one the `Update()` watchdog deliberately cannot see. Filed as a connectivity failure so it takes the gentle schedule and gets pulled forward on relaunch. `AppCheckTokenProvider` caches its init task forever *including when it faults*, so a token that fails to arrive once never arrives again in this process — the retry that matters is the next launch, which is precisely what this queue is for.
- **`RunJob` must stay incapable of throwing, and `RunLoop` is started exactly once.** Unity terminates a coroutine on an unhandled exception, so before 2026-09-29 a single throw stopped all retries for the rest of the process with `running` stuck true. `HandleResult` used to be called bare from the iterator body; it does file IO and synchronously invokes `JobCompleted`, whose subscriber chain runs a **full UI Toolkit tree rebuild** in the app layer. C# forbids `yield return` inside a try-with-catch, which is the only reason the tail lives in a separate non-yielding `FinishJob` with `running = false` in a `finally` — do not inline it back. `JobCompleted` is raised by walking `GetInvocationList()` with a try/catch per subscriber, so one broken listener cannot deny the others or the queue. `Update()` additionally watchdogs the loop (restart if no tick for `tickIntervalSeconds * 5`, gated on `!running` so a long upload never trips it), and `OnApplicationPause`/`OnApplicationFocus` re-stamp the liveness clock — without them every return from background false-fires, because `Time.realtimeSinceStartup` advances while the player is paused and `Update` runs before suspended coroutines resume.
- **The tick uses a fresh `WaitForSecondsRealtime` each iteration.** `WaitForSeconds` is scaled by `Time.timeScale` (a paused app would stop retrying), and the instruction latches its deadline in its constructor — reusing one instance returns immediately once elapsed and spins the loop every frame.
- **`ListPending` promises FIFO, so `LoadPending` sorts by `CreatedAtUtc` then `Id`.** `Directory.GetFiles` order is filesystem-dependent; the doc-comment's FIFO claim was false across a restart. `LoadPendingFromDisk` also refuses to reload while `running`, so a reload can never orphan the job currently executing.
- **Envelope fields are ADD-only.** `lastFailureWasNetwork`, `backoffStep` and `networkFailureStep` were added 2026-09-29 and default to false/0, so a job file written by an older build still loads. Renaming or removing one silently drops that data from every job already queued on a device.
- **The existing test suite could not have caught any of the above.** Every test drives the queue through `RunOnceForTests()`, which calls `NextDueJob` + `RunJob` directly and **never enters `RunLoop`** — so the loop's lifetime, its exception behaviour, the stuck `running` flag, the connectivity edge and the realtime wait are all outside every seam the suite has. Where a fix lives in the loop, the decision is extracted to an internal method and tested there (`OnConnectivityRegained`, `ClassifyHttpFailure`, the launch clamp via `LoadPendingFromDisk`); the loop plumbing itself needs PlayMode or a device.

- **Custom job types must be registered before disk-load**. Production calls `EnsureInitialized()` then `LoadPendingFromDisk()` from `Start`, so `JobQueue.Instance.RegisterType<MyJob>()` should run earlier — from another component's `Awake`, or via a manual `LoadPendingFromDisk()` re-call after late registration. Otherwise old `MyJob`-typed files on disk get skipped with a `LogError` ("unknown job type"). The simplest registration site is right inside `JobQueue.EnsureInitialized()` next to `HttpPostJob`/`FileDownloadJob`/`ReportSightingJob` — that runs before disk-load no matter who triggers it.
- **Lazy initialization is intentional**. `EnsureInitialized()` runs from `Awake` *and* from any public entry (`Enqueue`, `GetStatus`, `RunOnceForTests`), guarded by an `initialized` flag. The lazy path exists because Unity EditMode tests don't reliably fire `Awake` on `AddComponent` — production never relies on it, but it makes the queue robust to that.
- **`FileDownloadJob` does NOT HTTP-resume on retry** — each retry restarts from byte 0 and overwrites the `.partial` file. Fine for small images; if you start downloading large videos, add a `Range: bytes=N-` header + `DownloadHandlerFile(append: true)` and verify the CDN returns `206 Partial Content` (servers that return `200` instead would silently corrupt the file).
- **No success records**. The queue deletes the job file on success and emits `JobCompleted`. Once `JobCompleted` fires, the only place that knew about the job is gone. If you need durable "did this ever succeed?" semantics, persist a flag yourself.
- **Concurrency = 1**. The loop runs one job at a time. If you add a slow `FileDownloadJob`, it blocks subsequent `HttpPostJob`s behind it. Adding per-type concurrency is a future change, not a current footgun — just be aware.

**Adding a new job type** — minimal skeleton:
```csharp
public class MyJob : Job
{
    public string SomeField;
    public override string Type => "MyJob";

    [Serializable] private struct Data { public string someField; }
    protected internal override string SerializeData() =>
        JsonUtility.ToJson(new Data { someField = SomeField });
    protected internal override void DeserializeData(string data) =>
        SomeField = JsonUtility.FromJson<Data>(data).someField;

    public override IEnumerator Execute(Action<JobResult> setResult)
    {
        // do work; setResult(Success | TransientFailure | PermanentFailure)
        yield break;
    }
}

// Wire up once at startup, before LoadPendingFromDisk runs.
// Easiest: add it right inside JobQueue.EnsureInitialized().
JobQueue.GetOrCreate().RegisterType<MyJob>();
```

**Tests** ([JobQueueTests.cs](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/JobQueueTests.cs), [JobSerializationTests.cs](src/app/MergulhoVirtual/Assets/Scripts/Tests/Editor/JobSerializationTests.cs)) use three internal seams exposed via [Assets/Scripts/AssemblyInfo.cs](src/app/MergulhoVirtual/Assets/Scripts/AssemblyInfo.cs) (`InternalsVisibleTo("Assembly-CSharp-Editor")`): `JobQueue.TestRootOverride` redirects storage to a temp dir per test, `IsOnlineOverride` swaps the connectivity check, and `RunOnceForTests()` runs one due job synchronously (the production `RunLoop` uses `WaitForSeconds`, which doesn't tick reliably in EditMode). When adding tests for a new job type, follow the `TestJob` pattern at the bottom of `JobQueueTests.cs` — it bypasses real HTTP and lets the test set the result directly.

### Educational article library — [content/articles/](content/articles/) + [tools/build_articles.py](tools/build_articles.py) + [ArticleLibrary.cs](src/app/MergulhoVirtual/Assets/Scripts/Content/ArticleLibrary.cs) + [IArticleCatalog.cs](src/app/MergulhoVirtual/Assets/UI/Interfaces/IArticleCatalog.cs) + [ArticlesScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ArticlesScreen.cs) / [ArticleScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ArticleScreen.cs)

"Conteúdo educativo" — an in-app library of pt-BR articles (index + reader), implementing the recommended shape in [docs/educational-content-options.md](docs/educational-content-options.md) §13: **native UI Toolkit screens over typed block JSON, parsed at build time so no Markdown parser ships in the APK.** Authoring guide: [docs/articles-authoring.md](docs/articles-authoring.md) (+ the shorter [content/articles/README.md](content/articles/README.md) next to the files).

```
content/articles/<slug>.md            ← the maintainer edits this (one file per article)
content/articles/images/*.jpg         ← optional: photos an article brings with it
   ↓  make articles   →  tools/build_articles.py   (Python 3, stdlib only, editor may stay OPEN)
Assets/Resources/articles.json        ← GENERATED, never hand-edited; committed
Assets/Resources/Articles/*.jpg       ← staged photos, installed with a Sprite .meta
   ↓  Resources.Load + JsonUtility
ArticleLibrary  →  UiServiceAdapters.ArticleCatalogAdapter  →  IArticleCatalog
   ↓
ArticlesViewModel / ArticleViewModel  →  ArticlesScreen (AppRoutes.Conteudos) / ArticleScreen (AppRoutes.Conteudo)
```

**The build step IS the renderer, and that is the whole architectural bet.** The app reads one typed JSON file and nothing else; every parsing decision — the Markdown subset, the escaping, the reference validation — happens on a developer's machine where a failure has a file name and a line number. The alternative (ship a parser, parse on the phone) moves every one of those failures to a beach. `tools/build_articles.py` collects *every* problem rather than stopping at the first, and **refuses to write `articles.json` while one stands** ("N error(s) — nothing written"), so `make articles` and `make articles-check` differ mainly in whether a clean run writes. Two exactnesses behind "mainly":
  - ⚠️ **The error message says "no articles.json written", and the qualification matters.** `install_images()` runs *before* the parse and therefore before the error gate, because an `![](Articles/foo)` can only be validated against a file that is already in `Resources`. So a **failing** `make articles` has still copied every photo staged in `content/articles/images/` into `Assets/Resources/Articles/` (with fresh Sprite `.meta`s), and the message names how many rather than claiming the tree is untouched. Harmless — the install is idempotent and the file is what the article was going to reference anyway.
  - **`make articles-check` FAILS on a stale JSON**, not just on malformed authoring. It re-serialises in memory and compares bytes; if they differ it prints `articles-check FAILED — the sources are valid (…), but …articles.json does not match them` and **exits 1**. That is deliberate: `--check` is the CI / pre-commit gate and the failure it exists to catch is exactly "edited a `.md`, forgot to regenerate" — the app reads ONLY `articles.json`, so a tree where the two disagree ships stale text to a phone with nothing in any log to say so. A note that still exited 0 was not a gate. Consequence for interactive use: run `make articles`, not `articles-check`, while you are editing.

**Block schema — a flat struct with a string discriminator, for a reason that is not stylistic.** `JsonUtility` cannot deserialise polymorphically, which is the same constraint `JobEnvelope` exists for in the job queue (see **Background job system** above) — but where a job nests its payload as an opaque JSON string, a block's payload is small and fixed, so the **whole field union is spelled out on every block**: `type`, `level`, `text`, `items`, `tone`, `attribution`, `src`, `caption`, `credit`, `url`, `title`, `key`, `name`, emitted in that order so the file is byte-stable across runs and Python versions. Fields a given `type` does not use are omitted and land as C# defaults. ⚠️ **Which fields carry meaning is decided by `ArticleBlock.Kind` and by nothing else** — `Level` is meaningless on a paragraph, `Tone` on anything but a callout, and reading one anyway gets you a default rather than an error. Never infer a block's kind from "which fields happen to be filled". Ten kinds ship: heading (level 2–3 only — the title is front matter, so a body `#` is a build error), paragraph, bulletList, numberedList, callout, quote, image, video, speciesRef, beachRef.

**`ArticleBlockKind.Unknown` is forward compatibility, not a data error.** It means *this build cannot read this block* — an `articles.json` from a newer `build_articles.py` inside an older APK — and it must render as **nothing at all**: no placeholder, no "conteúdo indisponível", no empty padded card. That is why the discriminator is a string on the wire and an enum in memory: an unrecognised token degrades to silence instead of failing the parse, so a newer file drops its unknown blocks and still shows every block the build does know. `ArticleLibrary` **keeps** them in `Article.Blocks` (so diagnostics can see that content was skipped), `ArticleBlock.IsRenderable` is the filter, and **`ArticleViewModel.Blocks` is the one place it is applied** — a screen cannot forget to, and a second screen cannot reach a different answer. Distinguish it from `BeachRiskLevel.Unknown`, which means "a human has not filled this in"; nothing here is unfilled.

⚠️ **UI Toolkit does NOT decode named HTML entities, so the escaping rule is narrower than HTML escaping — and it was measured, not assumed.** `&lt;` renders as the four literal characters `&lt;` on screen. So `&` and `>` are emitted **exactly as the author typed them** (neither can open a tag), and the only character touched is `<`, which is wrapped **per character** as `<noparse><</noparse>`. `<noparse>` suspends tag parsing for its contents and is in Unity 6000.3's supported-tag table ([docs/educational-content-options.md](docs/educational-content-options.md), "What UI Toolkit rich text can and cannot do"); during the build it was additionally confirmed **by rendering** a probe paragraph — a literal `<b>` inside a noparse region printed as text and left the following words un-bolded. ⚠️ That probe was a one-off in the implementation session and **is not pinned by a test** (`--self-test` asserts the emitted *string*, not what the text generator does with it), so if you ever doubt the behaviour on a new Unity version, re-probe it in a render rather than reasoning about it. Per-character wrapping is what makes it **injection-proof by construction** rather than by exhaustion: an author typing `</noparse>` becomes `<noparse><</noparse>/noparse>`, whose noparse region holds exactly one `<`, so everything after it is literal text and nothing can escape the region. This runs **before** any of the generator's own tags are inserted, and links are pulled out to sentinels before the emphasis regexes run, because a URL may legitimately contain `_` or `*`. Front-matter prose (`title`, `summary`, `category`, `heroCredit`) goes through the same neutralisation — a UI Toolkit `Label` parses rich text by default — but is deliberately **not** marked up; inline `**bold**` and links are confined to body blocks.

⚠️ **The post-generation assertion is a left-to-right scanner, NOT a regex, and the obvious regex is what makes it necessary.** `check_emitted_tags` requires every `<` in every emitted string to begin one of the four permitted tags (`<b> <i> <u> <a href="https://…">` and their closers) or the exact escape sequence. `<[^>]*>` fails both halves: the escape sequence reads to it as two separate tags that are only legal *together*, and **a bare `<` with no `>` after it matches nothing at all** — which is the worst case, because that is precisely the `<` that opens a tag the text generator then hunts a closer for. The `--self-test` pins the behaviour in memory, including a literal `Foto: <autor> / <licença> (<fonte>)`: the repo's own credit convention, and therefore the realistic way an author produces angle brackets. **A screen must render `ArticleBlock.Text` as-is** — re-escaping it prints the tags, and concatenating unescaped text into it re-opens the hole.

⚠️ **An inline `<a href>` gets zero visual treatment and cannot be styled from USS**, because there is no way to target an inline span — so an un-underlined link reads as ordinary prose and the reader cannot tell it is tappable. The emitter therefore writes `<a href="…"><u>texto</u></a>`: **underline is the affordance**, and `<u>` carries no colour, so it does not smuggle a literal past the token-discipline rule the way a hard-coded `<color=…>` would. `<a>`/`<link>` also carry a documented **256-character limit** past which UI Toolkit truncates silently — i.e. ships a link that opens the wrong page — so that is a hard build error, as is any URL that is not `https://` with no spaces, quotes, angle brackets or parens (the attribute is built around it).

**The loader degrades and never throws into a screen**, the same contract `BeachContentLibrary` sets: a missing file, empty or malformed JSON, a `schemaVersion` from the future, an entry with no `id`, a duplicate `id`, an unreadable block `type` or callout `tone`, an `items` array on a kind that has no list, an unparseable `updated` date — each is logged once under the `[Articles]` tag (bad tokens aggregated into one warning naming up to 8 offenders, not one line per occurrence) and degraded. An unreadable **tone** falls back to `Info` because the sentence is still worth showing and a neutral tint cannot over- or under-state a notice the author wrote; an unreadable **kind** renders nothing, because there is no honest way to draw a payload you cannot read. Worst case is an empty catalog with `IsAvailable` false, which the index renders as an `MvStateView`.
  - ⚠️ **`IsAvailable == false` means the BUILD is broken, not that the user is offline.** `articles.json` ships inside the APK; there is no network in this path and nothing to retry, which is why `ArticleFormatter.StateActionLabel` returns **null always** and the state view draws no button. The two states read differently on purpose: *readable but empty* is "nothing authored yet" (a normal stage of a content project), *unreadable* is "this build shipped without its generated file".
  - ⚠️ **`IsAvailable` cannot detect a missing `"articles"` key — that reads as an EMPTY library, and it is a `JsonUtility` fact rather than a choice.** `JsonUtility` mirrors Unity's serialiser and never leaves a `List` field null, so a parsed `{"schemaVersion":1}` is indistinguishable from `{"articles":[]}`. The first draft did treat a null list as unreadable and that branch was simply dead code. It is a null-coalesce now because the realistic failures (never generated, half-written) are already caught as "missing" and "malformed JSON".

⚠️ **Two key traps the validator exists to catch, both of them the repo's standing machine-key-vs-label problem:**
  - **`@praia[…]` takes the `places.json` `name`, never the pt-BR `displayName`** — `Sueste Beach`, not `Baía do Sueste`; `Sharks Cove`, not `Enseada dos Tubarões` (see the two-names note under **Location + reverse geocoding**). The build reads `places.json` and rejects anything else, naming the trap in the error text. The screen then renders the destination's `DisplayName`, so the awkward English key never reaches the reader.
  - **`@especie[…]` takes an `AnimalDef` asset file name** under `Resources/Animals/` (`tiger_shark`, `hammerhead`, `lemon_shark`, `nurse_shark`, `reef_shark`) — the same key `beaches_content.json` and `ISpeciesCatalog.Find` use. The build lists the known keys when it rejects one.
  - Both checks read the **real files in this working copy**, so they can only validate against the species and beaches that exist here; `places.json` missing downgrades `@praia` to unchecked with a warning rather than failing the run.

⚠️ **`ArticleBlock.Src` and `heroImage` carry their OWN `Resources` folder — unlike every other image path in the app — so the loaders must not prefix them.** `AppUiHost` now has **three** sprite loaders: `LoadBeachSprite` prepends `Beaches/`, `LoadSpeciesSprite` prepends `Animals/`, and **`LoadArticleSprite` prepends nothing**, because an article authors a complete path (`Beaches/praia_do_sancho`, `Animals/tiger_shark`, `Articles/<name>`) — which is exactly what lets one article illustrate itself with a beach photo, a species photo and an image of its own. Prefix it and **every figure resolves to null and silently disappears**, since a path that does not resolve draws nothing at all (an unseeable image is not a figure, and its caption would describe something absent). [UiShotFixtures](src/app/MergulhoVirtual/Assets/Editor/UiShots/UiShotFixtures.cs) mirrors the same three-loader split, and `UiScreenshotHarness` picks the article one by matching "article" in the parameter name.

**Own photos**: drop a `.jpg`/`.jpeg`/`.png` in [content/articles/images/](content/articles/images/) and `make articles` copies it to `Assets/Resources/Articles/` **and writes a Sprite `.meta` beside it** — cloned from an existing `TextureImporter` meta with a fresh GUID, the same trick [tools/populate_animals.py](tools/populate_animals.py) uses — so Unity imports it correctly with nobody opening the Editor. Reference it as `Articles/<filename-without-extension>`. `make articles-check` copies nothing but still treats a staged file as resolvable, so CI passes before the install has happened. Photos already in the project do **not** belong there: reference `Beaches/<name>` / `Animals/<name>` directly.

**Ordering, and the one field whose default is a trap.** The index is `order` ascending, then title, then id — the id tie-break is what makes the order **total**, so it does not depend on `List.Sort` being stable (it is not) or on the generator's emission order. Category sections are **first-appearance, never alphabetical**: walking the already-ordered list and opening a group the first time a category is seen makes section order a consequence of the same `order` lever, and sorting them would hand that lever to the Portuguese alphabet. ⚠️ **An absent `order` deserialises to 0 and therefore sorts FIRST**, which is why the build script always writes an explicit `1000` rather than omitting the field. Comparisons are `Ordinal`/`OrdinalIgnoreCase`, not culture-aware, because IL2CPP can strip culture data from a player build and a sort that differs between editor and device is worse than one that puts "Água" after "Zebra".

**Adding an article — three steps** (and nothing else; no code, no scaffolder, no Editor):
1. Copy an existing file to `content/articles/<slug>.md` and edit the front matter + body. Required front matter: `id` (kebab-case, the stable key, normally the file name), `title`, `summary`, `category` (free pt-BR text, and simultaneously the grouping key and the visible heading). Optional: `hero` (a complete `Resources` sprite path — emitted into the JSON as `heroImage`), `heroCredit`, `order`, `updated` (`YYYY-MM-DD`). **Any other key is an error** — front matter is strictly typed so `titel:` fails loudly instead of dropping the title silently.
2. `make articles` — validates everything and writes the JSON.
3. Commit the `.md` **and** the regenerated `articles.json` (plus its `.meta` on a first run, and any installed photo).

**Renaming an `id` is a breaking change**, the same way renaming an `AnimalDef` asset or a `places.json` `name` is: it is the route payload and the only thing that identifies an article, so anything carrying it stops resolving. Add an article rather than re-keying one. Likewise the JSON DTO fields in `ArticleLibrary` are a **persisted wire format — add, never rename**; the loader ignores fields the file has and the DTOs lack (`_generated`, and anything a newer generator adds), which is what makes a newer file readable at all.

**Two footguns that are not about the pipeline:**
  - **`ArticleViewModel.ListNumberFor` / `ArticleFormatter.ListNumber` are dead weight in the shipped screen.** They emit `"1."`, `"2."` for an inline numbered list; `ArticleScreen.BuildNumberedList` instead uses the design system's `MvNumberedList`, which draws its own numbers in filled circles. So the contract now carries **two renderings of the same thing** and only one is reachable (the other is covered by tests alone). Harmless, but do not assume a numbered list is inline text because the formatter says so — and if you delete one, delete its test with it.
  - **`IBeachCatalog` has no `Find`,** so `ArticleScreen.BeachName` walks the `Beaches` list per `beachRef` block to turn the machine key into a `DisplayName`. It is 17 entries and it runs while an article is built, not per frame, so it is not a performance problem — it is an interface asymmetry (`ISpeciesCatalog` *does* have `Find`) worth knowing before you add a third caller.

**Seeing it without a device**: `make ds-shots SHOT=conteudo` — the filter is a substring match, so that one command renders all five subjects (10 PNGs, light + dark), `shell-conteudos` included, which is the index with the nav bar up. Four *screen* subjects exist because the corpus has four genuinely different shapes and no single article exercises them all — `conteudos` (the index: four categories, three covers and one without), `conteudo` (tubarões: the only article with a video block and with `speciesRef`, five of them in a row), `conteudo-sem-capa` (the no-hero path, which swaps the 240dp `MvHeroHeader` for a plain back-button row, plus the angle-bracket paragraph only a render can settle) and `conteudo-praticas` (numberedList, warning + success callouts, two `beachRef`s, and the one figure in the corpus with neither caption nor credit). **These PNGs are not a comparison — they are the design review**, because there is no Figma frame for either screen.

### App shell, scene layout and the AR performance gate — [AppUiHost.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/AppUiHost.cs) + [MdRouter.cs](src/app/MergulhoVirtual/Assets/UI/Navigation/MdRouter.cs) + [ScreenManager.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/ScreenManager.cs) + [SplashScreen.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/SplashScreen.cs)

The app is a **single scene**, never `SceneManager.LoadScene`. Reason: AR session startup, camera permission, GPS fix, and the ONNX worker + GPU tensor allocations in [CameraFeedToInference.cs](src/app/MergulhoVirtual/Assets/Scripts/CameraFeedToInference.cs) are expensive and visibly slow on Android; reloading the scene to "go back" restarts all of them. Keep AR/sensors/inference components at the scene root.

**Navigation is [`MdRouter`](src/app/MergulhoVirtual/Assets/UI/Navigation/MdRouter.cs), not `ScreenManager`.** Since Slice 1 of [DESIGN_IMPLEMENTATION.md](DESIGN_IMPLEMENTATION.md) the app boots into a UI Toolkit shell: one always-on `UIDocument` on the scene-root **`AppUI`** GameObject, whose router owns every destination plus the persistent `MdNavigationBar`. `ScreenManager` kept exactly one job — deciding whether the AR session runs. The full contract (`IAppScreen`, `AppRoutes`, `Navigate` vs `Push`/`Back`, edge insets, the `LegacyUguiScreen` adapter) is documented under **Phase 3 — UI layer** below; this section is the scene and the gate.

Scene layout — **verify against the file, not this list** (`grep m_Name: Assets/Scenes/MainScene.unity`; it drifts). Top-level GameObjects sit flat at the root — there is **no** `Systems` parent, each concern is its own root object:

**Slice 6 emptied the rest of `ScreenUI`.** `BottomNav`, `BeachesScreen`, `RegisterScreen` and `AnimalsScreen` — deactivated and unrouted since Slices 1–3 — were deleted from the scene along with their controllers and builders; the four GameObjects above are all that is left of uGUI. `MainScreen` and `AboutScreen` are activated/deactivated by the router (`LegacyUguiScreen` / `AppUiHost.OnRouteChanged`) — don't `SetActive` them by hand. `MainScreen` outlived Slice 6 only because it hosted the on-beach **ArTuning** panel; that was removed 2026-09-29, so it is now an empty shell holding one deactivated `TopBar` and is ready to be deleted (see the AR stabilization section for the exact removal list).

`JobQueue` is **not** in the scene tree either — `JobQueue.GetOrCreate()` auto-spawns a `JobServices` GameObject with `DontDestroyOnLoad`; today that happens from `AppUiHost.Awake` via the sighting-reports adapter (see **Background job system**). If you ever pre-place one in the scene (e.g. to set `maxQueueSize`), the singleton check in `Awake` still works — but don't have both.

**What `ScreenManager` owns, and only this** ([ScreenManager.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/ScreenManager.cs)): the AR-session performance gate. `AppUiHost` calls `ScreenManager.SetRoute(route)` on every route change (it may fire before `Start`, so the route is remembered and applied once the display rate has been read). The gate then:

- **Inference gate**: `CameraFeedToInference.inferenceEnabled = (route == AppRoutes.Mergulho && !splashActive)`, so tensor work is paused on every non-AR route. Don't bypass it by toggling screens outside the router.
- **Performance gate**, behind the `Use Optimized Performance` Inspector bool (default on; uncheck for the legacy "AR + 30 fps everywhere" behavior). On a non-AR route: `arSession.enabled = false` (camera + tracker stop — big battery win, sub-second resume; no anchors are used, so no re-localization concerns), `matchFrameRateRequested = false`, and `Application.targetFrameRate = displayRefreshRate` so UI scrolls at the panel's native 90/120 Hz instead of the camera's 30. On Mergulho and during the splash, AR stays enabled at 30. **Splash deliberately keeps AR alive** so camera/tracker init hides behind the splash image — the same rationale that drives the single-scene architecture. `QualitySettings.vSyncCount = 0` is set once in `Start()` because `Application.targetFrameRate` is silently ignored on some Android targets while vSync is on.
- **Splash handoff**: `Start()` shows `ScreenUI/SplashScreen` and calls `appUi.SetShellVisible(false)`; `SplashScreen.GoToMain` calls back into `OnSplashFinished()`, which hides the panel and re-shows the shell. Only the shell's **panel-root `display`** is toggled — never the `AppUI` GameObject — so the visual tree is not torn down and rebuilt mid-session.

**Draw order**: the UI Toolkit panel is at `sortingOrder 100`, the uGUI Canvas at 0, so the shell always paints on top of every legacy screen — including the `Panel` debug overlay, which is therefore only visible where the shell paints nothing (i.e. under the AR HUD). The router root and its screen container are `PickingMode.Ignore`, so taps fall through to the canvas wherever the shell draws nothing. If the order ever looks wrong on device, that is one number: `AppUiBuilder.PanelSortingOrder` + `make ui-setup`.

**Adding a screen** is now a router registration, not a `ScreenManager` field: implement `IAppScreen`, add a route key to `AppRoutes`, `Register` it in `AppUiHost.RegisterScreens`, and add its `.uss` to `AppUiBuilder.ScreenStylePaths` — see **Phase 3 — UI layer** below for the full checklist. `ScreenManager` should not grow fields again.

**UI framework: uGUI → UI Toolkit (decided 2026-09-14, in progress).** The legacy uGUI + TextMeshPro screens were throwaway debug UI; the app is being rebuilt on the **design system** at [Assets/DesignSystem/](src/app/MergulhoVirtual/Assets/DesignSystem/) against the designer's V2 prototype, screen by screen, per [DESIGN_IMPLEMENTATION.md](DESIGN_IMPLEMENTATION.md) §7 (the content of Phase 3 in [design-system-implementation-plan.md](design-system-implementation-plan.md)). Slices 0–4 (foundations, shell + Início, Praias, Avistamentos, Mergulho) have landed, and **Slice 6 has deleted the superseded uGUI screens**; only SOS (Slice 5, blocked on Decision D3) is left. **Strangler, never a big-bang cutover** — but note parity was declared as each slice landed, and the replaced screens were deactivated and unrouted for one slice before being deleted, not kept "live until parity". The uGUI layout rules further down still apply to whatever legacy screen you touch; they do **not** apply to UI Toolkit screens, which have their own rules in the design-system sections.

## Working in this codebase

- **Resources loading**: the code deliberately uses `Resources.Load<TextAsset>("name")` (no extension) for `class_desc`, `places`, `articles`, etc. Anything referenced this way must live under `Assets/Resources/` — moving it breaks runtime loading silently (you get a `null` TextAsset and a `LogError`, not a compile error).
- **`content/` at the repo root is authoring input, not code.** [content/articles/](content/articles/) holds the educational articles' Markdown source and `make articles` compiles it into `Assets/Resources/articles.json` (+ installs any staged photo into `Assets/Resources/Articles/`). So **generated assets inside the Unity project have their source outside it**, and both halves are committed — edit the `.md`, re-run the target, commit the `.md` and the regenerated JSON together. Do not hand-edit `articles.json`; the next `make articles` overwrites it. See **Educational article library** under Architecture.
- **Unity 6 + URP + AR Foundation 6**: several APIs used here (`Worker`, `TextureConverter.ToTensor`, `ARCameraFrameEventArgs`) are recent. When searching docs, pin to Unity 6 / URP 17 / AR Foundation 6 — older Barracuda/Sentis and AR Foundation 4.x examples will mislead you. Specific footgun: in AR Foundation 6 the frame-rate-matching property is `arSession.matchFrameRateRequested` (settable bool) with `matchFrameRateEnabled` as the read-only "what the subsystem actually negotiated" companion — **not** `matchFrameRate`. Older docs and forum posts mention `matchFrameRate`; that name compiles in AR Foundation 4 but errors in 5/6 with `'ARSession' does not contain a definition for 'matchFrameRate'`.
- **Prefabs and scene references**: `MonoBehaviour` fields are wired via the Inspector in `MainScene.unity`/prefabs. Renaming a serialized field (e.g. `classificationResultText`) without a `[FormerlySerializedAs]` attribute will silently drop its Inspector reference.
- **`AspectCover` doesn't observe sprite changes**: it computes the aspect ratio in `OnEnable` and never reruns. Only two uGUI objects still carry it (`ScreenUI/SplashScreen/Image` and `ScreenUI/AboutScreen/Image`), both with a design-time sprite — but if you ever swap an `Image.sprite` at runtime on a component with `AspectCover`, call `AspectCover.Refresh()` after the assignment — otherwise the `AspectRatioFitter` keeps its design-time ratio and the photo renders the wrong shape (too tall, too wide, or letterboxed inside the mask).
- **Generated files**: `Library/`, `Temp/`, `Logs/`, `UserSettings/`, and all `*.csproj`/`*.sln` under the Unity project are generated by the editor — do not edit or commit them. The `.gitignore` already excludes them, as it does the repo-root `.shots/` folder `make ds-shots` writes and the `.arsim/` folder `make ar-sim` writes.
- **Git LFS also tracks the TextCore font assets** — `src/app/MergulhoVirtual/Assets/DesignSystem/Fonts/*.asset` is in the repo-root [.gitattributes](.gitattributes) alongside the native binaries. They are plain-text YAML, but TextCore bakes the rasterised glyph atlas into the file, so they grow to tens of MB and **churn on every `make ds-setup` and every `make ds-shots` run** — `ds-setup` rebuilds them from the TTFs outright, and `ds-shots` grows the atlas whenever it rasterises a glyph that was not in it. **Expect them dirty after either target; they are regenerated output, not edits.** They are fully regenerable with `make ds-setup`, editor closed. `MaterialSymbols.ttf` itself churns the same way whenever `make ds-icons` re-subsets it. A fresh clone still needs `git lfs install`; the production VM deliberately has no `git-lfs` and doesn't need one (the backend never reads `Assets/`).
- **Tide JSON is built from the official DHN tide table** (Brazilian Navy), not a numerical model. Source-of-truth PDF: [src/app/MergulhoVirtual/tabua_mare_noronha_2026_marinha.pdf](src/app/MergulhoVirtual/tabua_mare_noronha_2026_marinha.pdf), printed annually by Marinha do Brasil for *Arquipélago de Fernando de Noronha (Baía de Santo Antônio)*, station Carta 52. Two-step pipeline:
  1. [tools/parse_dhn_tide_table.py](tools/parse_dhn_tide_table.py): PDF → `tools/dhn_tides_2026.json` (3–4 official extrema per day; 365-day coverage; uses `pdftotext -layout` to slice the 8 sub-columns per page; self-validates day count).
  2. [tools/build_app_tides.py](tools/build_app_tides.py): events JSON → [Assets/Resources/tides_noronha.json](src/app/MergulhoVirtual/Assets/Resources/tides_noronha.json), which carries **two** parallel views of the data: `heights_m` (8760 hourly samples for the year, cosine-interpolated between adjacent extrema, mirror-extrapolated one half-cycle on each year boundary) for the smooth sparkline curve, and `events` (1410 `{utc, h, k}` records, the literal DHN extrema in UTC) for the next-high/next-low display in `ConditionsCard`. [TideService.cs](src/app/MergulhoVirtual/Assets/Scripts/TideService.cs) reads `events` to preserve the published HH:MM peak times exactly — the hourly grid alone can only resolve peaks to HH:00, which doesn't match the navy table when read by a local user (e.g. DHN says low at 12:40 0.42 m; the hourly scan would have said 12:00 0.40 m).
- **Heights are LAT-referenced** (chart datum / lowest astronomical tide) — same convention as the DHN printed table, so values are essentially all positive (rare extreme spring tides print as `-0.03 m` in the official table itself; cosine interp passes through them). The PDF header prints `Nível Médio 1.28 m` — that IS the MSL→LAT offset for this station, drawn as a dashed horizontal reference by `MdSparkline.Baseline`, which every conditions card sets to `1.28` (the uGUI `TideSparkline` that first carried the constant went with Slice 6). Locals reading "2.2 m próxima alta" in `ConditionsCard` will match the navy table exactly.
- **Tide accuracy**: cross-checked across all **939 official DHN tide events** in the May–Dec 2026 prediction window when this was still pyTMD/GOT5.6: mean abs error 37 mm, p95 79 mm, max 118 mm. Now that the app is fed the DHN table directly, app-vs-DHN error is just hourly-sampling residual (mean 17 mm, max 39 mm) and there's no model to disagree with. The pyTMD path remains in the repo as a fallback for when no DHN PDF is available for a year.
- **Regenerating tides for a new year**: download the next year's PDF from Marinha do Brasil, drop it under `src/app/MergulhoVirtual/`, then `./tools/parse_dhn_tide_table.py <pdf>` followed by `./tools/build_app_tides.py`. No venv needed — only `pdftotext` (poppler-utils) plus the Python stdlib. Update `YEAR` at the top of [tools/parse_dhn_tide_table.py](tools/parse_dhn_tide_table.py) when crossing into the new calendar year. The legacy pyTMD generator is still at [tools/generate_tides.py](tools/generate_tides.py) (needs venv + ~250 MB GOT5.6 model download — see its SETUP block); only reach for it if no DHN table is available, and remember it produces MSL-referenced heights, not LAT.
- **External UPM packages (besides Unity's own)**: `com.yasirkula.nativegallery` (git URL in [Packages/manifest.json](src/app/MergulhoVirtual/Packages/manifest.json)) is required for the gallery picker. First import needs internet; after that it resolves from the package cache. iOS additionally needs `NSPhotoLibraryUsageDescription` set in Project Settings → Player → iOS → Other Settings (NativeGallery prints a warning otherwise). ## Design system — UI Toolkit + Material Design 3 ([Assets/DesignSystem/](src/app/MergulhoVirtual/Assets/DesignSystem/))

**Component footguns already paid for.** Each of these was a real defect; the fix is in the file with its reasoning, and the trap is the part worth knowing before you edit that component:

- ⚠️ **`MdChip` — padding compensates a removed border, so the padding numbers are not the spec numbers.** The base chip is `12px` horizontal with a 1px outline, i.e. 13dp of transcribed inset; a **selected** chip drops the outline (it fills with `primary` / `on-primary`, the brand navy + white), so its rule pays the 1px back as `padding: 13px`. The `--with-icon` pair is the same arithmetic one step in (8 → 9). The old sheet carried only the `9/17` *icon* pair and assumed every selected chip had an icon, which held only because **`MdChip.cs` injected a check glyph onto any selected chip regardless of `Kind`** — so tapping an *Assist* chip grew it 18.5dp and re-flowed the row under the user's finger. Glyph injection is now gated on `Kind == Filter` and the no-icon pair is authored explicitly, with `.md-chip--selected.md-chip--with-icon` at higher specificity so source order stops mattering. **If you change a chip padding value, change its selected partner in the same edit.**
- ⚠️ **`MvOptionCard` — `min-height`, never `height`, on anything with `overflow: hidden`.** The card carries `overflow: hidden` because the state-layer contract requires the layer to follow the corners. Its label was `nowrap` at a fixed `height: 93px`; letting it wrap without moving to `min-height` would have *clipped* line two behind the overflow rather than growing the card. The pair is the rule: **a wrapping label inside a clipped box needs the box to be a floor, not a fixed size.**
- **`MdSparkline` extremum labels are clamped, not just centred.** They were positioned by percent with `translate: -50%` and no clamp, so the last label ran 3.5dp past the card's padding box and an extremum at index 0 or n−1 would have put half a label outside the card entirely. `MdSparkline.ClampLabelCenter` holds them inside the strip.
- **`MdTopAppBar`'s centre-aligned title is `position: absolute` with symmetric 48dp insets, and the actions slot is pinned right.** Without the pin, a bar with actions but no navigation icon jumps its actions to the left.
- **`MdMenu` is a `surface` with a 1px `outline-variant` border, because UI Toolkit has no `box-shadow`.** On `surface-container` it was near-invisible against the `background` page (#F3F4F6 on #F9FAFB, no border, no shadow), and `.md-menu__scrim` was styled in **no `.uss` file in the project at all**. Selected rows use `surface-container-high`, not `secondary-container` — V2 draws no amber row in a menu.
- **`MdNavigationBar` labels are `width: 100%` + `-unity-text-align: middle-center`, and that is not decoration.** "Avistamentos" is 71dp of text in a 64dp tab, and **Yoga clamps an over-wide flex child to flex-start instead of centring it** — so that one tab alone rendered ~3.75dp left of its own icon. Making the label fill the tab and centre its text puts the overhang on both sides. Related: **the bar measures 99dp against Figma's 98 and that is deliberate** — the extra 1dp is the `border-top`, which sits outside the fill, and the *content* position measured exact; chasing 98 would move the content off spec.
- **`MdButton` carries `min-width: 48px`** so a short text button is still a 48dp target rather than the ~42dp its text width gave it.
- **`MvMediaPicker`'s remove badge is a real alpha over an arbitrary backdrop.** It used to set `background-color: scrim` and declare **no `opacity` at all** — an opaque black disc — while the comment three lines above described exactly the 25 % the spec asks for. It is now `0.47` (see the linear-colour-space rule below). Its size hint is `middle-left` in the base rule with the empty state re-centring it, not centred for both.

Gallery/Tests/Editor asmdefs sit alongside, and the app layer `MergulhoVirtual.UI.asmdef` (screens + ViewModels) references DesignSystem only — see **Phase 3 — UI layer** below.
- **Everything visual is a token; everything is regenerable.** Components and screens may only consume `var(--md-*)` variables — never literal colors/sizes. **`TokenDisciplineTests` fails if a USS hard-codes a color, uses an undefined token, or the two themes drift** — and it scans `Assets/UI/**/*.uss` as well as the component sheets. ⚠️ **It scans raw file text, so a `#RRGGBB` literal in a USS *comment* fails exactly like a real declaration.** That matters here because the good comments are full of measured colours (which value composited to what, what V2 draws). **Write hex in a USS comment as `0xRRGGBB`** — it is the house convention, already used throughout `HomeScreen.uss`, `MergulhoScreen.uss`, `EspecieScreen.uss` and `ReportScreen.uss`. This broke the build once and cost a sweep of ~28 comment literals across four stylesheets. (The `Tokens/` files are exempt — they are where the literals are *defined* — which is why `_brand-*.uss` can write `#3A3F45` in its table.)
- **Color tokens are generated from the brand JSON, not from a seed.** `Tokens/_colors-light.uss` / `_colors-dark.uss` are GENERATED — `make ds-tokens` runs [generate_md3_tokens.py](tools/design_system/generate_md3_tokens.py) **`--from-json tools/design_system/brand-theme.json`**, which copies `schemes.light`/`schemes.dark` verbatim. The seed path is wrong for this palette: V2's navy `#152336` (primary) and amber `#FFC107` (secondary) are independent hues, not a tonal derivation of one seed, so `brand-theme.json` is hand-authored from the Figma measurements (DESIGN_IMPLEMENTATION.md §3.1 / Appendix A.1) and committed. **Never hand-edit `_colors-*.uss`.**

They measure at **exactly the brand navy's chroma and hue in CIELAB** (C 14.2, h 272 against primary's C 14.2, h 273), on the same constant-chroma ramp as `primary-dim` and `on-primary-fixed-variant`; a Material Theme Builder seed pass would have forced chroma to ~48 and could not land C 14.2 four times running. `tertiary-container` / `on-tertiary-container` likewise sit on the amber hue (h 83–86), matching `brand-theme.json`'s own stated rule. They are `on-primary` now. `TokenDiscipline` cannot catch this: it only checks that a token is defined, not that it is one the design uses. When a role "looks close", check it against A.1 before shipping it.
- **`_brand-light.uss` / `_brand-dark.uss` are the hand-maintained extension tokens.** M3 has `error` but no `success` and no `warning`, and V2 needs both (the "Risco: Baixo" badge, the lifeguard alert bar), so `--md-sys-color-success|warning` + their `on-`/`-container`/`on-…-container` partners live here, keeping the `--md-sys-color-*` prefix so components can't tell stock M3 from ours. **Three things move in lockstep or the suite goes red**: both brand files must define the *identical* variable set, both `.tss` files must `@import` their side (parity-tested), and `TokenDisciplineTests.TokenFiles(theme)` lists them explicitly. The same pair also carries the **`camera-*` family** (the AR HUD's surfaces, identical in light and dark because the backdrop is a lens rather than a theme) and **`inverse-on-surface-muted`**; most of those are pre-blended composites — see the linear-colour-space rule immediately below.
- ⚠️ **An alpha transcribed from Figma will NOT composite the way Figma composited it — the project renders in LINEAR colour space.** This is systemic, it bites every component and screen author, and it is the single most common reason a transcription "looks right in the file and wrong in the render."
  - **Mechanism**: `ProjectSettings.asset` has `m_ActiveColorSpace: 1`, so a USS colour is converted sRGB→linear, blended, and converted back. **Figma blends directly in sRGB.** The same `rgba` over the same backdrop therefore lands somewhere else in Unity — always too **light**. Validated, not theorised: white @0.10 over `camera-surface-dim` (`#050B14`) was predicted at (90,90,92) and measured (90,91,92) in the render; the model agreed to ±1 on every channel tested.
  - ⚠️ **The direction depends on the overlay, so never reflexively "reduce the alpha."** A *light* overlay on a dark backdrop needs its alpha cut ~3.5× (0.15 → 0.043). A *dark* overlay on a light backdrop needs it **raised** ~1.7× (0.25 → 0.43).
  - **Per-channel corrections diverge** (one measured case wanted 0.032 / 0.042 / 0.054 on R/G/B), so **no single alpha reproduces Figma exactly.** That divergence is what decides the fix:
    - **Backdrop opaque and known → pre-blend to an opaque token. This is exact.** Every `camera-*` hairline and fill is a composite authored as a hex, not an alpha: `camera-outline` `#2A3037` (white .15 over `camera-surface-dim`), `camera-outline-dim` `#54585D` (white .13 over `camera-surface`), `camera-divider` `#262B33`, `camera-fill` `#1E232C`, `camera-fill-outline` `#40444C` (white .15 over `camera-fill`), and `inverse-on-surface-muted` (`inverse-on-surface` @.5 over `inverse-surface`). **`camera-divider` and `camera-fill-outline` exist only because pre-blending is backdrop-bonded**: `camera-outline` / `camera-outline-dim` each served *two* different opaque backdrops, and one alpha can serve two backdrops where one pre-blend cannot. **The rot risk is the flip side of the same coin** — move `camera-surface` or `camera-surface-dim` and every composite has to be recomputed by hand; they will not follow the way an alpha would. They are named after the surface they are drawn **on** for that reason.
    - **Backdrop arbitrary (a photo, a video frame) → keep a real alpha, at the corrected value.** `MvHeroHeader`'s scrims are **0.505** (authored 0.35) and **0.38** on the 240dp compact variant (authored 0.25); `MvTag--on-image` is **0.90** (authored 0.80); `MvMediaPicker`'s remove-badge fill is **0.47** (authored 0.25 — and note it goes *up*). App-side: `HomeScreen.uss` sparkline fill 0.14 → **0.025**, freshness 0.7 → **0.49**, sparkline baseline 0.4 → **0.19**, state-view icon 0.5 → **0.27**, state-view body 0.75 → **0.57**; `EspecieScreen.uss` model-placeholder icon 0.4 → **0.15**. Every one of these carries its arithmetic in a comment above the rule — **do not "restore the spec number."**
  - **The biggest single miss this rule caught** was `MdNavigationBar`: inactive destinations drawn as `inverse-on-surface` + `opacity: 0.5` rendered **(183,184,185)** against the design's **(127,130,136)**, i.e. inactive tabs read nearly as bright as the active one and the selected-state signal was gone. They now take the pre-blended `inverse-on-surface-muted`, and `--active` swaps the ink **colour** instead of the opacity (the `opacity: 1` overrides are deleted).
  - **Alphas deliberately NOT corrected — this list is what stops someone "finishing the job" wrongly**: the M3 **state layers** `0.08 / 0.10 / 0.12` (`--md-sys-state-*`, ~30 sites) are relative interaction feedback, not Figma transcriptions; **`MdDialog` / `MdBottomSheet` scrims (both 0.32)** and the **sheet handle (0.4)** are M3 spec constants and V2 has no dialog or sheet frame to match against (they have the same defect — the 0.32 scrims deliver only a ~0.157 effective dim and would need ~0.58 — so it is a one-line change each if anyone ever wants it); **`MdMenu`'s scrim 0.32 is kept on purpose** because a menu is *not* modal (stock M3 gives it no scrim, V2's Tela 9 shows no page dim) and under linear blending that 0.32 renders as the light non-modal veil a dropdown actually wants — it coincides with `MdDialog`'s number while **meaning something different, so do not unify the three**; `MdSparkline`'s component-default fill 0.15 / baseline 0.6 have **no authored alpha to transcribe** (the sparkline is a bitmap in the Figma file) and are eye-tuned; the sparkline's screen-side label `0.75` already renders `#E1E1E2` against the Figma bitmap's `#E5ECF2` peaks, so **correcting it would move away from the design**; and `.mv-report__pending-retry`'s `:disabled` 0.45 is M3 disabled vocabulary dimming a subtree that contains a `primary` label.

- **Typography is Inter, retuned** ([Tokens/_typography.uss](src/app/MergulhoVirtual/Assets/DesignSystem/Tokens/_typography.uss), hand-maintained). Four weights = four TTFs = four TextCore SDF assets (400/500/600/700), because UI Toolkit resolves weight through a separate font asset, and `-unity-font-definition` is declared on **every** class (even the 400 ones) because it inherits — omit it and a body label nested in a bold title renders bold. The `.md-typescale-*` class **names** are kept so every Md* component inherits the brand automatically; only the **values** are retuned to V2's 11/12/13/14/15/16/18/20/24/26 ladder, and **letter-spacing is 0 everywhere** (M3's Roboto tracking is wrong for Inter). - ⚠️ **`corner-full` is a CIRCLE token, not a pill token — pills carry a literal half-height radius.** CSS resolves an over-large `border-radius` by scaling *all* radii by one shared factor, which preserves the stadium; **UI Toolkit instead clamps each axis independently** (`rx = min(r, width/2)`, `ry = min(r, height/2)`), so `corner-full`'s 1000px on a 295×42 element resolves to rx 147.5 / ry 21 — a full ellipse (a lens). A stadium therefore needs `r == height/2` **exactly**; larger re-opens the ellipse, smaller is a plain rounded rect. Two ways to get it, and the choice is mechanical:
  - **Height authored in USS** (every pill in the library but one): write the literal half-height on the same rule as the height it halves — `height: 40px; border-radius: 20px`. No runtime cost, still overridable from a screen stylesheet. `MvHeroHeader`'s selector pill is `border-radius: 21px` against its 42dp height for exactly this reason.
  - **Height driven by content** (font metrics, wrapping, OS font scale) so it cannot be written down: call [`MdShape.KeepStadium(element)`](src/app/MergulhoVirtual/Assets/DesignSystem/Components/Shape/MdShape.cs), which re-pins the radius to half the *resolved* height on every `GeometryChangedEvent`. `MvTag` is the only user. It writes an **inline** style, which outranks every stylesheet — so once a component opts in, its radius can no longer be restyled from USS. That is the point, and it makes this a decision about the component, not a tweak.
  - **`ShapeDisciplineTests` fails the build** if `corner-full` appears on a rule that does not declare equal width and height, and separately if a USS radius is authored on the element `KeepStadium` owns — so a pill cannot quietly regress into a lens, and nobody can "tidy up" by putting `corner-full` back on `MvTag`. `StadiumCornersTests` covers the runtime half in PlayMode. The **four surviving `corner-full` uses are all genuinely square** and therefore correct circles: `MdIconButton` (40×40), `MdCheckbox` (40×40), `MvNumberedList` (24×24), `MvMediaPicker`'s remove badge (28×28).
- **Component contract** (reference implementation: [MdButton.cs](src/app/MergulhoVirtual/Assets/DesignSystem/Components/MdButton/MdButton.cs)): `[UxmlElement]` partial class; data in via `[UxmlAttribute]` properties, events out via C# events; root element = ≥48dp touch target, visible `__container` child holds a first-child `.md-state-layer` (base class in `_state.uss`) driven by `:hover/:active/:focus` opacities; BEM classes (`md-button--filled`); own `.uss` imported by BOTH theme files (keep the two import lists in sync — tested). A component ships code + USS + gallery entry + tests or it isn't done.

Skip the second and every render still shows the old glyphs, with nothing in the log to say so.

Material Symbols is a variable font and the whole set used to ship **Outlined** (`FILL: 0`), while every V2 glyph is a **solid** mark — measured amber ink coverage in the Home feature tiles was 25/16/33 % in Figma against 8/8/13 % in the build, marks 4–8dp smaller carrying a third to half the ink. **48 of the 95 icons gain ink, up to 4×** (`visibility` 10.5 → 34.5 %, `location_on` 14.6 → 37.0 %). Substituting a plausible-but-wrong glyph is exactly what the D7 note in `material_symbols_icons.txt` forbids, and the rule does not only apply to the shark fin. (The FILL measurement above was taken at 95 icons; the +1 changes none of it, since advance widths are identical per glyph.)

- **dp calibration**: both PanelSettings assets use Constant Physical Size @ 160 dpi so **1 USS px = 1 dp = 1 Figma pt** — transcribe spec values literally, no scaling.
- **UI Toolkit limitations accepted**: no `line-height` (the type scale is size only; Inter's own metrics approximate V2's fixed line heights), no `box-shadow` (V2's shadowed surfaces all carry a 1px `outline-variant` border too — render the border, drop the shadow), no `cubic-bezier()` (nearest named easings, see `_motion.uss`), font weight = a separate font asset.
- **Label metrics are reset app-wide — don't re-discover this.** Unity's default runtime theme gives every `Label` `padding: 4 2 4 1` + `margin: 4 4 2 2` — **14dp of invisible vertical and 9dp of invisible horizontal space** that no Figma text node has, which both doubles every transcribed gap (a 17dp conditions row measured 31dp) and costs whole wrapped lines (a feature-card body wrapped to 4 lines at 140dp where Figma fits 3 at 149). `.unity-label { padding: 0; margin: 0 }` in [Tokens/_typography.uss](src/app/MergulhoVirtual/Assets/DesignSystem/Tokens/_typography.uss) (the "Label metric reset" block) zeroes it once for the design system AND the screens, which is why Figma dp values transcribe directly. Cascade: default theme < `_typography.uss` < `Components/*.uss` < a screen's own stylesheet, so a component or screen puts spacing back with a plain single-class rule — **no compensating margins, and nothing may lean on the default metrics**: any new stack of labels authors its own (see `MdTextField`'s `margin-top: 4px` on supporting text, or the Home feature card's `margin-bottom: 2px` title).
- **You cannot hide a ScrollView's scrollbar from USS.** `ScrollView` writes the scrollers' `display` as an **inline** style on every layout pass (that is how `ScrollerVisibility.Auto` appears and disappears), and inline styles beat stylesheets — so `display: none` on `.unity-scroller` does nothing. UI Toolkit's stock scroller is a desktop control (permanent track + ▲▼ steppers) and is in none of the V2 frames. **In the app assembly use [`AppScrollView`](src/app/MergulhoVirtual/Assets/UI/Controls/AppScrollView.cs)** — a `ScrollView` subclass whose only job is `ScrollerVisibility.Hidden` on both axes, so the decision lives in one place instead of a line every screen has to remember. Inside a design-system component (which may not reference the app assembly) set `ScrollerVisibility.Hidden` from C# directly, as [MvMediaCarousel](src/app/MergulhoVirtual/Assets/DesignSystem/Components/MvMediaCarousel/MvMediaCarousel.cs) does; and on a `ScrollView` you did not create — the one inside an `MdMenu` popup, say — `Q<ScrollView>()` it and set the same two properties after opening (`PraiasScreen.OpenBeachMenu`). Touch/wheel/keyboard scrolling are unaffected either way.
- **`flex-basis: 0` means *width* in a row and *height* in a column.** The same declaration that makes grid cells split a row evenly collapses a card to zero height the moment you reuse it as a child of a column — which is exactly what happened to the Home "Sobre" card: `flex-grow: 1; flex-basis: 0` inherited from the grid-cell class, plus `min-height: 0`, left nothing holding it open and it shrank to its 24dp of padding and clipped its own title. Any class reused across a row and a column context must reset `flex-grow: 0; flex-basis: auto` (see `.mv-feature-card--wide` in [HomeScreen.uss](src/app/MergulhoVirtual/Assets/UI/Screens/HomeScreen.uss)).
- ⚠️ **Moving an existing Label into a flex ROW silently makes it shrinkable and wrappable — pin it in the same edit.** A flex child defaults to `flex-shrink: 1`, and the app's heading classes carry `white-space: normal` (headings elsewhere are block-level and may legitimately wrap). Splitting "Se identifique (opcional)" into two labels so the parenthetical could take its own weight and colour therefore shrank the title to a fraction of its text width, wrapped it onto two lines, and **collided with the "Seu nome" field below** — with the entire test suite green, because structure tests cannot see layout. **The house pattern for the whole class of failure is `flex-shrink: 0` + `white-space: nowrap` on every label in such a row** (see `.mv-report__section-heading` in [ReportScreen.uss](src/app/MergulhoVirtual/Assets/UI/Screens/ReportScreen.uss)), which is only safe because the strings are short by construction — if they are not, the *decorative* one takes the ellipsis (`PraiaDetalheScreen`'s binomial) and the load-bearing one stays whole. Related: UI Toolkit has no baseline alignment, so a row of differently-sized labels uses `align-items: flex-end` as the closest approximation of a shared baseline — which means the heading's own `margin-bottom` has to move to the *row*, or it pushes the heading above its own note.
- **Headless workflow — minimize editor GUI.** The editor must be **CLOSED** for `ds-setup` / `ds-test` / `ds-test-play` / `ds-compile` / `ds-shots` / `ui-setup` — and for the AR targets `ar-sim` / `ar-sweep` (see **Offline wave-drift simulator**) — since they all fail with "project already open". `make ds-tokens` and `ds-icons` are pure Python and don't care.
  - `make ds-tokens` — regenerate `_colors-*.uss` from `brand-theme.json`.
  - `make ds-icons` — re-subset `MaterialSymbols.ttf`.
  - `make ds-setup` — FontAssets + PanelSettings + GalleryScene via `-executeMethod` (also under Tools > Mergulho Virtual > Design System). FontAssets are TextCore dynamic SDF generated from the TTFs — regenerate after re-subsetting icons or adding a weight.
  - `make ds-test` / `ds-test-play` / `ds-compile` — EditMode tests (three assemblies, see the status block above), PlayMode interaction tests, and an imports-and-compiles-only check.
  - `make ui-setup` — rebuild/rewire the app shell into `MainScene` (see **Phase 3**). The old `ui-beaches-setup` name is kept as an alias.
  - **`make ds-shots` — render every UI Toolkit screen and gallery section to PNG.** This is the fastest way to see a UI change without a device build: 98 PNGs (both themes, 2× supersampled at 390×844 dp so they line up with the 2× Figma renders in `.figma-sync/png/`) into a gitignored `.shots/`, plus a `manifest.json` recording the frame size, scale, safe-area insets and the frozen clock. `make ds-shots SHOT=home` filters by subject id. Harness: [Assets/Editor/UiShots/](src/app/MergulhoVirtual/Assets/Editor/UiShots/) — the **subject table at the top of [UiScreenshotHarness.cs](src/app/MergulhoVirtual/Assets/Editor/UiShots/UiScreenshotHarness.cs#L63)** is one line per shot (a screen can also carry `VmMethod`/`VmCalls` to drive its ViewModel into a state, which is how `report-filled` gets a real picked photo), and any `IAppScreen` the table does not name is auto-discovered and shot anyway. Screens are constructed against the deterministic [UiShotFixtures](src/app/MergulhoVirtual/Assets/Editor/UiShots/UiShotFixtures.cs) — frozen clock, fixed conditions/tide, no GPS, no backend — so a PNG changes only when the UI does. **Two footguns**: it is the one Unity target that must NOT pass `-nographics` (it needs a real graphics device to rasterise the panels), so it needs an X display — the Makefile defaults to `DISPLAY=:1`, override with `make ds-shots DISPLAY=:0`; and because it renders new glyphs, it **churns the LFS-tracked font assets** (see **Working in this codebase**).
  - **Rendering at other device widths — the responsive check.** There is no separate make target; the harness is already env-var driven and the Makefile only sets `MV_SHOT_FILTER` and `DISPLAY`, so exporting the rest in front of `make ds-shots` is the whole workflow. It reads `MV_SHOT_WIDTH`, `MV_SHOT_HEIGHT`, `MV_SHOT_SCALE`, `MV_SHOT_TOP_INSET`, `MV_SHOT_BOTTOM_INSET`, `MV_SHOT_DIR`, `MV_SHOT_THEMES` and `MV_SHOT_FILTER`. Device geometry comes from **`DesktopReviewMode.Presets`** ([DesktopReviewMode.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/DesktopReviewMode.cs)) — `360×640` insets 24/0 (small 16:9, the stress test), `360×800` 24/0 (most common budget device), `390×844` 47/34 (the design target), `412×915` 24/0, `430×932` 47/34. That table predates the workflow: it drove a runtime hotkey picker in the Windows review build, and until this pass **no screen had ever been rendered at those sizes headlessly.** Output goes to **`.shots-devices/<preset>/`**, gitignored alongside `.shots/` and `.arsim/`. The two 360 presets render pixel-identically apart from viewport height.
  - ⚠️ **`MV_SHOT_DIR` is used verbatim, so a RELATIVE path does not land at the repo root.** Only the *default* goes through the harness's `RepoPath()` helper (`Application.dataPath/../../..`); the env var overrides it with whatever string you export, and a relative one is then resolved by the batchmode process's own working directory — the Unity project folder, not the repo root. Nothing errors, the summary line prints the path it used, and the PNGs land in a directory **neither `.gitignore` covers**, i.e. they show up as untracked noise somewhere unexpected (or get committed). **Export an absolute path**, or stick to the default `.shots/` and the `.shots-devices/<preset>/` convention.
  - ⚠️ **Understand the mechanism before reading a device render.** Both PanelSettings are **Constant Physical Size @160 dpi**, so `1 USS px = 1 dp` *and layout does not scale on a different phone* — a narrower device simply gets **less width** and has to reflow. **Pixel resolution is therefore a non-issue**; usable **dp width** and **safe-area insets** are the entire risk surface, which is why the preset list is five (width, inset) pairs rather than a resolution matrix.
- **The gallery is the debugging weapon**: [GalleryScene.unity](src/app/MergulhoVirtual/Assets/DesignSystem/Gallery/) shows every component/variant/state with a live light/dark toggle (it swaps `PanelSettings.themeStyleSheet` at runtime; both assets *ship* Theme-Light) + resolved-token swatches. Reproduce UI bugs there first; if it reproduces it's a component bug (fix + regression test), if not it's screen wiring. One `Build*Section` method per component in [GalleryController.cs](src/app/MergulhoVirtual/Assets/DesignSystem/Gallery/GalleryController.cs) — and `make ds-shots` emits one PNG per section, so a component's whole state matrix is inspectable without opening Unity.

### Phase 3 — UI layer ([Assets/UI/](src/app/MergulhoVirtual/Assets/UI/)): the app shell and the V2 screens

**As-built — Slices 0–4 and 6 of [DESIGN_IMPLEMENTATION.md](DESIGN_IMPLEMENTATION.md) §7 have landed; only Slice 5 (SOS) is left.** The app boots into a **UI Toolkit shell** (one always-on `UIDocument`, an `MdRouter` owning every destination plus the persistent `MdNavigationBar`) with eight real UITK screens — **Início**, **Mergulho**, **Praias**, **Praia detalhe**, **Avistamentos**, **Espécie**, **Conteúdos** and **Conteúdo** — and one surviving uGUI screen (Sobre) routed through an adapter. The last two are the educational article library and are **not part of the V2 rebuild at all** — the feature postdates the prototype and has no Figma frame; see **Educational article library** under Architecture for the content pipeline behind them. **Slice 6 (2026-09-29) deleted the superseded uGUI screens** — `BottomNav`, `BeachesScreen`, `RegisterScreen`, `AnimalsScreen` — from `MainScene` along with their controllers and Editor builders; `MainScreen` survived it for the `ArTuning` panel alone, and that panel was removed 2026-09-29, leaving it an empty shell (see the scene layout above). Slice 0 re-based the foundations on the V2 brand (see the token bullets above); Slice 1 built the shell + Início and reduced `ScreenManager` to the AR gate; Slice 2 replaced the browsable Beaches list with Praias + Praia detalhe; Slice 3 replaced the uGUI Register screen with Reportar; Slice 4 replaced the uGUI AR HUD's top bar with the Mergulho screen. The single-screen `BeachesUiToolkitHost` / `BeachesUiScreenBuilder` / `useUiToolkitBeaches` arrangement that preceded all this is **gone**, as is the scene-root `BeachesScreenUITK` GameObject (the builder deletes it on sight) and the UITK `BeachesScreen.cs`/`.uss`.

Everything lives in `MergulhoVirtual.UI.asmdef`, which **references `MergulhoVirtual.DesignSystem` and nothing else**. Assembly-CSharp auto-references it back (which is also why [MoonPhase.cs](src/app/MergulhoVirtual/Assets/UI/Domain/MoonPhase.cs) could move here from `Assets/Scripts/` with no caller changes). **The dependency is one-way and load-bearing: `MergulhoVirtual.UI` may never reference Assembly-CSharp** — anything that needs AR, uGUI, Firebase, `Resources`, `PlayerPrefs` or a `MonoBehaviour` goes behind an interface here and an adapter there.

- **Interfaces** ([Assets/UI/Interfaces/](src/app/MergulhoVirtual/Assets/UI/Interfaces/)) — `IBeachCatalog` · `IBeachContent` · `ISpeciesCatalog` · `IConditionsService` · `ITideService` · `IActiveBeach` · `IBeachOverride` · `IOnboardingState` · `ISightingReports` · `IPhotoPicker` · `IArSelection` · `IArticleCatalog`, plus the engine-free data mirrors `BeachInfo` / `BeachContent` / `SpeciesInfo` / `ConditionsData` / `TideData` / `SightingDraft` / `SightingRecord` / `ArticleSummary` / `Article` / `ArticleBlock`. **Every implementation lives in ONE file** — [UiServiceAdapters.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/UiToolkit/UiServiceAdapters.cs) (Assembly-CSharp) — wrapping `ConditionsService`, `TideService`, `GPSHandler`, `ReverseGeocoding`, `BeachContentLibrary`, the `AnimalDef` assets, `JobQueue`, `GalleryPicker` and `PlayerPrefs`. A new screen that needs new data adds an interface here and an adapter there, never a direct service reference.
  - **`IActiveBeach` vs `IBeachOverride`** are the read and write sides of the same state, and the read side is deliberately **not** sourced from `ConditionsService` — that one falls back to a default beach when GPS has nothing, which is fine for fetching a forecast and a lie under the words "você está em". A **null active beach is a first-class, common state** (off every polygon, no fix yet, no GPS at all) that the Praias landing has a real UI for.
  - **`IOnboardingState`** is one `PlayerPrefs` int behind `OnboardingPrefKeys.WelcomeDismissed`, with an explicit `Save()` — Unity only flushes prefs on a clean quit, so without it the dismissed welcome card comes back after an app kill.
  - **`IArticleCatalog`** (`All()` / `Find(id)` / `IsAvailable`) is an immutable read of a file that ships in the build, so it has **no change event** — which is why both article ViewModels have a `Dispose()` with nothing to unsubscribe and why `AppUiHost` constructs **one** `ArticleCatalogAdapter` for both: a second instance would be a second copy of the same bytes, not a second source. `Find` returning **null is the host's cue not to navigate** (a stale link or a typo in the content file; a blank reading screen is worse than staying put), and `IsAvailable` is a *build* fact, never a connectivity one — see **Educational article library** under Architecture.
- **Domain + ViewModels** — plain C#, no UnityEngine, with `utcNow`/`toLocalTime` injected so tests are deterministic and timezone-proof. **Screens must not build user-visible strings**: every pt-BR string lives in a formatter and is pinned by a test. [ConditionsFormatter.cs](src/app/MergulhoVirtual/Assets/UI/Domain/ConditionsFormatter.cs) (the shared Onda/Maré/Lua/Vento/Água rows + "Atualizado:" + sparkline extremum labels, ported byte-for-byte from the legacy `ConditionsCardView`), [BeachContentFormatter.cs](src/app/MergulhoVirtual/Assets/UI/Domain/BeachContentFormatter.cs) (risk pill, stat values, alert bar, species behaviour line, tip numbering, sighting count) [ReportFormatter.cs](src/app/MergulhoVirtual/Assets/UI/Domain/ReportFormatter.cs) (pending-feed status pill + "Hoje, 9:32 · Baía do Sueste" caption) and [SpeciesCardFormatter.cs](src/app/MergulhoVirtual/Assets/UI/Domain/SpeciesCardFormatter.cs) (the AR card's title/binomial + its three spec rows). **Two return conventions, deliberately different: `null` means "hide this element", `"—"` (`ConditionsFormatter.NoValue`) is what a fixed stat slot shows when unfilled** — neither is ever an invented value, and `SpeciesCardFormatter` shows which applies where: its spec rows are stacked full-width lines with no sibling to strand, so an unfilled one is **dropped**, not dashed. ViewModels: `HomeViewModel`, `PraiasViewModel`, `BeachDetailViewModel`, `ReportViewModel`, `MergulhoViewModel`, `ArticlesViewModel`, `ArticleViewModel`, plus `BeachesViewModel`, which outlived its screen — it is kept solely for the override-choice list ("Automático (GPS)" + the key mapping) that `PraiasViewModel` borrows.
  - **[ArticleFormatter.cs](src/app/MergulhoVirtual/Assets/UI/Domain/ArticleFormatter.cs) + [ArticleTokens.cs](src/app/MergulhoVirtual/Assets/UI/Domain/ArticleTokens.cs)** are the article library's half of the same discipline: the index title/subtitle, the reading estimate, "Atualizado em 29 de setembro de 2026", the category heading, "12 conteúdos", the callout tone labels, the quote dash, the two cross-reference labels, and five deliberate aliases of `SpeciesMediaFormatter`'s video-player copy (an article's inline clip and a species page's are the same control on the same player, and two spellings of "Pausar" would teach a reader they are two different things). `ArticleTokens` holds the wire vocabulary — the block `type` and callout `tone` strings `build_articles.py` emits — as a **contract pinned by a test in this assembly**, not an implementation detail of the loader, exactly as `BeachContentTokens` is. ⚠️ **Most of this copy has no Figma frame behind it and is flagged `invented` at each declaration** — it wants a designer's eyes and every one is a one-liner to change. Two honesty rules show up here plainly: `ReadingTime` returns **null** rather than "0 min" when the word count is 0 (a derived number must not assert something the data cannot support), and `WordsPerMinute = 200` is documented as an **assumption, not a measurement of this audience**.
  - **`StateViewCopy` grew an articles section** (`ArticlesEmptyTitle` / `ArticlesEmptyBody` / `ArticlesErrorBody` + the two selectors). `ArticleFormatter.StateActionLabel` returns **null unconditionally**, so the state view draws no button: neither state is retryable, and offering a tap that cannot help is a lie the user pays for. The method exists rather than the screen simply knowing, so that if a reason to retry ever appears it appears there.
- **Navigation contract** ([Assets/UI/Navigation/](src/app/MergulhoVirtual/Assets/UI/Navigation/)): `IAppScreen` (`Key`/`Root`/`OnEnter`/`OnExit`/`SetEdgeInsets`) + `AppRoutes` — the four tab keys `Home`/`Mergulho`/`Praias`/`Avistamentos` in `AppRoutes.Tabs`, plus the sub-screen keys `PraiaDetalhe`/`Sos`/`Especie`/`Sobre`/`Conteudos`/`Conteudo`. **`Conteudos` and `Conteudo` are sub-screens, not a fifth tab** — V2's bottom bar has exactly four destinations and that is fixed, so the article library is reached the way Sobre is (Decision D2), from a card on Início; `AppRoutes.Tabs` is untouched. `MdRouter` registers screens by key, keeps them all alive and toggles `display`, so **per-visit work belongs in `OnEnter`/`OnExit`, never in a constructor**; the outgoing screen's `OnExit` always runs before the incoming `OnEnter`. **`Navigate` = a bottom-bar destination** (clears the back stack, moves the bar's selection); **`Push`/`Back` = a sub-screen** (the bar stays visible with the *originating* tab still selected — sub-screens have no tab of their own; the Figma SOS frame showing Praias highlighted is a copy-paste artifact). **An unregistered route is a deliberate no-op**: one `LogWarning`, `false` returned, nothing activated and the bar snapped back — that is how a route whose screen has not landed yet behaves, so never guard a tile behind an `IsRegistered` check just to hide it. Android's system Back button is deliberately not wired.
- **Screens** ([Assets/UI/Screens/](src/app/MergulhoVirtual/Assets/UI/Screens/)) — all four **built in code, no UXML** (the components' data APIs are code-only, so a UXML file would hold nothing but empty boxes) and all four **router-agnostic**: a screen raises an `AppRoutes` key on an event and the host decides `Navigate` vs `Push`, so screens stay unit-testable with no router.
  - [MergulhoScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/MergulhoScreen.cs) — the AR HUD (Tela 8). **A HUD, not a page**: it paints no opaque surface at all — the root, the 160dp `MvHeroHeader` control strip and the dock between them are transparent and `PickingMode.Ignore`, so the camera shows through and a tap on open water reaches the AR scene. Only two things are pickable: the hero's back button + beach pill (same selector as Praia detalhe, so picking a beach sets the GPS override) and the bottom-anchored species card, which is opened by `IArSelection` and dismissed by its ⨯. Its colours come from the `camera-*` extension tokens, which are identical in both themes because the backdrop is a lens.
  - [HomeScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/HomeScreen.cs) — Início: live conditions card (`ConditionsFormatter` rows + `MdSparkline` at baseline 1.28) + the 2×2 feature grid (Praias / Mergulho / Avistamentos / SOS) + a full-width "Sobre o projeto" card + the first-run welcome card.
  - [PraiasScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/PraiasScreen.cs) — the Praias tab root ("você está em"): `MvHeroHeader` + location card + two stat columns + the "Ciência cidadã" CTA. **It is not a list** — V2 deleted the browsable beach list, so the hero's selector pill is the only way to reach another beach, and picking one *sets the GPS override* rather than inventing a second notion of "the beach I'm browsing" that the AR spawner and the conditions fetch would not follow.
  - [PraiaDetalheScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/PraiaDetalheScreen.cs) — pushed from Praias, dismissed by the hero's back button. **The empty screen is the normal screen**: measured over the 17 beaches, risk level / best season / sighting peak / lifeguard hours / tips are filled for *none*, species for 3, environment tags for 11, advisories for 7, ideal tide for 4 — so every block is gated on a `Has*` flag and simply is not built when false (no placeholder strings, no empty cards, no headings over nothing). What keeps a content-empty beach from looking broken is the **description card**, which is not in the Figma frame and is the one deliberate addition: `places.json` has a 170–280 character description for all 17.
  - [ReportScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ReportScreen.cs) — the Avistamentos tab root; see **Sighting reports** above for the form, the submit semantics and the backend contract. Its back button is hidden because a tab root has nothing behind it (`ShowBackButton`).
  - [ArticlesScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ArticlesScreen.cs) — **Conteúdos**, the article index (`AppRoutes.Conteudos`), pushed from the Início "Conteúdo educativo" card. Cards grouped into category sections, each whole card a tap target raising an **article id**. ⚠️ **No Figma frame exists**, so it reuses the idioms Início and Praia detalhe established (16dp gutters, white outlined `MdCard`s on the off-white page, `title-medium` section headings, muted `label-small` credits) and invents no new visual pattern. Its back affordance is an `MdIconButton`, **not** an `MvHeroHeader`: an index has no cover photo, and a hero with no image is a 240–340dp empty box (its foreground is absolutely positioned, so it cannot collapse to content) — the same reason the reader has a `navRow` fallback.
  - [ArticleScreen.cs](src/app/MergulhoVirtual/Assets/UI/Screens/ArticleScreen.cs) — **Conteúdo**, the reader (`AppRoutes.Conteudo`), pushed **with a payload**. It is a **block renderer and the block list is its API**: it binds `ArticleViewModel.Blocks`, never `Current.Blocks`, so a kind from a newer `articles.json` renders as nothing without this screen remembering to skip it — and a kind its own `switch` does not handle is likewise skipped in silence, for the same forward-compatibility reason. Also ⚠️ **no Figma frame**. Three things worth knowing before editing it:
    - **The empty rendering is the normal rendering.** Every optional piece is gated on presence: one of the four shipped articles has **no hero** (so it draws the plain back-button row instead of a 240dp photo frame, which would read as a failed image load), and one of the three image blocks has **neither caption nor credit**. An empty caption row under a photo is the bug, not the absence.
    - **It takes `ISpeciesCatalog` / `IBeachCatalog` as optional constructor args** purely to name a cross-reference's destination. A `speciesRef` / `beachRef` block carries only a machine key the contract forbids rendering, and the two labels the ViewModel offers are fixed strings — the tubarões article has **five consecutive** species references, which with the fixed label alone would be five identical rows. The name is read straight off the catalog (`DisplayName`), exactly as `PraiaDetalheScreen` renders `species.DisplayName`, so **rule 2 still holds**: it is a catalog data value, not a string the screen built. With no catalog wired, or a key the catalog lacks, the name line is simply absent and the fixed label stands alone.
    - **Teardown in `OnExit` is load-bearing.** It shares the **same `IVideoPlayback` instance** as `EspecieScreen`; the router keeps screens alive and only toggles `display`, so without the explicit `Stop()` a clip streams on behind a hidden screen for as long as the app is open — a bandwidth and battery regression that looks like nothing. Sharing one player is safe *precisely because* both screens release it on the way out.
  - **Each screen's `.uss` is token-only** (`TokenDisciplineTests` scans `Assets/UI/**/*.uss`) **and must be listed in `AppUiBuilder.ScreenStylePaths`** ([AppUiBuilder.cs:44](src/app/MergulhoVirtual/Assets/Editor/AppUiBuilder.cs#L44)) **followed by `make ui-setup`**, or it is simply never loaded onto the panel — **no error, no warning, just a completely unstyled screen**. Add the sheet in the same commit as the screen. `ScreenStylePaths` is **eight** sheets now: Home · Mergulho · Praias · PraiaDetalhe · Report · Especie · **ArticlesScreen** · **ArticleScreen**. (The one thing it *does* fail loudly on is a path that resolves to nothing — the builder throws rather than registering a null sheet.)
- **Per-beach editorial content — [Resources/beaches_content.json](src/app/MergulhoVirtual/Assets/Resources/beaches_content.json)** (Slice 2), loaded by [BeachContentLibrary.cs](src/app/MergulhoVirtual/Assets/Scripts/Content/BeachContentLibrary.cs) and surfaced as `IBeachContent`. `places.json` keeps the geometry and the photo; this file adds everything the V2 beach page shows — `riskLevel`, `environmentTags`, `bestSeason`, `idealTide`, `sightingPeak`, `lifeguardHours`, `advisories[]`, `species[] {key, tag, behaviour}`, `tips[]`. Shape and conventions:
  - **The key is the `places.json` `name`, NOT `displayName`** (see the two-names footgun under **Location + reverse geocoding**), and `species[].key` is an `AnimalDef` asset file name under `Resources/Animals/`.
  - Unlike `places.json` it is a top-level **object** (`{schemaVersion, beaches: [...]}`), so it needs none of the `{"places": …}` wrapping `JsonUtility` forces on a bare array. `_comment`, `_todo` and `_sources` markers are for the content authors and are ignored by the parser; the file also carries its own `riskLevelValues`/`idealTideValues` vocabularies, which [BeachContentTokens.cs](src/app/MergulhoVirtual/Assets/UI/Domain/BeachContentTokens.cs) parses forgivingly (case/accents/whitespace) but **never guesses**: an unrecognized token logs and becomes `Unknown`, i.e. "not filled in".
  - **It never throws into a screen.** Missing file, malformed JSON, keyless entry, duplicate key, unknown token — each is logged once and degraded; the worst case is an empty catalog, which renders exactly like an all-blank entry. **Blank fields are legitimate**, not bugs: the screen hides the section. Filling it in is content work tracked in [docs/beaches-content-todo.md](docs/beaches-content-todo.md).
- **Edge insets are the host's job, NOT `SafeAreaElement`** (deliberate deviation, applies to every UITK screen): top/left/right safe-area insets are applied as *padding on the opaque content container* so its surface still paints under the status bar/notch — `SafeAreaElement` would leave that strip transparent, i.e. raw camera feed — and it works in the Device Simulator (mocked `Screen.safeArea`; `SafeAreaElement` skips editor panels). `AppUiHost` measures the insets in panel units and `MdRouter` decides who consumes each edge: the **bottom** inset is absorbed by the nav bar as padding (V2's 34dp home-indicator strip IS that padding, not a drawn element), so screens get bottom = 0 while the bar is visible. Screen roots stay transparent + `PickingMode.Ignore`.

## UI layout rules

> **Scope: legacy uGUI only.** Everything in this chapter is about `ScreenUI`'s uGUI panels — `AboutScreen` is the only one still routed, plus the now-empty `MainScreen` shell that `AppUiHost` still toggles on the Mergulho route. **New screens are UI Toolkit** and follow the design-system rules instead (flexbox, USS tokens, `AppScrollView`, `AppUiBuilder.ScreenStylePaths`); none of the Layout Group / anchor / RectMask2D advice below applies to them.

Most of the friction in the (now-deleted) Beaches/Animais screen rollout came from getting Layout Group settings wrong, then chasing visible symptoms (white squares, narrow rows, an overdrawn bottom nav) instead of the underlying layout cause. Internalize these defaults before editing any legacy screen under `ScreenUI`.

### Default Vertical/Horizontal Layout Group settings

Unless you have a specific reason to deviate, every Layout Group on a content panel — and the Horizontal Layout Group inside a list-item prefab — wants:

- **Control Child Size: Width ✓ Height ✓**. Without Height, every child's `LayoutElement.PreferredHeight` is silently ignored — the layout group only positions children, doesn't size them. Symptom: "I set `PreferredHeight = 300` but the banner still renders at 100." Without Width, same thing for `PreferredWidth`.
- **Child Force Expand: Width ✓ Height ✗**. Width force-expand is what makes children with no explicit `PreferredWidth` stretch to fill the column; without it, list rows shrink to their natural content width and look "squished." Height should *not* force-expand because a single child is meant to absorb leftover vertical space (see next bullet) — force-expanding height pads every child instead.
- Designate **exactly one child with `LayoutElement.FlexibleHeight = 1`** to absorb remaining vertical space — typically the `ScrollView` in a list panel, or `DescriptionText` in a detail panel. Other siblings declare a fixed `PreferredHeight`.

### LayoutElement is not auto-attached

`UI > Image`, `UI > Text - TextMeshPro`, `UI > Button`, etc. add their primary component plus the basics, but **never** add a `LayoutElement`. To set Preferred/Min/Flexible sizes, **Add Component → Layout Element** explicitly. Editor-new contributors look for the fields on the Image or RectTransform itself, don't find them, and assume the instructions are wrong — flag this proactively when writing Editor walkthroughs.

### Sibling order under `ScreenUI` is render order

uGUI renders later siblings on top of earlier ones, and raycasts hit later siblings first. Implications that recur in this project:

- **The uGUI `BottomNav` had to be the *last* child of `ScreenUI`** — otherwise any full-stretch screen panel later in the sibling list drew on top of it, hiding the nav and blocking taps. Slice 6 deleted it; `MdNavigationBar` on the UI Toolkit panel replaced it and sits above the whole Canvas at `sortingOrder 100`, so the problem cannot recur. The rule still generalizes to any always-on uGUI overlay you add — e.g. the `Panel` debug overlay, which is deliberately the *first* sibling and is therefore painted over by every screen.
- **Detail panels were siblings of their list panels** under each two-stage screen, both toggled inactive/active by the screen controller. Nesting the detail inside the list means hiding the list also hides the detail.
- **Screen container `Image` keeps `Raycast Target = on` deliberately** to block taps from bleeding through to whatever's underneath. Don't try to "fix" hidden BottomNav by moving it under a screen — fix the sibling order instead.

### Don't stretch-full anchor children of a layout group

Children of a Layout Group should have **non-stretch anchors** (top-center or top-left — first row of the anchor preset selector, *no Alt-click*). Stretch-full anchors `(0,0)/(1,1)` override the layout group's positioning and make the child fill its entire parent — the canonical "white square covers everything" bug. Stretch-full is right for screen *containers* (`BeachesScreen`, `AnimalsScreen`) directly under the Canvas, and wrong for any content child inside them.

### Diagnosing "white square covers the layout"

A bare `Image` with `Source Image = None` renders as a white rectangle the size of its `RectTransform`. When one is covering other elements, the cause is almost always one of:

1. **Stretch-full anchors** on the Image's RectTransform — see above.
2. **Layout group not controlling height** — the element is rendering at default 100×100 instead of its declared `PreferredHeight`.
3. **Sibling order** — the Image is a later sibling of the text/element it's covering.

Confirm by reading the saved scene file: `grep m_Name Assets/Scenes/MainScene.unity`, locate the offender, and read its `RectTransform` (anchors, sizeDelta) and adjacent `LayoutElement` block. Unity does not write to disk until Ctrl+S — when the user reports "X is missing/broken", ask them to save first. A stale `.unity` file is misleading; a freshly-saved one is source-of-truth and overrides screenshots.

### Tall detail panels need a ScrollRect

A detail panel with a fixed-height stack (banner + headings + multi-row text + chart) easily overflows the available height in landscape. Without a `ScrollRect`, the parent `VerticalLayoutGroup` shrinks children below their preferred height, and any TMP with `Overflow Mode = Overflow` spills onto the next sibling — that's how `ConditionsCard`'s "Atualizado: ..." freshness line ended up rendering on top of `TideSparkLine` before `BeachesDetail` was wrapped.

Pattern (used in `BeachesDetail`):
```
BeachesDetail (Image bg only — no layout group, no ContentSizeFitter)
└── Scroll View (ScrollRect, vertical only; full-stretch with bottom = nav-bar clearance)
    └── Viewport (Mask)
        └── Content (VerticalLayoutGroup + ContentSizeFitter Vertical=Preferred)
            └── BannerImage / NameText / DescriptionText / ConditionsCard / TideSparkLine / BackButton
```

Notes that bit us building this:

- **Move the `VerticalLayoutGroup` off the screen container onto `Content`.** Leaving it on `BeachesDetail` while children move under `Content` makes the layout group try to lay out the lone Scroll View child and ignore everything below.
- **`Content` needs `ContentSizeFitter` with `Vertical Fit = Preferred Size`**, otherwise its height stays at the Viewport's height and there's nothing to scroll. The Vertical Layout Group on `Content` provides preferred height; the fitter applies it to the RectTransform.
- **Keep bottom clearance** (Scroll View's RectTransform `Bottom ≈ 220`) so the last item doesn't get covered by the bottom nav.
- **Reset scroll position on entry**: a two-stage uGUI screen has to set `detailScroll.verticalNormalizedPosition = 1f` when it shows the detail — without this, re-entering a detail starts at wherever you last scrolled.
- **`Image.preserveAspect` for runtime-assigned sprites**: when an `Image`'s `Source Image` is left empty in the editor (because the sprite is loaded by code), the Inspector hides the `Preserve Aspect` toggle — but the underlying `m_PreserveAspect` field is still serialized. Set it from script (`detailImage.preserveAspect = true;`) next to the sprite assignment, not via the Inspector.

### Code-driven Editor scaffolders for new screens

> **Legacy pattern — no uGUI screen scaffolder survives.** New screens are UI Toolkit, built in C# inside `MergulhoVirtual.UI` and wired by the single [AppUiBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AppUiBuilder.cs) shell scaffolder (`make ui-setup`). Slice 6 deleted `RegisterScreenBuilder`, `AnimalsScreenBuilder` and `VideoSectionBuilder` with the screens they built. The *reasoning* below still generalizes — and still applies to the three uGUI scaffolders that remain, none of which builds a screen: [InstagramWidgetBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/InstagramWidgetBuilder.cs) (a section inside AboutScreen), [ArStabilizationBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/ArStabilizationBuilder.cs) (the AR rig only, since its ArTuning panel was removed — it now builds no UI at all) and [AnimalViewerRigBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/AnimalViewerRigBuilder.cs) (the 3D turntable). The mechanics of "build a whole screen under `ScreenUI` and bind it into the nav" do not: there is nothing left to bind into.

For any non-trivial uGUI hierarchy (multiple cards, ScrollRect, several rows of inputs), prefer a `Tools > Mergulho Virtual > Create <Thing>` Editor menu over hand-building in the Inspector — one menu click applies every UI rule above (VLG settings, RectMask2D over `Mask`, sibling order, nav-bar clearance, RoundedRectCard material, ScrollRect→Viewport→Content) and auto-wires every `SerializeField` via `SerializedObject`, instead of leaving it to Inspector dragging. `AnimalViewerRigBuilder` also shows the pattern for a builder that owns a non-UI scene ROOT rather than a canvas child.

Why it's worth the upfront code:

- **Every UI rule is enforced once**, in code, instead of re-discovered per screen via the "white square covering everything" failure mode. New contributors crib from existing factory helpers instead of reinventing.
- **Design tokens are explicit.** Palette colors (`BgNavy`, `CardSurface`, `Accent`, …) and spacing constants live as `static readonly` fields at the top — change one value, re-run the menu, see it everywhere.
- **No Inspector dragging.** Auto-wiring eliminates the most common "I added a screen but the button does nothing" failure mode.
- **Idempotent re-runs.** Prompts to *Replace* if the screen already exists, so iterating on layout = edit code → re-run → save scene.

Limits — don't reach for this when:

- **You're going to hand-edit the screen in the Inspector afterwards.** Re-running the menu wipes those edits. Pick one path per screen: iterate entirely in code (re-run the menu) OR entirely in the Editor (don't re-run). Mixing alternately loses work — say so explicitly when handing the workflow to the user.
- **You need to wire references to assets the scaffolder can't infer** (Animator controllers, prefab references not loadable by a stable name). Either load via `Resources.Load`/`AssetDatabase.LoadAssetAtPath` from inside the scaffolder so the wiring is also reproducible, or accept that those slots need re-dragging after each re-run.
- **The screen is trivial** (one Image + one TMP). Splash-class screens don't need a scaffolder; the cost only pays off at ≥3 layout groups or ≥4 wired references.

When you do build a new scaffolder, follow [InstagramWidgetBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/InstagramWidgetBuilder.cs)'s structure: low-level helpers (`NewUI`, `StretchFull`, `NewText`, `AddLayoutElement`) at the bottom, factory helpers in the middle, the build sequence at the top under `[MenuItem]`. Keep the sequence comment-banner-separated by section so it reads top-to-bottom like a wireframe.

## TMP sprite assets and emoji icons

The pill UI ([ConditionsPillView.cs](src/app/MergulhoVirtual/Assets/Scripts/UI/ConditionsPillView.cs)) inlines emoji glyphs (🌊 wave, 🌑–🌘 moon phases) by emitting Unicode codepoints from C# and letting TMP route them through a sprite asset. This was painful to wire up the first time; the gotchas below are the ones that actually wasted hours, not the ones in TMP's docs.

### Wiring path

`TMP_Text` → font asset (`LiberationSans SDF`) finds the codepoint missing → falls through to **TMP Settings → Default Sprite Asset** (Project Settings → TextMesh Pro) → that asset's `m_SpriteCharacterTable` matches `m_Unicode` → renders the sprite. Custom sprite assets live alongside their source PNGs (e.g. [Assets/Images/UI/moon/moon_sheet.asset](src/app/MergulhoVirtual/Assets/Images/UI/moon/)). Chain additional sprite assets via the **active Sprite Asset's own `Fallback Sprite Assets` list** — *not* via the font asset's Fallback Font Assets list, which only accepts `TMP_FontAsset` (sprite assets are a different type and the slot rejects them).

### Sprite-asset gotchas (in order of nastiness)

- **`Create → TextMeshPro → Sprite Asset` on a multi-selection produces one `.asset` per source texture, not one bundled asset.** To get a single asset with N entries you need a single source texture (a sprite sheet) sliced into N sprites, then run Create on the sheet. Combining individual PNGs into a sheet is one ImageMagick line: `convert a.png b.png ... +append sheet.png`. Resize source PNGs to a sane size first (`-filter Lanczos -resize 128x128 -strip`) — OpenMoji ships at 618×618, which is 25× the texture memory you actually need for a UI pill.
- **All sprites in a single asset (or reachable via fallback) must share consistent dimensions.** TMP sizes glyphs by their `GlyphRect` width/height relative to the font's em — a 618-tall sprite chained next to a 128-tall sprite renders ~5× larger than the others. Resize sources, or hand-edit the metrics block to a uniform scale.
- **Slice pivot at sheet creation time bakes into the glyph's `m_HorizontalBearingX`.** Default sprite slice pivot is **Center**, which makes TMP set `BX = -width/2` — every emoji renders centered on the cursor and overlaps the previous character. Set **Pivot = Bottom Left** in the Sprite Editor *before* creating the Sprite Asset. If the asset already exists with bad bearings, **the `Update Sprite Asset` button does NOT recompute metrics from new pivots** — fix by editing the `.asset` YAML directly: `sed -i 's/m_HorizontalBearingX: -64/m_HorizontalBearingX: 0/g' path/to/asset.asset`.
- **Vertical alignment with text needs `m_HorizontalBearingY` ≈ 75% of sprite height.** With sprite height 128, BY=64 centers the sprite on the baseline (half hangs below text), BY=96 puts the bottom on the baseline and the top near cap-height. Same `sed` pattern works.
- **Unicode codepoints in `m_SpriteCharacterTable` are stored as DECIMAL, not hex** — `🌕` = `1F315` hex = **127765** decimal. Filenames like `1F315_color.png` do **not** auto-populate this column on Sprite Asset creation; either set each entry manually in the Inspector (it accepts hex there), or hand-edit the YAML and remember to convert.
- **The shipped `EmojiOne` sample sprite asset only maps 16 codepoints** — face emoji (smileys, hearts, frowns). It does NOT cover moons, waves, weather, food, or anything else. Don't recommend "test against EmojiOne first" — it'll miss almost every codepoint and the user wastes time chasing why a glyph "doesn't work."
- **`TMP_SpriteAsset` is not a `TMP_FontAsset`.** It will never appear in the Font dropdown on a `TMP_Text` component. Sprites flow in only via the fallback chain described above. New users hunting the Font dropdown for "EmojiOne" will conclude something's broken — flag this proactively.

### Source PNGs and content-creator pipeline

OpenMoji (https://openmoji.org, CC-BY-SA) is the chosen emoji set in this project. Filenames are `<HEX_CODEPOINT>_color.png`. Standard import workflow:

1. Download the codepoint PNGs to [Assets/Images/UI/moon/](src/app/MergulhoVirtual/Assets/Images/UI/moon/) (folder name is historical — extends to non-moon icons too).
2. `cd` there and resize: `convert *.png -filter Lanczos -resize 128x128 -strip <out>.png` (or per-file).
3. (Multi-emoji case) Combine into a sheet: `convert a.png b.png ... +append sheet.png` — order matters, append left to right; choose an order that's stable so future re-renders don't shuffle codepoints.
4. Unity import: Texture Type = **Sprite (2D and UI)**, Sprite Mode = **Single** (one PNG) or **Multiple** (sheet) → **Pivot = Bottom Left** → Apply.
5. Right-click → **Create → TextMeshPro → Sprite Asset**.
6. Open the asset → set the `Unicode` column on each `m_SpriteCharacterTable` entry (hex in the Inspector, decimal in the YAML).
7. Wire as TMP Default Sprite Asset OR add to an existing asset's Fallback Sprite Assets.

### Emitting emoji from C# code

Use C# `\U` escapes for the codepoint (`\U0001F315` for full moon — *uppercase* `U`, eight hex digits, since these are non-BMP). **Do not** rely on pasting literal emoji into Unity's Inspector text field — some Unity versions silently strip non-BMP codepoints when typed/pasted into the Inspector, even though the same characters render fine when set from script. If a Unicode emoji "doesn't render" but `<sprite=N>` works, suspect Inspector stripping before suspecting the sprite asset wiring.

## Rounded UI corners — use the SDF shader, not `Mask`

`UnityEngine.UI.Mask` clips via the GPU stencil buffer, which is binary (alpha threshold → in/out, no AA). When the masking sprite has rounded corners (e.g. [background_crop.png](src/app/MergulhoVirtual/Assets/Images/UI/background_crop.png)), children get a 1-pixel-wide stair-step boundary along every curve. Don't try to fix it by upscaling the mask sprite — the source is fine; the stencil test is the bottleneck. The Beaches list cards initially used `Mask` and produced visibly jagged photo corners; the project switched to a small custom shader instead.

The rounded-card pattern in this project (Beaches list cards, reusable for Animals etc.):

- **Shader**: [Assets/Shaders/UI/RoundedRect.shader](src/app/MergulhoVirtual/Assets/Shaders/UI/RoundedRect.shader). `UI/RoundedRect` — drop-in for `UI/Default` plus an SDF rounded-rect coverage with `fwidth`-based AA along the curve.
- **Material**: [Assets/Materials/UI/RoundedRectCard.mat](src/app/MergulhoVirtual/Assets/Materials/UI/RoundedRectCard.mat). One asset, shared across all cards (so they batch). The `_Radius` property sets the corner radius in canvas units.
- **`RectMask2D` on the card root** — non-negotiable. The shader rounds corners of the parent `RectMask2D`'s `_ClipRect`, **not** the Image's own mesh rect. That decoupling is what lets a photo Image with `AspectCover EnvelopeParent` (oversized to cover-fit the card) still produce rounded corners aligned to the card edges. Without `RectMask2D`, the shader falls back to UI/Default behavior — square corners — and the photo overflows past the card.
- **Apply the material to every visible Image** in the card (background fill, photo, gradient overlay). RectMask2D's clip applies via `_ClipRect`, but only Graphics that actually use the SDF shader get rounded — anything else inherits a binary rectangular clip via `UnityGet2DClipping` and produces square corners poking into the rounded region.

Reference structure — this was `Assets/Prefabs/UI/ListItem.prefab`, the Beaches/Animais photo card, which Slice 6 deleted with its two screens. The **surviving** example is the Instagram card at `ScreenUI/AboutScreen/AboutScroll/Viewport/Content/InstagramSection/InstagramCard` (built by [InstagramWidgetBuilder.cs](src/app/MergulhoVirtual/Assets/Editor/InstagramWidgetBuilder.cs)); the shape the pattern wants is:
```
Card (RectMask2D + Image[surface fill, RoundedRectCard mat] + Button)
├── Thumbnail        (Image[no sprite at design time, RoundedRectCard mat] + AspectRatioFitter + AspectCover)
├── GradientOverlay  (Image[card_gradient_bottom, RoundedRectCard mat], bottom-anchored)
└── Title            (TMP_Text — NOT the RoundedRectCard material)
```

Footguns this combination dodges that the previous `Mask` setup didn't:
- Stencil aliasing on curves (the original problem).
- Photo overflow when AspectCover oversizes the rect — RectMask2D rectangularly clips it cleanly (no jaggies on axis-aligned edges), and the SDF rounds the corners on top.
- Gradient corners poking out — applying the same material to the gradient means its bottom corners cleanly follow the card's rounded shape.
- **`Mask` + transparent Image clips everything to nothing.** A `Mask` component needs its `Graphic` (usually an Image) to render to the stencil buffer, but `CanvasRenderer.cullTransparentMesh = true` (the default) drops a fully-transparent mesh entirely → no stencil mark → all children inside the mask get clipped away. Symptom: a screen that's "just the background color, no children visible" right after wiring up a ScrollRect with a fresh Viewport. Fix: use `RectMask2D` (which clips by rect, no Graphic required) instead of `Mask`, or, if you must use `Mask`, give the Image a non-zero alpha (even `1/255` works) or set `cullTransparentMesh = false` on its CanvasRenderer.

Don't apply the material to TMP text — TMP has its own SDF font rendering with its own clip-rect handling, and swapping the material breaks the font.

## Adding a new shark species

End-to-end workflow from a Sketchfab download to a beach-spawned, animated, looping AR shark. Assumes the source is a typical Sketchfab FBX bundle (`source/<file>.fbx` + `textures/*.png`); the gotchas below are specific to that source — Sketchfab's FBX exports don't ship with import-friendly defaults for Unity 6 + URP.

### 1. Drop assets into the project

Mirror the existing layout — one folder per species, kebab-case name. `source/` and `textures/` are seeded by hand; `Materials/` is created by step 2's *Extract Materials* and stays alongside them:

```
Assets/Models/<kebab-name>/
├── source/<name>.fbx     ← rename to drop spaces and parens; asset paths need to stay clean
├── textures/*.png        ← rename to a clean Species_<MapType>Map.<ext> convention before import (drop Sketchfab's V10/4K/00000-suffixed names)
└── Materials/            ← populated by Extract Materials in step 2; don't pre-create
```

Five species ship, all structurally identical — [great-hammerhead-shark](src/app/MergulhoVirtual/Assets/Models/great-hammerhead-shark/), [tiger-shark](src/app/MergulhoVirtual/Assets/Models/tiger-shark/), [lemon-shark](src/app/MergulhoVirtual/Assets/Models/lemon-shark/), [nurse_shark](src/app/MergulhoVirtual/Assets/Models/nurse_shark/), [reef_shark](src/app/MergulhoVirtual/Assets/Models/reef_shark/) — note the folder, prefab and controller naming has drifted between kebab-case, snake_case and PascalCase across species; match whatever the species already uses rather than normalising. Each has a matching prefab at [Assets/Prefabs/Sharks/<name>.prefab](src/app/MergulhoVirtual/Assets/Prefabs/Sharks/) (`hammerhead` · `tiger_shark` · `lemon_shark` · `nurse_shark` · `reef_shark`), an Animator Controller at [Assets/Animations/<Name>.controller](src/app/MergulhoVirtual/Assets/Animations/), and an `AnimalDef` of the same name under [Resources/Animals/](src/app/MergulhoVirtual/Assets/Resources/Animals/) — the `.asset` name is the species key the beach content file and the report form use.

### 2. Fix FBX import settings (Sketchfab gotchas)

Click the FBX in the Project window. For each tab in the Inspector:

- **Rig tab → Animation Type**: defaults to **None** on Sketchfab FBXs, which means **no Animator component is added when you instantiate the prefab** — the GameObject in the Hierarchy will only have a Transform. Set to **Generic** → Apply. (If Generic still produces no Animator, the FBX may be transform-animated only — try **Legacy** as fallback, which adds an `Animation` component instead.)
- **Animation tab → Clips list → per-clip Loop Time**: defaults to **off**. The clip will play once then freeze. Tick **Loop Time** for each cycle that should loop, then Apply. There is **no Loop setting on the Animator Controller** — looping is entirely driven by this checkbox on the clip, so visually diffing two `.controller` files won't reveal the cause when one shark loops and another doesn't.
- **Materials tab → Extract Materials...**: extracts to a folder you choose (see "Linux folder picker quirk" below). Then for each extracted `.mat`, switch its **Shader** to **Universal Render Pipeline > Lit** — the default Standard shader renders magenta under URP. Wire textures: ColorMap → **Base Map**; NormalMap → **Normal Map** (click "Fix Now" when prompted to mark it as a normal map); MetalnessMap → **Metallic Map** with the Smoothness slider as a quick approximation, or pack metallic+inverted-roughness into one texture for a correct PBR result.
- **Model tab → Scale Factor**: defaults to **1.0**, which imports the FBX in its native units — for Sketchfab assets that varies wildly (millimeters, centimeters, "100×life-size"), and the three reference FBXs in this project originally spanned a ~50× inherent-size range. **Convention**: Scale Factor bakes the **real-world body length in meters**, prefab Transform scale stays at `(1, 1, 1)` always, and `1 Unity unit = 1 m` everywhere downstream. To find the right value, drop the FBX into the Hierarchy at the default Scale Factor `1.0`, then run **Tools → Mergulho Virtual → Print Shark Sizes** ([SharkSizeReporter.cs](src/app/MergulhoVirtual/Assets/Editor/SharkSizeReporter.cs)) — it prints native bounds and the exact Scale Factor to type back into the importer for each species' real-world target length, then re-run after Apply to confirm `✓ already at target`. Add new species to `TargetLengthsM` at the top of the script before running so it produces a target line for them.

### 3. Animator Controller

Animator Controllers live in [Assets/Animations/](src/app/MergulhoVirtual/Assets/Animations/) — one `.controller` per species, shared across the project (not colocated with the model folder). This keeps the Animations folder as a single browse target when comparing or copying state machines between species.

- Project window → [Assets/Animations/](src/app/MergulhoVirtual/Assets/Animations/) → right-click → **Create > Animator Controller**, name it after the species (existing files: `HammerheadShark.controller`, `TigerShark.controller`, `lemon_shark.controller` — naming has drifted between PascalCase and snake_case; pick whichever matches your prefab name and stop worrying about it).
- Double-click the controller → Animator window opens.
- Expand the FBX in the Project window (click its arrow to reveal nested clips) → drag the animation clip into the Animator window. Unity creates a default state auto-connected from `Entry` — that state plays automatically.
- The controller is assigned to the **prefab's** Animator component in the next step, *not* to a Hierarchy instance — the spawner instantiates from the prefab at runtime, so a Hierarchy assignment never sees the spawned object.

### 4. Build the prefab

- Drag the FBX from `Assets/Models/<kebab-name>/source/` into the Hierarchy temporarily.
- Inspector → Animator component → drag the controller from step 3 into the **Controller** slot.
- **Leave Transform Scale at `(1, 1, 1)`** — real-world length is baked into the FBX via Scale Factor in step 2. Tune Position + Rotation only, per-species, so the body broadside is visible from the AR origin; rotation is usually `Y = 90°` (FBX nose typically points along +X). Spawn distance is per-species since a 4 m shark frames very differently from a 2.5 m one at the same `z` — expect to push `z` farther than the legacy `(-4, 0, 4)` once models are at real-world size (a 4 m shark at 4 m straddles the camera).
- Drag the Hierarchy GameObject into [Assets/Prefabs/Sharks/](src/app/MergulhoVirtual/Assets/Prefabs/Sharks/) → **choose `Prefab Variant`** when prompted (NOT *Original Prefab*). A Variant live-references the FBX, so future Scale Factor changes — and any other FBX-side fixes — propagate to the prefab automatically. *Original Prefab* bakes the entire bone hierarchy into the prefab as static data; after that, changing FBX Scale Factor only rescales mesh vertices (not the baked bones), the SkinnedMeshRenderer skins through the old bones, and the rendered shark stays at the old size despite the importer reporting the new value. Discovered the hard way with `tiger_shark`, which had to be recreated as a Variant once we tried to bake real-world scale.
- Delete the Hierarchy instance — the spawner owns the lifecycle.

To later tweak the controller, scale, or position, double-click the prefab to enter **Prefab Mode** and edit there; spawned instances pick up the changes next play.

### 5. Wire into the spawner

- Hierarchy → select **`Beach Shark Spawner`** (root GameObject).
- Inspector → **Beaches** list → find the beach entry whose name matches a [places.json](src/app/MergulhoVirtual/Assets/Resources/places.json) **`name`** exactly (case + accents — **not** the pt-BR `displayName`; several differ, e.g. `Sueste Beach` vs `Baía do Sueste`) → expand its `Shark Prefabs` array → `+` → drag the prefab in.
- If a beach doesn't already have an entry in the list, add one with the matching name first.

### 6. Test in editor

Press Play → the GPS stub resolves to Cacimba do Padre, so unless that is the beach you wired, tap **Praias** in the bottom bar and use the **hero selector pill** to pick the wired one → the prefab should spawn under `Beach Shark Spawner` and animate. The AR view itself is the **Mergulho** tab.

### 7. Add the `AnimalDef` — **not optional any more**

The `AnimalDef` ScriptableObjects under [Resources/Animals/](src/app/MergulhoVirtual/Assets/Resources/Animals/) are the app's **species catalog**: `UiServiceAdapters.SpeciesCatalogAdapter` loads them for the Praia detalhe species cards and the Reportar species chips, and `beaches_content.json`'s `species[].key` is the `.asset` file name. (They also still back the Animais catalog + 3D viewer, which is currently unrouted — see that section.) **A species with no `AnimalDef` exists in AR and nowhere else.** To add one:

- **Assets > Create > Mergulho Virtual > Animal** → save under `Resources/Animals/<kebab-name>.asset`.
- Fill in `displayName` (Portuguese), `binomial` (scientific name — leave blank rather than guessing; the screens then show the common name alone), `approximateSize` / `diet` / `behaviour` (the AR card's spec rows, same rule — a blank drops the row), `imageName` (string — the filename of a sprite-typed image at `Resources/Animals/<imageName>.<ext>`, no extension in the field), `description`, `prefab` (the same one wired into `BeachSharkSpawner`), `photoCredit` (e.g. `Foto: Author / CC BY-SA 4.0 (Wikimedia Commons)`) and `modelCredit` on the matching one-line form (`Modelo: Author / CC BY 4.0 (Sketchfab)`) — see the credit convention under **Species catalog + 3D viewer rig**; a pasted model description is not a credit. Check the model's licence while you are there: two of the five shipped models are CC BY-NC, which is a problem for commercial distribution. The viewer auto-fits the camera per shark (see "Camera framing" in the architecture section), so you usually don't need to touch `viewerScale` / `viewerOffset` — leave them at defaults `(1,1,1)` / `(0,0,0)` unless you want to nudge the body within the auto-framed pose. To attach educational clips, add entries to the `videos` list (each a `title` + a public MP4 URL — see **Inline video player**); they render as tap-to-play cards below the description with no code or scaffolder change.
- **Source the image automatically**: [tools/populate_animals.py](tools/populate_animals.py) (mirrors `populate_beaches.py`) reads every `.asset` under `Resources/Animals/`, looks up Wikipedia by scientific binomial (then common name) for empty fields, downloads the lead image, fills `description` + `imageName` + `photoCredit`, and auto-generates a Sprite-typed `.meta` next to the image (cloned from `tiger_shark.jpg.meta` with a fresh GUID, so Unity imports it as Sprite without an Inspector trip). Add the species to `ARTICLE_TITLE_CANDIDATES` at the top of the script (asset filename → `[binomial, pt common name, en common name]`), then `python3 tools/populate_animals.py --apply`. Stdlib only, no venv. Default behavior only fills empty fields — pass `--force` to rewrite existing values.

No code or scaffolder re-run needed — both the Animais controller and `SpeciesCatalogAdapter` do `Resources.LoadAll<AnimalDef>("Animals")` lazily on first use. To show the species on a beach page, also add `{"key": "<asset name>"}` to that beach's `species` array in [beaches_content.json](src/app/MergulhoVirtual/Assets/Resources/beaches_content.json).

### Replacing an existing species' FBX breaks every reference to its prefab

Because the shark prefabs are **Prefab Variants** of the FBX, the variant's root GameObject has no fileID of its own — Unity *computes* it from the FBX's internal object ids, which the importer derives from node names. Swap the FBX for a different export (new rig, renamed root node) and that computed fileID changes — and **every serialized reference to the prefab root silently dangles**, even though the prefab's GUID and file path are unchanged. The references die in *both* wiring sites at once:

- `AnimalDef.prefab` on the `.asset` under [Resources/Animals/](src/app/MergulhoVirtual/Assets/Resources/Animals/) → the Espécie screen drops its "Modelo 3D" section entirely (`SpeciesModelViewerAdapter.Show` returns `false` with one `LogWarning`; nothing appears on screen).
- Each `Shark Prefabs` slot in `Beach Shark Spawner`'s **Beaches** list — and a prefab wired into *multiple* beaches breaks in **every** entry; re-dragging it into one beach doesn't heal the others (this exact half-fix happened with nurse_shark: Sancho re-wired, Cacimba do Padre left stale).

**After replacing any FBX under `Assets/Models/<species>/source/`**, re-drag the prefab from [Assets/Prefabs/Sharks/](src/app/MergulhoVirtual/Assets/Prefabs/Sharks/) into: (1) the `prefab` slot of the species' `.asset` in `Resources/Animals/`, and (2) every beach entry listing it in `Beach Shark Spawner` → save the scene. Broken slots show **"Missing (Game Object)"** in the Inspector. Also re-check the FBX import settings (step 2) and the prefab's Animator Controller — a new export resets to Sketchfab-default rig/loop settings.

### Linux folder picker quirk for "Extract Materials..." / "Extract Textures..."

Under GTK, Unity's folder picker opens in CREATE_FOLDER mode and shows a "Name" / "filename" field that looks like a save dialog. It is still a folder picker — the name field is the **new subfolder** to create at the navigated location. Type `Materials` (or `Textures`), navigate into the species folder, and click the action button. An empty name will be rejected; pick a real name.

## Unity Editor — quick reference

The maintainer is learning Unity. These are the Editor operations that come up often in this repo:

- **Create a root GameObject**: right-click empty space in the Hierarchy → *Create Empty*. For a child, right-click the intended parent instead. Rename in place (F2 or double-click).
- **Attach a script as a component**: select the GameObject → Inspector → *Add Component* at the bottom → start typing the class name. Prefer attaching to an existing, relevant GameObject over creating a new empty one — only create a dedicated GameObject when the logic truly needs its own lifecycle (independent enable/disable).
- **Wire a `[SerializeField]` slot**: drag a GameObject from the Hierarchy (or an asset from the Project window) onto the field in the Inspector. For typed MonoBehaviour fields, drop the GameObject that has that component — Unity resolves it automatically.
- **Don't trust this CLAUDE.md for exact Hierarchy structure**: always verify against the actual `.unity` file before giving or following Editor instructions (grep `m_Name:` in `Assets/Scenes/*.unity`). The structure here drifts as the project evolves.
- **"Missing (Mono Script)" on a component**: the `.cs` file was deleted but the component reference survived on any GameObject/prefab that had it. Fix: select the GameObject, find the component showing "Missing", click its ⋮ (kebab) menu → *Remove Component*. If many GameObjects are affected, menu *GameObject > Remove Missing Scripts*. Scene-level overrides (components added on top of a prefab instance) persist even after the underlying script is gone; sometimes easier to delete the whole orphan `MonoBehaviour` block from the `.unity` file directly, then reimport.
- **Before creating a prefab**: check [Assets/Prefabs/](src/app/MergulhoVirtual/Assets/Prefabs/) — the scene GameObject you're looking at is often already an instance of a prefab that exists on disk (scene YAML shows `m_CorrespondingSourceObject` with a prefab GUID → search the project's `.meta` files for that GUID). You can reference the existing prefab directly; no need to drag-to-Project.
- **Dragging from Hierarchy to Project fails with "Missing script"**: almost always an orphan component on the source GameObject — remove it first (see above).
- **Script recompile**: Unity recompiles when you Alt-Tab back to the Editor after external edits. A compile error blocks Play mode; check the Console.
- **Refer to files by their actual on-disk name, not by a name you suggested as a rename.** Unity names auto-created assets after their source — `Create → TMP → Sprite Asset` on `moon_sheet.png` produces `moon_sheet.asset`, not `MoonSpriteAsset.asset`; the same applies to extracted Materials, generated Sprite Atlases, and `.meta` files. If you suggest a rename, present it as optional and **keep using the original name in any subsequent step** until the user confirms the rename happened. Don't compose later instructions around the suggested name as if it were already on disk — that produces "I don't have a file called X, only Y" pushback.
